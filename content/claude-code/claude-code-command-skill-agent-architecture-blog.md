# Claude Code의 Command vs Skill vs Agent: 세 가지 확장 패턴의 아키텍처 차이

## 한눈에 보기

Claude Code는 세 가지 확장 패턴을 제공합니다. **Command**는 슬래시로 호출하는 명시적 명령이고, **Skill**은 자동으로 주입되는 지속적 지침이며, **Agent**는 독립 컨텍스트에서 실행되는 서브 프로세스입니다. 이 글에서는 세 패턴이 왜 다르게 설계되었는지, 각각의 격리 수준과 컨텍스트 관리 방식이 어떻게 다른지, 그리고 언제 어떤 패턴을 선택해야 하는지를 탐구합니다.

---

## 들어가며

Claude Code를 사용하다 보면 자연스럽게 마주치는 질문이 있습니다. `/init`이나 `/doctor` 같은 슬래시 커맨드는 무엇이고, `CLAUDE.md` 파일에 작성한 지침은 어떻게 적용되며, Claude가 스스로 생성하는 Task는 왜 별도로 존재하는 것일까요?

이 세 가지는 Claude Code의 확장 패턴입니다. 각각 **Command**, **Skill**, **Agent**라고 부르며, 서로 다른 문제를 해결하기 위해 서로 다른 방식으로 설계되었습니다.

흥미로운 점은 이 세 패턴이 단순히 "기능의 종류"가 아니라, **격리 수준**, **컨텍스트 관리 방식**, **실행 인터페이스**라는 근본적인 설계 차원에서 다르다는 것입니다. 마치 운영체제에서 인라인 코드, 공유 라이브러리, 독립 프로세스가 각각 다른 역할을 하듯이, Claude Code의 세 패턴도 각자의 영역에서 최적화된 역할을 수행합니다.

이 글에서는 세 패턴의 아키텍처 차이를 깊이 있게 살펴봅니다. 단순히 "이렇게 사용하세요"가 아니라, "왜 이렇게 설계되었는가"를 중심으로 탐구합니다.

---

## 세 가지 패턴의 기본 구조

먼저 각 패턴이 무엇인지 간단히 정리해 보겠습니다.

### Command: 명시적으로 호출하는 프롬프트 매크로

Command는 슬래시(`/`)로 시작하는 명령어입니다. 사용자가 `/review`라고 입력하면, 미리 정의된 프롬프트가 현재 대화에 주입됩니다.

```markdown
# .claude/commands/review.md
코드 리뷰를 수행해주세요. 다음 관점에서 검토합니다:
- 보안 취약점
- 성능 이슈
- 코드 스타일 일관성
- 테스트 커버리지
```

Command는 **반복 작업의 피로도**를 해결합니다. 매번 같은 프롬프트를 입력하는 대신, 짧은 명령어로 대체할 수 있습니다.

### Skill: 자동으로 적용되는 지속적 지침

Skill은 `CLAUDE.md` 파일에 정의된 지침으로, 모든 대화에 자동으로 적용됩니다.

```markdown
# CLAUDE.md
## 코딩 규칙
- TypeScript 사용, any 타입 금지
- 함수는 단일 책임 원칙 준수
- 모든 public 함수에 JSDoc 주석 필수
```

Skill은 **Claude의 기본 행동 양식을 수정**합니다. 프로젝트의 코딩 스타일, 선호하는 패턴, 금지된 관행 등을 정의하면 매 응답에서 이를 따릅니다.

### Agent: 독립적으로 실행되는 서브 프로세스

Agent는 `Task` 도구를 통해 생성되는 독립 실행 단위입니다. 메인 Claude가 복잡한 작업을 하위 작업으로 분할하고, 각각을 별도의 Agent에게 위임합니다.

```
메인 Claude: "전체 코드베이스 보안 분석"
  |
  +-- Agent 1: 인증 코드 분석
  +-- Agent 2: 입력 검증 분석
  +-- Agent 3: 의존성 보안 검사
  |
  v
결과 통합 및 보고서 생성
```

Agent는 **복잡한 작업의 격리된 수행**을 담당합니다. 대규모 분석이나 장시간 실행되는 작업을 메인 세션과 분리하여 처리합니다.

## 격리 수준: 왜 세 패턴의 경계가 다른가

세 패턴의 가장 근본적인 차이는 **격리 수준**입니다. 이 차이는 의도적인 설계 결정이며, 각 패턴이 해결하는 문제의 성격에서 비롯됩니다.

### 격리의 스펙트럼

```
완전 공유                                              완전 격리
    |                                                      |
    v                                                      v
+--------+            +--------+            +--------+
| Command|            |  Skill |            |  Agent |
+--------+            +--------+            +--------+
    |                     |                     |
메인 세션에           메인 세션에           별도 프로세스와
직접 주입             자동 포함             컨텍스트에서 실행
```

**Command**는 격리가 거의 없습니다. 프롬프트 텍스트가 메인 세션에 직접 주입되기 때문입니다. 이는 의도적입니다. Command의 목적이 "현재 대화의 연장"이므로, 격리는 오히려 기능을 방해합니다.

**Skill**은 부분적 격리를 제공합니다. 지침은 시스템 레벨에서 적용되지만, 결과는 메인 세션의 컨텍스트로 반환됩니다. 외부 도구를 호출하는 Skill의 경우, 도구 실행 자체는 별도 프로세스에서 이루어집니다.

**Agent**는 완전한 격리를 제공합니다. 별도의 프로세스와 컨텍스트에서 실행되며, 메인 세션과는 명확하게 정의된 인터페이스로만 통신합니다.

### 격리 수준이 다른 이유: 위험-이득 균형

이 차이는 **위험-이득 균형**에서 비롯됩니다.

| 패턴 | 위험 수준 | 이득 | 격리 필요성 |
|------|----------|------|------------|
| Command | 낮음 (텍스트 주입) | 현재 맥락 완전 활용 | 낮음 |
| Skill | 중간 (행동 수정) | 일관된 응답 품질 | 중간 |
| Agent | 높음 (자율 실행) | 복잡한 작업 처리 | 높음 |

Agent의 완전 격리가 필요한 이유는 세 가지입니다.

첫째, **토큰 경제성**입니다. Agent가 수만 토큰을 소비해도 메인 세션의 컨텍스트 윈도우는 영향받지 않습니다.

둘째, **실패 격리**입니다. Agent가 무한 루프에 빠지거나 잘못된 방향으로 진행해도, 메인 세션에서 간단히 중단할 수 있습니다.

셋째, **병렬 실행**입니다. 여러 Agent를 동시에 실행할 수 있으며, 서로 간섭하지 않습니다.

### 역사적 배경: 프로세스 격리의 교훈

이 설계는 운영체제와 브라우저의 역사에서 교훈을 얻었습니다.

1960년대 Multics에서 시작된 **프로세스 격리**는 하나의 프로그램 오류가 전체 시스템을 붕괴시키는 것을 방지하기 위해 도입되었습니다. 1990년대 Netscape의 NPAPI 플러그인은 격리 없이 브라우저 프로세스에서 직접 실행되었고, 하나의 플러그인 크래시가 전체 브라우저를 종료시켰습니다. Chrome은 이 교훈을 바탕으로 각 탭과 플러그인을 별도 프로세스로 실행하는 샌드박스 아키텍처를 도입했습니다.

Claude Code의 Agent 패턴은 이러한 역사적 교훈을 반영합니다. 복잡하고 위험할 수 있는 작업을 격리된 환경에서 실행하여, 실패해도 메인 세션이 안전하게 유지됩니다.

## 컨텍스트 관리: 세 패턴의 메모리 전략

격리 수준과 밀접하게 연결된 것이 **컨텍스트 관리 방식**입니다. 각 패턴은 LLM의 컨텍스트 윈도우를 다르게 활용합니다.

### 컨텍스트 흐름 다이어그램

```
┌─────────────────────────────────────────────────────────┐
│                   메인 세션 컨텍스트                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│  │ System   │  │ 대화     │  │ Tool     │              │
│  │ Prompt   │  │ 히스토리  │  │ 결과     │              │
│  └──────────┘  └──────────┘  └──────────┘              │
│       ^             ^             ^                     │
│       │             │             │                     │
│   ┌───┴───┐    ┌───┴───┐    ┌───┴───┐                 │
│   │ Skill │    │Command│    │ Skill │                 │
│   │ 주입  │    │ 주입  │    │ 결과  │                 │
│   └───────┘    └───────┘    └───────┘                 │
└─────────────────────────────────────────────────────────┘
                         │
                         │ Task 호출
                         v
┌─────────────────────────────────────────────────────────┐
│                   Agent 독립 컨텍스트                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│  │ 초기    │  │ 자체    │  │ 자체    │               │
│  │ 지시사항 │  │ 추론    │  │ 도구 사용│              │
│  └──────────┘  └──────────┘  └──────────┘              │
│                         │                              │
│                         v                              │
│                  ┌──────────┐                          │
│                  │ 결과 요약 │ ──────────────────────> 메인
│                  └──────────┘                          │
└─────────────────────────────────────────────────────────┘
```

### Command와 Skill: 공유 컨텍스트의 장점

Command와 Skill은 메인 컨텍스트를 공유합니다. 이 설계의 핵심 이점은 다음과 같습니다.

**암묵적 지식 활용**: 이전에 논의된 내용, 읽은 파일, 시도한 해결책을 자동으로 참조합니다. "아까 그 파일"이라고 말해도 이해합니다.

**점진적 개선**: 첫 번째 시도의 결과를 바탕으로 두 번째 시도를 개선합니다. 실패 원인을 기억하고 다른 접근법을 시도합니다.

**일관성**: 프로젝트 전체에서 동일한 코딩 스타일, 명명 규칙, 아키텍처 패턴을 유지합니다.

### Agent: 독립 컨텍스트의 필요성

Agent가 독립 컨텍스트를 가지는 이유는 LLM의 본질적 특성에서 비롯됩니다.

Transformer 아키텍처의 Self-Attention은 O(n^2) 복잡도를 가집니다. 컨텍스트가 길어질수록 계산 비용이 기하급수적으로 증가합니다. 또한 연구에 따르면 LLM은 컨텍스트의 시작과 끝에 있는 정보를 중간보다 더 잘 활용합니다(Lost in the Middle 현상).

Agent의 독립 컨텍스트는 이 문제를 해결합니다.

```
시나리오: 10개 파일 분석

[순차 처리 - 공유 컨텍스트]
파일 1 → 파일 2 → ... → 파일 10
컨텍스트 누적: 5K → 8K → 11K → ... → 35K 토큰
총 입력: ~200,000 토큰

[병렬 처리 - 독립 컨텍스트]
Agent 1(3K) | Agent 2(3K) | ... | Agent 10(3K)
결과 통합: 5K
총 입력: ~37,000 토큰
```

독립 컨텍스트를 사용하면 토큰 사용량이 크게 줄어들고, 병렬 처리로 전체 소요 시간도 단축됩니다.

### 토큰 효율성 비교

| 시나리오 | Command/Skill | Agent |
|----------|--------------|-------|
| 짧은 대화 (5회 이하) | 효율적 | 오버헤드 발생 |
| 긴 대화 (20회 이상) | 누적으로 비효율 | 격리로 효율적 |
| 순차 작업 | 빠름 | spawn 오버헤드 |
| 병렬 작업 | 불가능 | 매우 효율적 |

## 인터페이스 설계: 실행 방식의 차이

세 패턴은 **호출 방식**도 다릅니다. 이 차이 역시 의도적인 설계입니다.

### 명시적 vs 암시적 vs 프로그래밍적

```
사용자 제어 ←──────────────────────────→ 자동화
     |              |              |
     v              v              v
 Command         Agent          Skill

  /review      Task 도구로    CLAUDE.md
  /doctor      자동 생성      자동 적용
  /init
```

**Command**는 **명시적 호출**을 요구합니다. 사용자가 `/doctor`를 입력해야만 실행됩니다. 이는 파괴적이거나 비가역적인 작업을 안전하게 처리하기 위함입니다. `/clear`가 자동으로 실행되면 의도치 않게 대화가 초기화될 수 있습니다.

**Skill**은 **암시적 적용**입니다. CLAUDE.md에 정의된 규칙은 매 응답에 자동으로 반영됩니다. "TypeScript를 사용하세요"를 매번 말하지 않아도 됩니다.

**Agent**는 **프로그래밍적 호출**입니다. Claude가 작업 복잡도를 판단하여 필요할 때 Task 도구를 통해 Agent를 생성합니다. 사용자가 직접 Agent를 호출하지 않지만, 로그를 통해 확인할 수 있습니다.

### 왜 이런 인터페이스 차이가 필요한가

이 설계는 **자율성 스펙트럼**에서 적절한 위치를 선택한 결과입니다.

**Command의 명시성**: 예측 가능성이 핵심입니다. 동일한 명령은 항상 동일한 결과를 만들어야 합니다. 스크립트나 CI/CD에서 자동화할 때도 이 예측 가능성이 필요합니다.

**Skill의 암시성**: 인지 부하 감소가 핵심입니다. "설정하고 잊어버리기"가 가능해야 합니다. 팀 전체가 같은 규칙을 공유할 때 특히 유용합니다.

**Agent의 위임**: 처리 능력 극대화가 핵심입니다. 인간이 수동으로 하기 어려운 대규모 작업을 Claude가 자율적으로 분할하고 처리합니다.

### 역사적 유사 패턴

이 인터페이스 설계는 개발 도구의 역사에서 검증된 패턴들입니다.

**Vim의 Ex 명령** (`:w`, `:q`, `:s/foo/bar/g`): Claude Code의 슬래시 커맨드와 동일한 명시적 호출 패턴입니다. 학습 곡선이 있지만 일단 익숙해지면 극도로 효율적입니다.

**Shell 설정 파일** (`.bashrc`, `.zshrc`): CLAUDE.md의 계층적 로딩(전역 -> 프로젝트 -> 디렉토리)과 동일합니다. 암묵적 지식을 명시적 설정으로 표현합니다.

**Make/npm scripts**: Agent의 작업 분할과 유사합니다. 고수준 명령을 여러 하위 작업으로 분해하고 실행합니다.

## 트레이드오프: 언제 무엇을 선택할 것인가

세 패턴의 특성을 종합하여 선택 기준을 정리합니다.

### 패턴별 트레이드오프 요약

| 측면 | Command | Skill | Agent |
|------|---------|-------|-------|
| **격리 수준** | 없음 | 부분적 | 완전 |
| **컨텍스트** | 메인 공유 | 메인 공유 | 독립 |
| **호출 방식** | 명시적 | 암시적 | 프로그래밍적 |
| **최적 시나리오** | 메타 작업, 자동화 | 상시 적용 규칙 | 복잡한 분할 작업 |
| **토큰 패턴** | 일회성 주입 | 매 요청 포함 | 독립 세션 |
| **예측 가능성** | 높음 | 중간 | 낮음 |
| **유연성** | 낮음 | 중간 | 높음 |

### 선택 의사결정 플로우

```
작업이 메타 작업인가? (설정, 상태, 초기화)
├─ Yes → Command
│        예: /init, /doctor, /config
└─ No ↓

항상 적용되어야 하는 규칙/컨텍스트인가?
├─ Yes → Skill (CLAUDE.md)
│        예: 코딩 스타일, 프로젝트 구조, 금지 패턴
└─ No ↓

대규모/병렬/격리가 필요한 작업인가?
├─ Yes → Agent
│        예: 전체 코드베이스 분석, 다중 파일 리팩토링
└─ No → 일반 대화로 처리
```

### 빌드 시스템 비유

세 패턴을 모듈화 수준의 스펙트럼으로 이해할 수 있습니다.

| 패턴 | 비유 | Turborepo 유사 개념 |
|------|------|---------------------|
| Command | 인라인 코드 | `import { x } from './utils'` |
| Skill | 공유 라이브러리 | `import { x } from '@repo/utils'` |
| Agent | 별도 서비스 | API 호출로 통신 |

각 수준은 **결합도**와 **배포 독립성** 사이의 트레이드오프를 나타냅니다.

### 복합 사용 패턴

실제로는 세 패턴을 조합하여 사용하는 경우가 가장 효과적입니다.

```
1. Skill로 기본 규칙 설정
   └─ CLAUDE.md: "모든 함수에 JSDoc 작성"

2. Command로 세션 초기화
   └─ /memory: 현재 모듈 정보 로드

3. 복잡한 작업에 Agent 활용
   └─ "10개 파일 병렬 리팩토링"

4. 메인 세션에서 결과 검토
   └─ Agent 결과 통합 및 최종 조정
```

## 마무리하며

Claude Code의 Command, Skill, Agent는 단순히 "기능의 종류"가 아닙니다. 각 패턴은 **격리 수준**, **컨텍스트 관리**, **인터페이스 설계**라는 세 가지 설계 차원에서 서로 다른 선택을 한 결과입니다.

**Command**는 사용자에게 최대 제어권을 제공합니다. 명시적 호출, 메인 컨텍스트 공유, 예측 가능한 결과. "내가 정확히 무엇을 요청하는지 안다"는 상황에 적합합니다.

**Skill**은 최대 편의성을 제공합니다. 자동 적용, 일관된 행동 양식, 인지 부하 감소. "이 규칙은 항상 적용되어야 한다"는 상황에 적합합니다.

**Agent**는 최대 처리 능력을 제공합니다. 완전 격리, 독립 컨텍스트, 병렬 실행. "이 작업은 너무 크고 복잡하다"는 상황에 적합합니다.

이 세 패턴이 조화롭게 작동할 때, 개발자는 "내가 원하는 수준의 개입"을 선택할 수 있는 유연성을 얻습니다. 단순한 작업에서는 Command로 빠르게 처리하고, 프로젝트 규칙은 Skill로 자동화하며, 복잡한 분석은 Agent에게 위임합니다.

결국 이 설계의 본질은 **적절한 추상화 수준에서 적절한 제어권을 제공**하는 것입니다. Unix의 프로세스 격리, 브라우저의 샌드박스 아키텍처, 마이크로서비스의 서비스 분리와 같은 역사적 교훈이 AI 에이전트 시스템에도 그대로 적용됩니다. 문제의 복잡도와 위험 수준을 파악하고, 그에 맞는 패턴을 선택하는 것이 Claude Code를 효과적으로 활용하는 핵심입니다.

대부분의 팀은 새 라우팅 구조를 한 번에 갈아엎을 수 없습니다.
현실적인 목표는 "완벽한 전환"이 아니라 "사고 없는 점진 전환"입니다.

이 글은 v6/Remix 기반 앱을 React Router v7 + RSC 방향으로 이동할 때 필요한 순서를 정리합니다.

---

## 1단계: 경계 인벤토리 먼저 만들기

코드 수정 전에 아래를 문서화해야 합니다.

- 라우트 트리와 소유팀
- loader/action 사용 지점
- 에러 경계/로딩 경계
- 전환 중 문제 발생 구간

이 단계 없이 전환을 시작하면, 기술 이슈보다 소유권 충돌이 먼저 터집니다.

---

## 2단계: 데이터 규칙부터 통일

RSC 도입 이전에 먼저 합의할 것:
- 어떤 데이터는 loader/action에 유지할지
- 어떤 데이터는 서버 컴포넌트 경로로 이동할지
- 재검증 트리거 표준

규칙이 없는 상태에서 전환하면 동일 리소스를 여러 경로에서 조회하게 됩니다.

---

## 3단계: 라우트 단위 점진 전환

권장 순서:
1. 트래픽 낮은 라우트
2. 읽기 중심 라우트
3. 뮤테이션 많은 라우트

이유:
- 리스크를 작게 시작
- 관측 가능성 확보 후 확장
- 팀 학습 곡선 반영

---

## 4단계: 롤백 설계 포함 배포

마이그레이션 배포는 기능 릴리스가 아니라 운영 이벤트입니다.

필수 항목:
- feature flag
- 롤백 시나리오
- 전환 전후 지표 비교 대시보드
- 장애 대응 채널/책임자

---

## 마이그레이션 체크리스트

- [ ] 경계 인벤토리 문서가 최신인가
- [ ] 데이터 책임 분리 규칙이 합의됐는가
- [ ] 라우트 단위 전환 순서가 정의됐는가
- [ ] 롤백 플랜이 테스트됐는가
- [ ] 전환 품질 지표(LCP/INP/에러율)를 추적 중인가

---

## 마무리

v7 + RSC 전환의 핵심은 기술 교체가 아니라 운영 전환입니다.
작게 시작하고, 경계를 명확히 하고, 측정 가능한 방식으로 확장해야 실패 비용을 줄일 수 있습니다.

다음 글에서는 마지막으로 MFE 환경에서 Router + RSC를 어떻게 운영 모델로 정착시킬지 다룹니다.

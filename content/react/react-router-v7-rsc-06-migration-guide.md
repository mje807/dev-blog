## 한눈에 보기

v6/Remix에서 v7 + RSC로의 전환은 “라우터 API 교체”가 아니라 **렌더링 경계, 데이터 책임, 배포 통제 모델**을 다시 설계하는 작업입니다. 특히 운영 중인 서비스에서는 기존 loader/action 기반 데이터 흐름과 RSC 기반 서버 렌더링 흐름이 일정 기간 공존하므로, 경계 정의 없이 전환을 시작하면 중복 조회·캐시 불일치·관측 공백이 빠르게 발생합니다.

React Router 7 + RSC의 실무 도입에서 검증 가능한 핵심 사실은 세 가지입니다.
1) RSC는 서버에서 실행되며, Client Component 경계가 명시되지 않으면 브라우저 상호작용 훅을 직접 사용할 수 없습니다.
2) 기존 v6/Remix loader/action은 내비게이션·뮤테이션 중심의 명확한 생명주기를 제공하며, 전환기에는 이 모델을 “즉시 폐기”하는 것이 아니라 목적별로 분리 운영해야 합니다.
3) 전환 성공은 “몇 개 라우트를 옮겼는가”보다 **에러율·Core Web Vitals·롤백 소요 시간**이 안정적으로 유지되는가로 판단해야 합니다.

따라서 안전한 전환 순서는 다음으로 수렴합니다.
- 라우트/데이터/오류 경계 인벤토리 고정
- loader/action 유지·이관 규칙 명문화
- 저위험 라우트부터 점진 전환
- 기능 플래그와 비교 대시보드를 포함한 운영 배포
이 순서를 지키면 기술 실험이 운영 리스크로 확대되는 것을 줄일 수 있습니다.

## 들어가며

React Router 7과 RSC를 함께 도입하려는 팀이 가장 자주 부딪히는 문제는 기술 난이도 자체보다 **문맥 전환 비용**입니다. v6/Remix 체계에서는 라우트 모듈이 데이터 입출력의 중심이었습니다. loader/action, 에러 경계, pending UI의 위치가 라우트 구조에 정렬되어 있었기 때문입니다. 반면 RSC를 도입하면 데이터 계산과 UI 구성 일부가 서버 컴포넌트 트리로 이동하면서, 책임 경계가 “URL 라우트”와 “서버 실행 경계”라는 두 축으로 분리됩니다.

이 변화는 추상 개념이 아니라 운영 지표에 직접 반영됩니다.
- 동일 리소스를 loader와 RSC에서 이중 조회하면 서버 부하와 응답 지연이 늘어날 수 있습니다.
- 캐시 무효화 트리거가 분산되면 사용자 세션마다 데이터 일관성이 깨질 수 있습니다.
- 장애 시 어느 경계에서 실패했는지 추적이 늦어지면 MTTR(평균 복구 시간)이 증가합니다.

또한 “RSC를 쓰면 성능이 자동 개선된다”는 기대는 사실과 다릅니다. RSC는 JS 전달량을 줄일 수 있는 구조적 이점이 있지만, 실제 사용자 지표는 **경계 설계, 데이터 왕복 횟수, 스트리밍 전략, 캐시 정책**에 의해 결정됩니다. 즉, RSC는 성능 개선의 필요조건일 수 있으나 충분조건은 아닙니다.

이 글은 v6/Remix 기반 서비스가 v7 + RSC로 이동할 때 반드시 확인해야 할 항목을 세 층위로 정리합니다.
1) 설계 방향과 의도: 왜 이 구조를 택하는가
2) 실제 구현과 런타임 동작: 요청-응답-하이드레이션이 어떻게 흘러가는가
3) 어떤 문제를 어떻게 해결하는가: 리스크를 어떤 절차로 국소화하는가
목표는 기능 시연이 아니라, 전환 이후에도 서비스와 팀이 더 안정적으로 운영되는 상태를 만드는 것입니다.

## 설계 방향과 의도

### 1) “전체 교체”가 아니라 “책임 분리”를 목표로 둡니다

점진 마이그레이션의 설계 목표는 최신 문법 채택이 아닙니다. 핵심은 기존 시스템의 강점(loader/action의 명확한 트랜잭션 모델)을 유지하면서, RSC가 유리한 구간(읽기 중심, 서버 연산 중심, 클라이언트 JS 절감 필요 구간)에 선택적으로 적용하는 것입니다.

- **유지 대상(초기):** 인증 상태 전환, 결제/주문 제출, 낙관적 UI가 필수인 상호작용 라우트
- **이관 대상(초기):** 읽기 중심 대시보드, 서버 조합 비용이 큰 상세 페이지, SEO 중요 콘텐츠 라우트

이 기준은 기술 취향이 아니라 장애 반경과 복구 난이도에 기반한 운영 기준입니다.

### 2) 경계 우선 설계: URL 경계와 실행 경계를 분리합니다

v6/Remix에서는 URL 라우트 경계가 곧 데이터 책임 경계인 경우가 많았습니다. v7 + RSC에서는 다음을 분리해 정의해야 합니다.

- **Routing Boundary:** URL, nested route, 에러/로딩 fallback 구조
- **Execution Boundary:** Server Component 실행 구간, Client Component 진입 지점, 서버 액션(또는 mutation 경로) 위치
- **Ownership Boundary:** 팀 소유권, 배포 권한, on-call 책임

세 경계를 문서로 고정하면 PR 리뷰·장애 대응·롤백 판단이 빨라집니다. 반대로 문서가 없으면 “이 데이터는 어디서 책임지는가”가 매번 논쟁이 됩니다.

### 3) 데이터 책임을 “조회/변경/재검증”으로 명문화합니다

전환기 문제의 대부분은 기술 스택이 아니라 데이터 규칙 부재에서 발생합니다. 최소한 다음 규칙이 있어야 합니다.

- **Read Path 규칙:** 리소스별 단일 우선 조회 경로 지정(loader 우선 또는 RSC 우선)
- **Write Path 규칙:** 뮤테이션 완료 후 어떤 경계에서 revalidation/re-fetch를 수행할지 지정
- **Consistency 규칙:** 사용자에게 허용 가능한 stale window(예: 0초, 30초, 이벤트 기반)를 리소스별로 정의

핵심은 “어디서나 읽을 수 있다”가 아니라 “항상 같은 방식으로 읽는다”입니다.

### 4) 배포를 운영 이벤트로 설계합니다

점진 전환의 배포 단위는 코드 묶음이 아니라 **통제 가능한 실험**이어야 합니다. 반드시 포함해야 할 항목은 다음입니다.

- 라우트 단위 feature flag
- 전환군/비전환군 비교 대시보드(LCP, INP, 에러율, TTFB, 서버 5xx)
- 즉시 롤백 절차(권한자, 커맨드/플래그, 커뮤니케이션 채널)
- 변경 이력과 실험 결과 기록 템플릿

이 구조가 있으면 “문제 발생 시 멈출 수 있는 전환”이 되고, 없으면 “끝까지 밀어야 하는 전환”이 됩니다.

### 5) 성공 지표를 완료율이 아니라 안정성으로 둡니다

실무에서 유효한 KPI는 다음과 같습니다.

- 전환 라우트의 에러율이 비전환 라우트 대비 유의하게 증가하지 않는가
- Core Web Vitals 분포(P75)가 악화되지 않는가
- 장애 탐지→롤백 완료 시간(SLO)이 목표 범위 내인가
- 팀별 변경 리드타임이 전환 전 대비 유지 또는 개선되는가

즉, “70% 전환 완료”는 결과 지표가 아니라 진행 지표입니다. 운영 관점의 성공은 안정성 지표가 유지될 때만 성립합니다.

## 실제 구현과 런타임 동작

### 1) 요청 흐름의 변화: 단일 라우트 모델에서 이중 경계 모델로

기존 v6/Remix 요청 흐름은 대체로 다음과 같았습니다.

1. URL 매칭
2. 해당 라우트의 loader 실행
3. 데이터와 함께 렌더링/하이드레이션
4. 사용자 액션 발생 시 action 실행 후 revalidation

v7 + RSC 전환 시에는 다음 흐름이 공존합니다.

1. URL 매칭(라우터)
2. Server Component 트리 평가(RSC payload 생성)
3. 필요 시 Client Component 번들 로딩 및 hydration
4. 사용자 상호작용 구간은 client boundary에서 처리
5. 변경 이벤트 발생 시 지정된 mutation 경로에서 데이터 반영 및 재검증

핵심 변화는 “데이터 조회 타이밍”과 “실행 위치”가 분산된다는 점입니다.

### 2) 서버/클라이언트 경계의 런타임 제약

RSC 구간은 서버에서 실행되므로 브라우저 전용 API(window, localStorage)나 클라이언트 훅(useState, useEffect 직접 사용)은 경계 밖입니다. 상호작용이 필요한 부분은 Client Component로 분리해야 하며, 이 경계 설계가 과도하면 번들 이점이 줄고, 부족하면 기능 제약이 늘어납니다.

즉, 설계 시점에 다음 판단이 필요합니다.

- 이 UI 조각은 서버에서 계산해 HTML/stream으로 제공해도 충분한가
- 즉시 상호작용이 필요한가, 아니면 지연 하이드레이션이 가능한가
- 상태 소유권을 서버(데이터 정합성)와 클라이언트(즉시 반응성) 중 어디에 둘 것인가

### 3) 스트리밍과 Suspense의 운영적 의미

RSC 환경에서 스트리밍은 초기 응답을 빠르게 전달할 수 있는 수단이지만, 경계를 잘못 잡으면 사용자 체감이 나빠질 수 있습니다.

- 장점: 상단 핵심 콘텐츠를 먼저 노출해 “첫 유의미 렌더”를 앞당길 수 있음
- 리스크: fallback 설계가 부정확하면 레이아웃 점프·인지 부조화 증가
- 운영 포인트: skeleton/fallback 컴포넌트도 실제 사용자 흐름 기준으로 설계해야 함

즉, 스트리밍은 단순 성능 기술이 아니라 UX/관측 설계와 결합되어야 효과가 납니다.

### 4) 데이터 중복 조회를 막는 런타임 규칙

전환기에 가장 자주 발생하는 패턴은 동일 리소스를 loader와 RSC에서 모두 호출하는 경우입니다. 이를 막기 위해 라우트별 “single source of fetch truth”를 둬야 합니다.

아래는 개념 예시입니다(운영 코드 축약).

```ts
// route-policy.ts (개념 예시)
export const routeDataPolicy = {
"/dashboard": { read: "rsc", write: "action", revalidate: "event" },
"/orders/:id": { read: "loader", write: "action", revalidate: "immediate" },
} as const;
```

이런 정책 테이블을 기준으로 리뷰하면, 코드 스타일이 아니라 데이터 책임 위반 여부를 기계적으로 확인할 수 있습니다.

### 5) 관측(Observability) 연결: 로그 스키마를 통일합니다

전환 라우트는 최소 다음 태그를 로그/트레이스에 남겨야 원인 추적이 가능합니다.

- route_id
- render_mode(loader|rsc|mixed)
- cache_status(hit|miss|revalidated)
- boundary(client|server)
- experiment_flag(on|off)

운영에서 중요한 점은 “에러가 났다”가 아니라 “어느 경계 조합에서 났다”를 즉시 분리하는 것입니다. 이 스키마 없이는 전환군과 비전환군 비교가 불가능합니다.

### 6) 롤백의 구현 단위를 코드가 아니라 플래그로 둡니다

실패 시 git revert만으로 복구하려 하면 배포 지연이 커집니다. 라우트 단위 플래그를 두면 실시간 트래픽에서 전환 경로를 우회할 수 있습니다.

```ts
// pseudo-config
if (flags.rsc_dashboard) {
return renderRSC();
}
return renderLegacyLoaderPath();
```

이 방식의 장점은 복구 속도입니다. 코드 재배포보다 플래그 전환이 빠르며, 장애 시간과 사용자 영향 범위를 줄일 수 있습니다.

## 어떤 문제를 어떻게 해결하는가

### 문제 1) 데이터 일관성 붕괴

**증상:** 같은 페이지에서 새로고침/내비게이션 시 데이터가 다르게 보임
**원인:** loader 경로와 RSC 경로의 재검증 규칙 불일치
**해결:** 리소스별 단일 read path 지정 + write 이후 revalidation 트리거 단일화
**검증:** 동일 사용자 시나리오에서 데이터 버전 해시 일치율 측정

### 문제 2) 성능 개선 실패 또는 역행

**증상:** RSC 도입 후에도 LCP/INP 개선이 없거나 악화
**원인:** client boundary 과다, fallback 과설계, 서버 왕복 증가
**해결:** 상호작용 임계 경계 재조정, 스트리밍 우선순위 재배치, 고비용 호출 병합
**검증:** 전환군/대조군 P75 지표 비교 + 주요 라우트 synthetic test

### 문제 3) 장애 시 원인 추적 지연

**증상:** 에러는 보이지만 loader/RSC 어느 경계 문제인지 불명확
**원인:** 로그 태그 표준 부재, 실험군 분리 미흡
**해결:** render_mode·boundary·flag 태그 강제, 대시보드 분할
**검증:** 장애 리허설에서 탐지→원인분리까지 목표 시간 충족 여부

### 문제 4) 팀 간 소유권 충돌

**증상:** PR 충돌·리뷰 지연·배포 책임 공백
**원인:** 라우트 소유권과 실행 경계 소유권 미분리
**해결:** route ownership map + on-call 매트릭스 + 변경 승인 규칙
**검증:** 전환 웨이브별 리드타임/리뷰 회수/롤백 책임자 명확성 점검

### 문제 5) “완료율 중심” 의사결정

**증상:** 지표 악화에도 일정 때문에 전환 강행
**원인:** KPI가 라우트 이전 개수 중심
**해결:** 안정성 게이트(에러율, CWV, 롤백 가능성) 통과 시에만 웨이브 진행
**검증:** 각 웨이브 종료 시 go/no-go 체크리스트 기록

### 실행 프레임: 4단계 웨이브 운영

1. **Baseline 고정**
- 전환 전 2~4주 지표 베이스라인 확정
- 핵심 사용자 여정별 실패율/응답시간 기준값 정의

2. **Pilot 라우트 전환**
- 저위험·읽기 중심 라우트 1~2개
- 플래그 기반 배포, 즉시 롤백 검증 포함

3. **동일 패턴 확장**
- 파일럿에서 검증된 경계 패턴만 재사용
- 신규 패턴 도입은 별도 실험으로 분리

4. **고위험 라우트 전환**
- 인증/결제/핵심 funnel은 마지막 단계
- 전환 전 장애 리허설과 커뮤니케이션 플랜 필수

이 프레임의 효과는 단순합니다. 실패를 “대형 사고”가 아니라 “작은 편차”로 흡수할 수 있습니다.

---

## 마무리하며

v6/Remix에서 v7 + RSC로의 점진 마이그레이션은 기술 데모 프로젝트가 아닙니다. 운영 중인 제품에서 실제로 필요한 것은 최신 기능의 나열이 아니라, **경계를 분리하고 책임을 고정해 리스크를 통제하는 능력**입니다.

팩트 기준으로 정리하면 결론은 명확합니다.
- RSC는 서버 실행 경계를 제공하지만, 경계 설계가 없으면 이점이 사라집니다.
- loader/action은 전환기에도 강력한 안정 장치이며, 목적별 공존이 현실적입니다.
- 전환 성공은 코드 이전율이 아니라 에러율·사용자 지표·복구 시간 안정성으로 증명됩니다.

따라서 실전 전략은 “빨리 옮기기”가 아니라 “작게 검증하고 안전하게 확장하기”입니다. 이 원칙을 유지하면 React Router 7 + RSC 전환은 단순 버전 업그레이드를 넘어, 팀의 배포 신뢰도와 운영 성숙도를 함께 끌어올리는 계기가 됩니다.

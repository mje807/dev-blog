## 한눈에 보기

React Router 7 + RSC + MFE 조합은 흔히 “최신 기술 스택”으로 소개되지만, 실무에서는 기술이 아니라 **운영 모델의 성숙도**가 성패를 좌우합니다.
왜냐하면 이 조합의 핵심은 화면 렌더링이 아니라 **경계(boundary)를 어떻게 정의하고, 누가 책임지고, 어떤 지표로 개선할지**에 있기 때문입니다.

이 글의 핵심 요지는 다음 다섯 문장으로 요약할 수 있습니다.

- **RSC는 성능 기능이기 이전에 책임 분리 기법**입니다. “무엇을 서버에서 읽고, 무엇을 클라이언트에서 상호작용할 것인가”를 명확히 만드는 도구입니다.
- **React Router 7은 URL 이동기라기보다 운영 제어면**입니다. 라우트는 단순한 경로가 아니라 팀 간 계약의 실행 단위입니다.
- **MFE는 독립 배포 선언으로 끝나지 않습니다.** 상호의존성을 관리하는 절차와 합의가 없으면 독립성은 금방 환상으로 바뀝니다.
- **Shell과 Fragment의 권한 경계가 흐려지는 순간**, 장애 원인 파악 시간과 복구 시간이 급격히 늘어납니다.
- **운영 성공의 KPI는 기능 속도 단일 지표가 아닙니다.** 변경 실패율(Change Failure Rate), 복구 시간(MTTR), 재발률까지 함께 봐야 합니다.

즉, “어떻게 구현할까?”보다 먼저 “왜 이 구조를 채택했고, 누가 무엇을 책임지며, 문제 발생 시 어떤 루프로 학습할 것인가?”를 합의해야 합니다.
이 합의가 없으면 React Router 7과 RSC는 생산성 도구가 아니라 복잡도 증폭기로 작동합니다.

## 들어가며

많은 팀이 React Router 7과 RSC를 이야기할 때 성능 그래프부터 꺼냅니다. 첫 응답 시간 개선, 번들 감소, hydration 부담 완화 같은 수치는 분명 중요합니다. 그런데 MFE 환경에서는 이 수치들이 **원인 변수**가 아니라 **결과 변수**인 경우가 많습니다.

왜 이런 현상이 생길까요?

핵심은 MFE가 원래부터 “경계가 많은 구조”이기 때문입니다.
팀 경계, 코드 경계, 배포 경계, 도메인 경계가 이미 존재하고, 여기에 RSC를 도입하면 서버/클라이언트 경계가 추가됩니다. 경계가 늘어나는 것 자체는 문제 아닙니다. 문제는 경계가 늘었는데 **운영 규칙이 그대로일 때**입니다.

예를 들어 이런 상황이 자주 벌어집니다.

- 도메인 팀 A가 특정 라우트의 읽기 로직을 RSC로 옮겼는데, 팀 B의 Fragment는 기존 client fetch 흐름을 유지합니다.
- Shell은 인증/권한을 전역으로 통제하지만, Fragment는 로딩과 오류 처리를 제각각 구현합니다.
- 장애가 발생하면 로그는 많지만 “누가 최종 판단자(owner)였는지”가 남아 있지 않습니다.

이때 현상은 다양해 보여도 근본 원인은 같습니다.
**기술 부채가 아니라 운영 부채**입니다.

운영 부채가 무서운 이유는 코드 리뷰에서 잘 드러나지 않고, 장애 시점에만 폭발한다는 점입니다. 평소에는 “유연한 자율성”처럼 보이지만, 사건이 터지면 “책임 공백”으로 바뀝니다. 그래서 React Router 7 + RSC + MFE를 도입할 때는 구현보다 먼저 운영 언어를 정리해야 합니다.

운영 언어란 거창한 문서가 아닙니다. 다음 네 질문에 팀이 같은 답을 갖는 상태입니다.

1. **이 경계는 누가 소유하는가?**
2. **이 경계는 어떤 계약으로 보호되는가?**
3. **계약 위반이 발생했을 때 누가 어떤 순서로 판단하는가?**
4. **판단의 근거는 어떤 로그와 지표로 남는가?**

React Router 7이 중요한 이유도 여기에 있습니다.
라우트는 URL 매핑 이상의 의미를 갖습니다. 어느 팀이 어떤 사용자 여정을 소유하는지, 에러를 어디서 흡수하는지, revalidation이 어떤 원인으로 발생했는지, fallback의 최소 품질을 누가 보장하는지까지 라우팅 경계에 연결됩니다.

RSC도 마찬가지입니다.
“서버에서 읽고 클라이언트에서 상호작용한다”는 한 줄 설명은 쉽지만, 실무에서는 그 과정이 곧 **책임의 왕복 경로**입니다. 읽기 실패는 누구 책임인지, 쓰기 실패 후 재검증은 어디까지 전파되는지, 부분 장애에서 사용자에게 어떤 신뢰 신호를 줄지까지 설계해야 합니다.

결국 이 조합의 본질은 하나입니다.
**경계를 기술로 만든 뒤, 그 경계를 운영으로 지키는 것**입니다.

## 트레이드오프

아래는 React Router 7 + RSC + MFE 환경에서 반복적으로 등장하는 선택지들입니다. 중요한 것은 “어느 쪽이 정답인가”가 아니라, **왜 이 선택이 우리 조직의 비용 구조를 줄이는가**를 설명할 수 있는지입니다.

### 1) Shell 중심 통제 vs Fragment 중심 자율성

가장 먼저 부딪히는 질문은 권한 배분입니다.

- Shell 통제를 강화하면 전역 UX와 보안 정책은 안정됩니다.
- Fragment 자율성을 강화하면 도메인 실험 속도는 빨라집니다.

둘 다 맞는 말입니다. 문제는 둘 중 하나를 절대화할 때입니다.

왜 절대화가 위험할까요?
통제 일변도는 중앙 병목을 만들고, 자율 일변도는 사용자 경험의 분열을 만듭니다. 결국 사용자는 “하나의 제품”을 기대하는데, 내부적으로는 “서로 다른 서비스 묶음”처럼 느끼게 됩니다.

그래서 실무에서는 권한을 이분법으로 나누기보다 **계층화**하는 편이 안정적입니다.

- **Shell 고정 영역(강제)**
- 전역 URL 규약
- 인증/권한 게이트
- 공통 에러 등급 체계
- 관측성 이벤트 최소 스키마
- **Fragment 자율 영역(선택)**
- 도메인 내부 내비게이션 경험
- 세부 fallback 문구/표현
- 도메인 특화 캐시/재검증 튜닝
- 실험성 인터랙션 패턴

핵심은 문서의 두께가 아니라 판별 가능성입니다. PR을 보는 순간 “이 변경은 Shell 승인 대상인지, Fragment 자율인지”가 즉시 판단돼야 합니다. 이 판별성이 없으면 리뷰는 토론이 아니라 협상전이 됩니다.

---

### 2) 데이터 접근 자유 vs 데이터 소유권 명시

RSC 도입 초기에 데이터 접근을 자유롭게 열어두면 속도가 빨라 보입니다.
문제는 규모가 커질수록 “누가 정합성을 책임지는가”가 사라진다는 점입니다.

왜 이것이 치명적일까요?
장애는 보통 쓰기 자체보다 **쓰기 이후의 상태 불일치**에서 터지기 때문입니다. 특히 MFE에서는 여러 Fragment가 같은 리소스를 다르게 해석하고 재검증 타이밍이 엇갈리면, 사용자는 같은 데이터라도 페이지마다 다른 진실을 보게 됩니다.

그래서 최소한 다음 4개 owner를 명시하는 것이 좋습니다.

- **Read owner**: 표준 읽기 경로는 어디인가(RSC/loader 등)
- **Write owner**: 쓰기 검증과 제약 조건의 최종 책임자는 누구인가
- **Revalidation owner**: 어떤 이벤트가 어디까지 재검증을 트리거하는가
- **Fallback owner**: 실패 시 사용자에게 어떤 최소 경험을 보장하는가

이 규칙은 통제를 위한 통제가 아닙니다.
장애 상황에서 선택지를 줄여 복구를 빠르게 하기 위한 장치입니다.

---

### 3) 표준 최소화 vs 품질 분산

“표준이 적을수록 빠르다”는 말은 단기적으로 맞습니다.
하지만 팀 수가 늘어나면 표준의 부재는 곧 비교 불가능성과 운영 비용 상승으로 이어집니다.

왜냐하면 MFE의 본질은 분산인데, 분산 시스템에서 공통 언어가 없으면 실패를 학습으로 전환할 수 없기 때문입니다.

React Router 7 + RSC 조합에서 특히 손실이 큰 최소 표준은 다음과 같습니다.

- route naming 규칙
- boundary 입력/출력/실패 시나리오 인터페이스
- 운영 로그 필드 스키마
- 전환 성능 측정 규격(구간 정의)
- 롤백 플레이북 템플릿

여기서 오해하면 안 되는 점이 있습니다.
표준은 창의성을 억압하려는 문서가 아니라 **복구 시간을 줄이는 보험**입니다.
팀이 이 사실에 동의하면 표준은 강제가 아니라 자산이 됩니다.

---

### 4) 일괄 대전환 vs RFC 기반 점진 진화

대규모 전환에서 흔한 실패는 “이번에 다 바꾸자”는 접근입니다.
기술적으로는 그럴듯하지만, 조직은 설계 문서처럼 작동하지 않습니다.

왜 점진 진화가 더 현실적일까요?
운영은 코드보다 습관의 영향을 더 크게 받기 때문입니다. 실제 트래픽, 온콜 경험, 팀 간 커뮤니케이션 패턴을 거치면서만 규칙이 살아남습니다.

실무적으로는 다음 루프가 가장 재현성이 높습니다.

1. 경계 변경 제안(RFC)
2. 소유 팀 합의
3. 제한 트래픽 실험
4. 운영 지표 검증
5. 채택/폐기 결정 및 표준 반영

이 루프의 장점은 기술 리스크보다 사회적 리스크를 줄인다는 데 있습니다.
사람들은 지시보다 검증 가능한 가설에 더 잘 협력합니다.

---

### 5) 기술 로그 중심 vs 운영 로그 중심

대부분의 팀은 “로그는 충분하다”고 생각합니다.
그런데 사고 회고에서 “그래서 누가 무엇을, 언제, 왜 결정했는가”가 남지 않는다면 그 로그는 운영 로그가 아닙니다.

왜 운영 로그가 따로 필요할까요?
복구의 본질은 버그 찾기가 아니라 **의사결정 복원**이기 때문입니다. 과거 판단의 맥락이 없으면 같은 장애가 다른 형태로 반복됩니다.

최소한 다음 필드는 통일하는 편이 좋습니다.

- routeId
- fragmentId
- ownerTeam
- sourcePath(RSC/loader/action)
- boundaryId
- revalidationReason
- userImpactScope

아래 코드는 개념 예시입니다. 중요한 것은 구현 방식이 아니라 필드 합의입니다.

```ts
type OpsEvent = {
routeId: string;
fragmentId: string;
ownerTeam: string;
sourcePath: "rsc" | "loader" | "action";
boundaryId: string;
revalidationReason?: string;
userImpactScope: "single" | "segment" | "global";
ts: string;
};
```

### 6) 코드 경계와 팀 경계의 불일치

아키텍처 다이어그램이 아름다워도 팀 구조와 안 맞으면 운영은 무너집니다.

예를 들어 라우트는 도메인 단위로 분리했는데 배포 승인권은 중앙 팀에만 있으면, 실질적으로는 모놀리식 운영과 크게 다르지 않습니다. 반대로 배포는 분산했는데 장애 대응 책임자가 불명확하면 롤백 판단이 지연됩니다.

왜 이 불일치가 반복될까요?
기술 설계와 조직 설계를 분리해서 논의하기 때문입니다.

실무에서 유효한 정렬 원칙은 단순합니다.

- **소유권 경계 = 라우트/프래그먼트 경계**
- **릴리스 권한 = 운영 책임**
- **의존성 지도 = 명시적 관리 대상**

정렬이 되면 기술 모듈화가 운영 독립성으로 이어집니다. 정렬이 안 되면 코드만 분리되고 의사결정은 중앙집중으로 회귀합니다.

### 7) 실패를 보고서로 끝내지 않고 규칙으로 환원하기

실패를 회고 문서로만 남기면 다음 릴리스에서 반복됩니다.
운영 성숙도는 “장애가 없음”이 아니라 “장애 학습이 규칙으로 전환됨”입니다.

대표적인 반복 패턴은 다음과 같습니다.

- **패턴 A: Shell 정책 독점**
- 증상: 도메인 팀 대기열 증가, 릴리스 지연
- 환원 규칙: Shell은 정책 프레임만 소유하고 도메인 UX 판단은 위임합니다.
- **패턴 B: Fragment 표준 무시**
- 증상: 사용자 경험 단절, 지표 비교 불가
- 환원 규칙: 공통 스키마 위반을 코드 취향 문제가 아닌 운영 리스크로 처리합니다.
- **패턴 C: 문서 없는 확장**
- 증상: 장애 시 책임 공백, 복구 지연
- 환원 규칙: 경계 변경은 PR 승인과 별개로 RFC 승인 단계를 둡니다.

여기서 중요한 것은 완벽한 예방이 아닙니다.
같은 실수를 두 번 반복하지 않는 학습 체계입니다.

---

### 8) “왜 React Router 7 + RSC인가”를 기능 목록으로 축소하지 않기

아키텍처는 기능표가 아닙니다. 조직이 지키는 의도입니다.
그래서 다음 문장을 팀의 공통 언어로 유지해야 합니다.

- React Router 7의 목적은 페이지 이동 구현이 아니라 **경계 선언의 일관화**입니다.
- RSC의 목적은 SSR 성능 튜닝이 아니라 **읽기 책임의 명료화**입니다.
- MFE의 목적은 독립 배포 그 자체가 아니라 **독립성과 전체 품질의 동시 확보**입니다.

왜 이 문장이 중요할까요?
목적이 흐려지면 각 팀은 로컬 최적화로 흩어집니다.
결과적으로 전체 시스템은 기능은 늘어나지만 운영 취약성이 커집니다.

---

### 9) 운영 다이어그램을 장식이 아닌 실행 계약으로 사용하기

다이어그램은 발표 자료가 아니라 행동 규칙이어야 합니다.
특히 Platform 팀의 역할을 “구현 대행”으로 오해하면 안 됩니다.

Platform 팀은 코드를 대신 만드는 조직이 아니라, **계약의 일관성을 유지하는 조직**입니다.
도메인 팀은 가치를 만들고, 플랫폼 팀은 그 가치들이 충돌 없이 함께 작동하도록 경계 규칙을 보증합니다.

이 역할이 선명해질수록 조직 확장성은 올라갑니다.
반대로 역할이 섞이면 “모든 중요한 결정이 중앙으로 모이는 느린 조직”이 됩니다.

---

### 10) 체크리스트를 배포 관문이 아니라 정렬 대화 도구로 쓰기

체크리스트는 통과/실패를 가르는 문서가 아니라, 팀이 같은 위험을 보는지 확인하는 질문지여야 합니다.

- [ ] Shell/Fragment 책임 계약이 문서화되어 있는가
- [ ] 리소스 단위 소유권(읽기/쓰기/재검증/복구)이 명시되어 있는가
- [ ] RFC 루프가 실제 트래픽 실험과 연결되어 있는가
- [ ] 운영 로그 필드가 의사결정 재현에 충분한가
- [ ] 팀 경계와 라우트 경계가 정렬되어 있는가
- [ ] 롤백 플레이북을 실제로 리허설했는가

왜 리허설이 중요할까요?
장애 때는 문서를 읽는 시간이 없습니다. 몸에 익은 절차만 작동합니다.

---

## 마무리하며

React Router 7 + RSC + MFE를 잘 운영하는 팀은 대개 “가장 똑똑한 팀”이 아닙니다.
대신 경계를 명확히 설계하고, 소유권을 문서로 고정하고, 실패를 학습 루프로 환원하는 팀입니다.

이 조합의 진짜 난이도는 구현이 아니라 운영이라는 말을 다시 강조하고 싶습니다.

- **RSC는 렌더링 기법이면서 동시에 책임 배치 기법**입니다.
- **React Router 7은 경로 시스템이면서 동시에 조직 경계의 실행 계층**입니다.
- **MFE는 배포 전략이면서 동시에 상호의존성 통제 전략**입니다.

셋이 정렬되면 팀이 커져도 품질이 유지됩니다.
하나라도 빠지면 초기 속도는 높아 보여도 시간이 갈수록 통합 비용과 장애 비용이 누적됩니다.

결국 장기적으로 이기는 방식은 화려한 구조가 아니라 단단한 운영 모델입니다.
구현은 출발점이고, 운영이 완성도입니다.
React Router 7 + RSC는 기술 선택지가 아니라 팀 간 약속이며, 그 약속을 지키는 방식이 제품의 미래를 결정합니다.

React Router 7 + RSC + MFE를 지속 가능한 자산으로 만들고 싶다면, 기술 도입과 동시에 운영 언어를 먼저 합의하시길 권합니다.

## 한눈에 보기

React Router 7과 RSC를 함께 도입한 팀이 가장 자주 겪는 착시는 “기능은 최신인데 체감 안정성은 왜 그대로인가”라는 질문입니다. 이 질문의 핵심은 프레임워크 성능이 아니라 경계 설계의 단위에 있습니다. 같은 지연이라도 사용자가 맥락을 유지한 채 기다릴 수 있으면 서비스는 안정적으로 느껴지고, 같은 오류라도 복구 경로가 명확하면 서비스는 통제 가능하다고 느껴집니다. 반대로 Pending과 Error가 같은 시각 신호로 섞여 보이면, 기술적으로는 전혀 다른 상태를 사용자 입장에서는 동일한 고장으로 해석하게 됩니다.

RSC의 스트리밍 모델은 원래 “부분 성공”을 전제로 합니다. 일부 세그먼트는 먼저 도착하고, 일부는 늦고, 일부는 실패할 수 있습니다. React Router 7은 이 비동기 현실을 라우트 계층으로 표현하도록 설계되어 있습니다. 따라서 RSC 환경 에러 경계 Pending UI 설계의 초점은 예쁜 fallback UI가 아니라 장애 반경의 제어, 복구 행동의 명확화, 문맥 보존 비용의 최소화로 이동해야 합니다. 이 글은 그 관점을 구현과 운영까지 한 흐름으로 연결합니다.

핵심 결론은 단순합니다. 첫째, Pending은 진행 상태이고 Error는 종료 상태이므로 절대 같은 언어로 표현하면 안 됩니다. 둘째, 경계는 화면 단위가 아니라 라우트 책임 단위로 배치해야 합니다. 셋째, 품질의 차이는 컴포넌트 기교보다 런타임 근거를 가진 운영 계약에서 발생합니다. 이 세 가지를 지키면 React Router 7 도입 효과는 기능 홍보가 아니라 MTTR 단축, 재이탈률 감소, 온콜 피로도 완화처럼 측정 가능한 결과로 나타납니다.

## 들어가며

React Router 7과 RSC 조합은 기술 문서만 보면 매우 이상적인 구조처럼 보입니다. 라우트 중심 데이터 모델, 계층적 경계, 전환 상태 표현, 서버 주도 렌더링까지 필요한 재료가 이미 제공되기 때문입니다. 그러나 실제 제품에서는 동일한 스택을 쓰는데도 어떤 팀은 “오류가 나도 서비스가 덜 무섭다”는 평가를 받고, 어떤 팀은 “조금만 느려도 멈춘 것 같다”는 피드백을 받습니다. 같은 프레임워크에서 이런 격차가 생기는 이유는 구현 숙련도보다 상태 의미를 다루는 방식의 차이입니다.

문제의 시작은 보통 선의에서 출발합니다. UI를 단순화하려고 로딩과 실패에 같은 카드, 같은 회색 블록, 같은 전면 오버레이를 재사용합니다. 개발자 입장에서는 컴포넌트 재사용률이 올라가고 디자인 일관성도 유지되는 것처럼 보입니다. 하지만 사용자 인지 과정에서는 정반대 결과가 나타납니다. Pending은 “잠시 후 결과가 도착할 가능성”을 포함한 상태이고 Error는 “현재 경로에서 결과가 더 이상 오지 않는다”는 확정 상태입니다. 상태 기계 관점에서 전이 조건이 완전히 다른 두 상태를 같은 신호로 보여주면, 사용자는 기다릴 타이밍과 복구할 타이밍을 구분하지 못합니다.

RSC 환경에서는 이 문제가 더 자주 노출됩니다. 서버가 응답을 한 번에 보내지 않고 세그먼트 단위로 흘려보내기 때문에, 화면은 본질적으로 비동기 조각들의 합으로 구성됩니다. 즉 정상적인 시나리오에서도 화면 일부는 완료, 일부는 진행, 일부는 실패일 수 있습니다. 이런 환경에서 페이지 전체 성공/실패 이분법을 유지하면, 시스템의 실제 상태와 UI 표현이 어긋납니다. 사용자는 이미 사용 가능한 정보를 보지 못한 채 대기하거나, 복구 가능한 국소 실패를 전체 장애로 오인하게 됩니다.

그래서 이 글은 문법 소개보다 계약 설계에 집중합니다. 어떤 경계를 어디에 둬야 하는지, 왜 그 위치가 런타임 전파 경로와 맞물리는지, 그 선택이 운영 비용을 어떻게 바꾸는지를 설명하겠습니다. 특히 RSC 환경 에러 경계 Pending UI를 하나의 운영 단위로 다룰 때 어떤 기준이 필요한지까지 연결하겠습니다. 목표는 React Router 7을 “도입했다”에서 끝내지 않고, “운영 가능한 실패 모델을 만들었다”로 끌어올리는 것입니다.

## 설계 방향과 의도

설계의 첫 기준은 영향 범위입니다. 경계는 오류를 없애는 장치가 아니라 오류의 반경을 제한하는 장치입니다. React Router 7의 중첩 라우트는 이 목적에 맞게 설계되어 있습니다. 상위 라우트는 내비게이션과 위치 인지 같은 지속 문맥을 담당하고, 하위 라우트는 특정 콘텐츠나 상호작용 단위를 담당합니다. 따라서 경계를 둘 때도 같은 계층 논리를 따라야 합니다. 상위 경계가 지나치게 많은 실패를 흡수하면 문맥 손실 비용이 커지고, 하위 경계가 없으면 사소한 실패가 상위까지 전파되어 전체 화면이 흔들립니다.

이 메커니즘을 런타임으로 보면 더 분명해집니다. React Router 7에서 오류는 가장 가까운 경계로 포착을 시도하고, 실패하면 상위로 전파됩니다. 즉 경계 위치는 단순히 렌더링 코드 배치가 아니라 전파 경로의 종착점을 정하는 설정입니다. 실무에서는 `error_origin_route`와 `error_caught_route`를 분리 기록하면 경계 설계가 적절한지 바로 드러납니다. 상위에서 과도하게 포착되는 비율이 높다면, 기능팀은 “오류가 많다”보다 먼저 “경계가 너무 위에 있다”를 의심해야 합니다.

설계의 두 번째 기준은 복구 가능성입니다. Error UI는 안내문이 아니라 의사결정 인터페이스입니다. 사용자는 실패 원리 자체보다 다음 행동의 비용을 먼저 계산합니다. 지금 다시 시도할지, 이전 화면으로 돌아갈지, 임시 우회 경로로 갈지 즉시 판단할 수 있어야 합니다. React Router 7은 라우트 단위 에러 경계 안에서 이 선택지를 지역적으로 제공할 수 있으므로, 복구 동작이 전역 정책과 충돌하지 않도록 설계하기 쉽습니다. 중요한 점은 버튼 개수보다 상태 보존 약속입니다. 입력값, 필터, 스크롤, 탭 위치가 복구 후 유지되는지 명확히 알려주지 않으면 사용자는 재시도 자체를 회피합니다.

운영 측면에서는 이 약속이 비용 구조를 바꿉니다. 상태 보존 없는 재시도는 재입력과 재탐색을 유발하고, 이는 사용자 체류 시간 증가처럼 보일 수 있지만 실제로는 마찰 증가입니다. 반대로 상태 보존이 명확하면 실패 후 복구 성공률이 올라가고 이탈률이 내려갑니다. 온콜 입장에서도 “왜 실패했는가” 이전에 “실패 후 사용자가 살아남는가”가 먼저 개선됩니다. 전자는 완전한 제거가 어렵지만 후자는 경계 계약만으로 빠르게 개선할 수 있기 때문입니다.

세 번째 기준은 문맥 보존 비용입니다. Pending UI를 설계할 때 많은 팀이 “무엇을 보여줄까”부터 고민하지만, 실제로는 “무엇을 가리지 말아야 할까”가 더 중요합니다. 짧은 지연에서 전체 오버레이를 띄우면 사용자는 현재 맥락을 잃고, 반복 전환 시 깜빡임이 누적되어 성능이 실제보다 나쁘게 체감됩니다. React Router 7의 전환 상태는 라우트 단위로 관찰할 수 있으므로, 지연 길이에 따라 노출 강도를 다르게 적용하는 것이 합리적입니다. 예를 들어 150~300ms 수준의 짧은 지연에서는 기존 UI를 유지하고, 의미 있는 지연에서만 국소 placeholder를 열어야 합니다.

이 선택은 런타임 근거를 가집니다. RSC 스트리밍에서는 먼저 도착한 세그먼트를 즉시 렌더링하는 편이 전체 체감 시간을 줄입니다. 그런데 상위 레벨에서 공격적으로 Pending을 띄우면, 이미 도착한 콘텐츠까지 함께 가려져 스트리밍 이점이 사라집니다. 즉 과한 Pending은 안정감을 주는 대신 정보를 숨겨 실제 의사결정 속도를 늦춥니다. 운영 지표로 보면 `pending_duration_ms` 자체보다 `visible_blocked_duration_ms`를 함께 추적해야 이유가 보입니다. 같은 대기 시간이어도 차단 시간이 짧으면 사용자 불만은 급감합니다.

마지막 기준은 소유권입니다. 경계는 코드 조각이 아니라 팀 간 계약입니다. React Router 7을 쓰면서도 팀마다 다른 복구 문구, 다른 Pending 정책, 다른 로그 스키마를 쓰면 앱 전체가 “작은 서비스 모음”처럼 동작합니다. 사용자 입장에서는 학습 비용이 라우트 이동마다 다시 발생합니다. 그래서 최소 계약을 고정해야 합니다. 어떤 이벤트를 기록하는지, 어떤 복구 행동을 기본 제공하는지, 어떤 라우트가 어느 팀 책임인지를 문서와 런북으로 묶어야 합니다. 이것이 개발 자유를 억압하는 규칙처럼 보일 수 있지만, 실제로는 장애 시 커뮤니케이션 비용을 줄여 배포 속도를 지키는 장치입니다.

## 실제 구현과 런타임 동작

실제 동작을 이해하려면 라우트 전환 순간부터 분해해서 보는 것이 좋습니다. 사용자가 링크를 클릭하거나 폼 액션을 실행하면 React Router 7은 새로운 매치 집합을 계산하고, 각 라우트 모듈의 데이터 의존성을 평가합니다. 이때 UI는 단일 상태로 이동하지 않습니다. 일부 라우트는 즉시 렌더 가능하고, 일부는 서버 응답을 기다리며, 일부는 에러를 던질 수 있습니다. RSC 스트리밍이 결합되면 이 비동기성은 더 명확해집니다. 결과가 준비된 세그먼트부터 순차적으로 전달되기 때문입니다.

따라서 구현의 핵심은 “한 번에 완성된 화면” 가정을 버리는 것입니다. 예를 들어 상위 레이아웃은 유지한 채 본문 슬롯만 Pending으로 전환하면 사용자는 현재 위치와 내비게이션 맥락을 유지합니다. 반대로 전역 오버레이를 띄우면 이미 렌더 가능한 영역까지 함께 차단되어, 실제로는 빨라진 시스템을 느리다고 평가하게 됩니다. 이 차이는 미묘한 미감 문제가 아니라 정보 접근 순서의 문제입니다. 사용자 판단에 필요한 최소 정보가 먼저 보이면 대기는 허용되고, 그렇지 않으면 같은 1초도 길게 느껴집니다.

오류 처리에서도 같은 원리가 적용됩니다. 하위 콘텐츠에서 발생한 오류가 해당 계층에서 포착되면 장애는 국소화됩니다. 사용자는 내비게이션을 유지한 채 문제 영역만 인지하고 복구를 시도할 수 있습니다. 하지만 가까운 경계가 없으면 오류는 상위로 전파되어 레이아웃 전체가 대체되고, 사용자는 “어디가 고장인지”보다 “앱 전체가 고장인지”를 먼저 의심하게 됩니다. React Router 7의 계층형 경계는 이 전파를 제어하는 기본 메커니즘이며, 실제 운영에서는 상위 경계 포착 비율을 낮추는 것이 안정화의 초기 목표가 됩니다.

다음은 라우트 단위 관측 이벤트를 기록할 때 사용하는 최소 형태의 예시입니다. 이 코드는 패턴을 설명하기 위한 축약본이며, 핵심은 어떤 값을 남겨야 사후 분석이 가능한지에 있습니다.

```ts
export function trackRouteEvent(type: "pending" | "error" | "recovery", payload: Record<string, unknown>) {
emit("route_event", { type, ...payload, ts: Date.now() });
}
```

이 정도 데이터만 있어도 운영 질문이 바뀝니다. “오늘 오류가 많았다”가 아니라 “어느 라우트에서 발생한 오류가 상위 경계로 과전파되었는가”, “재시도 버튼이 실제로 복구에 기여하는가”, “Pending이 길어서 문제인지 가시 차단이 길어서 문제인지”를 구분할 수 있습니다. 즉 React Router 7 구현의 완성도는 컴포넌트 코드의 우아함보다 이벤트 설계의 정확성에서 판가름 납니다.

재시도 전략도 라우트 책임과 함께 설계해야 합니다. 일시적 네트워크 변동이 잦은 조회성 라우트는 제한된 자동 재시도가 유리할 수 있습니다. 반면 사용자 입력 비용이 큰 작성 플로우에서는 자동 재시도보다 상태 보존과 명시적 선택지가 우선입니다. 자동 재시도가 길어질수록 사용자는 시스템이 일하고 있는지 멈췄는지 판단하기 어려워지고, 결국 브라우저 새로고침으로 탈출합니다. 새로고침은 종종 문맥을 초기화하므로 운영적으로는 “실패 1회”보다 더 큰 손실입니다.

복구 액션을 설계할 때도 버튼 개수보다 메시지 품질이 중요합니다. 예를 들어 “다시 시도”만 두는 것과 “입력한 필터는 유지되며 다시 시도할 수 있습니다”라고 명시하는 것은 사용자의 위험 인식을 다르게 만듭니다. 전자는 실패 가능성을 다시 떠안는 느낌을 주지만, 후자는 실패 비용이 제한적이라는 신호를 줍니다. 이런 문구 차이가 실제 재시도율을 바꾸고, 고객지원 채널에서 반복 문의를 줄입니다. 결국 RSC 환경 에러 경계 Pending UI에서 텍스트는 장식이 아니라 복구 비용을 낮추는 운영 인터페이스입니다.

또 하나 중요한 지점은 하이드레이션 시간차입니다. RSC 결과가 도착해도 클라이언트 상호작용이 즉시 가능하지 않은 구간이 생길 수 있습니다. 이때 Pending을 단순 로딩 아이콘으로 처리하면 사용자는 “보이는데 왜 눌리지 않지”라는 혼란을 겪습니다. React Router 7 구현에서는 상호작용 가능 시점과 데이터 도착 시점을 분리해 안내해야 합니다. 예를 들어 버튼을 비활성화하면서 이유를 제공하거나, 상호작용 준비 중이라는 짧은 텍스트를 노출하면 인지 부조화를 줄일 수 있습니다. 이런 미세한 신호 설계가 누적되어 서비스 신뢰도를 만듭니다.

## 어떤 문제를 어떻게 해결하는가

현장에서 가장 먼저 터지는 문제는 상태 해석의 충돌입니다. 같은 회색 블록, 같은 스피너, 같은 전면 마스킹을 Pending과 Error에 함께 쓰면 사용자는 대기와 실패를 구분하지 못합니다. 이 현상은 단순 취향이 아니라 인지 모델의 충돌입니다. Pending은 시간이 지나면 성공으로 전이될 수 있는 상태이고, Error는 외부 개입 또는 다른 경로 선택이 필요한 상태입니다. React Router 7에서는 전환 상태와 에러 경계를 분리해 모델링할 수 있으므로, 두 상태를 문구·행동·가시 영역까지 분리해야 합니다. 이를 적용하면 사용자는 기다려야 할 순간과 행동해야 할 순간을 빠르게 구분하고, 불필요한 새로고침이나 이탈이 줄어듭니다.

두 번째 문제는 작은 실패가 전체 실패처럼 보이는 전파 효과입니다. 메커니즘은 명확합니다. 하위 라우트의 오류를 처리할 경계가 없으면 상위 경계가 대신 처리하고, 그 결과 상위 레이아웃 전체가 대체됩니다. 사용자 눈에는 본문 한 위젯 실패가 앱 전체 붕괴로 보입니다. React Router 7 구현에서는 하위 경계의 추가가 단순한 방어 코드가 아니라 장애 반경 축소 전략입니다. 특히 내비게이션과 위치 정보를 담당하는 레이아웃 경계는 최대한 보존하고, 콘텐츠 경계에서 실패를 흡수하도록 구조를 잡아야 합니다. 운영 결과로는 상위 경계 점유율이 감소하고, 복구 후 탐색 재개율이 올라갑니다.

세 번째 문제는 깜빡임입니다. 성능이 충분히 빠른데도 “느리다”는 평가를 받는 경우가 여기에 해당합니다. 원인은 짧은 지연에도 공격적으로 Pending을 노출하는 정책입니다. React Router 7 런타임은 라우트 전환 신호를 제공하므로, 지연 임계값을 기준으로 노출 강도를 조절할 수 있습니다. 짧은 구간에서는 기존 UI를 유지하고, 일정 시간을 넘길 때만 국소 placeholder를 보여주면 됩니다. 이 방식은 평균 응답 시간을 바꾸지 않아도 체감 품질을 크게 개선합니다. 운영 측면에서는 전환당 시각적 상태 변경 횟수가 줄어들어 사용자 피로와 민원 빈도가 함께 감소합니다.

네 번째 문제는 장애 대응의 개인 의존성입니다. 동일한 오류라도 누구의 온콜 주간인지에 따라 대응 속도와 결과가 달라진다면, 기술 부채는 코드보다 프로세스에 쌓입니다. React Router 7은 라우트라는 명확한 책임 단위를 제공하므로, 이를 운영 조직과 연결해야 합니다. 각 라우트에 책임 팀, 1차 완화 행동, 로그 대시보드 링크, 롤백 기준을 연결한 런북을 두면 초기 대응이 표준화됩니다. 결과적으로 탐지부터 완화까지의 경로가 짧아지고, 회고에서 재발 방지 조치가 구조화됩니다. 이 변화는 개발자 경험뿐 아니라 야간 온콜 피로도까지 줄이는 실질적 효과가 있습니다.

다섯 번째 문제는 개선 우선순위가 보이지 않는다는 점입니다. 페이지 단위 지표만 보면 “어디가 문제인지”가 아니라 “어디든 문제인 것 같다”는 결론만 남습니다. React Router 7 설계 의도에 맞추려면 라우트 단위로 Pending, Error, Recovery를 함께 수집해야 합니다. 그래야 지연은 짧지만 복구 성공률이 낮은 라우트, 오류는 드물지만 상위 전파가 큰 라우트처럼 숨어 있는 위험을 찾을 수 있습니다. 운영 비용 관점에서 이는 매우 중요합니다. 우선순위가 정밀해질수록 적은 인력으로 더 큰 체감 개선을 만들 수 있기 때문입니다.

여섯 번째 문제는 팀 간 품질 편차입니다. 어떤 팀은 복구 버튼을 충분히 제공하고, 어떤 팀은 오류 문구만 남기며, 어떤 팀은 상태 보존 여부를 아예 밝히지 않습니다. 사용자에게는 이것이 “앱 성격이 화면마다 바뀌는 경험”으로 전달됩니다. 해결의 핵심은 자율성을 없애는 것이 아니라 최소 계약을 명확히 하는 것입니다. React Router 7 기준으로 복구 행동 최소 개수, 상위 문맥 보존 원칙, 이벤트 필수 필드를 공통 규약으로 고정하면, 각 팀은 도메인 특화 UX를 유지하면서도 바닥 품질을 일정하게 보장할 수 있습니다. 이 구조는 신규 인력 온보딩 비용도 낮춥니다. 무엇을 반드시 지켜야 하는지 선명하기 때문입니다.

결국 문제 해결의 공통 분모는 같습니다. 경계를 UI 장식으로 보지 않고 런타임 계약으로 다루는 것입니다. 계약이 명확하면 구현 선택은 다양해도 운영 결과는 수렴합니다. 계약이 없으면 훌륭한 컴포넌트도 조합 순간에 불안정해집니다. React Router 7과 RSC는 이미 충분한 메커니즘을 제공합니다. 남은 과제는 그 메커니즘을 팀의 운영 언어로 번역하는 일입니다.

## 트레이드오프

### 경계 세분화: 장애 반경 축소 vs 테스트 복잡도 증가
경계를 세분화하면 장애 반경은 줄어들지만 구현 복잡도와 테스트 포인트는 늘어납니다. 왜 이런 비용이 생기냐면, 라우트가 많아질수록 Pending·Error·Recovery의 조합 상태가 기하급수적으로 증가하기 때문입니다. React Router 7 런타임은 계층형 전파 규칙을 제공하지만, 각 라우트가 서로 다른 복구 정책을 갖는 순간 QA 시나리오와 관측 스키마도 함께 늘어납니다. 운영 측면에서는 초기 설정 비용이 분명히 커집니다. 다만 이 비용은 장애가 발생했을 때 상위 전파를 막아주는 보험료에 가깝습니다. 초기에 표준 템플릿을 만들면 이후 증분 비용은 빠르게 낮아집니다.

### Pending 임계값: 시각 안정성 vs 즉시성 인식
Pending 노출 임계값을 높이면 깜빡임은 줄지만, 실제 대기 시간을 감추는 것 아니냐는 우려가 생길 수 있습니다. 이 딜레마의 메커니즘은 사용자가 “시간”보다 “통제감”에 더 민감하다는 점에서 풀립니다. React Router 7 구현에서는 상위 문맥을 유지하면서 지연을 국소 표시하면, 총 대기 시간은 같아도 사용자는 작업이 멈췄다고 느끼지 않습니다. 운영 지표로는 평균 응답 시간이 동일해도 불만 접수율과 새로고침 비율이 내려갑니다. 즉 임계값 조정은 속도 미화가 아니라 인지 비용 최적화에 가깝습니다.

### 자동 재시도: 일시 장애 복원력 vs 지속 장애 체감 악화
자동 재시도 비중을 높이면 일시 장애 복구율은 오르지만, 지속 장애에서는 사용자 체감이 더 나빠질 수 있습니다. 원인은 실패가 확정된 상황에서 시스템이 계속 시도만 반복하면 사용자 의사결정이 지연되기 때문입니다. React Router 7에서는 라우트별로 자동 재시도 한도를 두고, 임계 초과 시 수동 복구로 전환하는 정책을 구현하기 쉽습니다. 운영 효과는 명확합니다. 불필요한 대기 시간이 줄고, 실패 후 행동 전환이 빨라져 이탈률이 낮아집니다. 대신 정책이 복잡해질수록 문서화와 온콜 교육이 필수이므로, 분기 규칙을 최소 집합으로 유지하는 것이 좋습니다.

## 마무리하며

React Router 7과 RSC 조합의 가치는 “최신 렌더링 기술을 썼다”는 사실이 아니라 “부분 성공과 부분 실패가 공존하는 현실을 사용자 경험으로 안전하게 번역했다”는 결과에서 확인됩니다. 이를 위해서는 Pending과 Error를 엄격히 구분하고, 라우트 계층에 맞춰 경계를 배치하며, 복구 행동과 상태 보존 약속을 운영 계약으로 고정해야 합니다. 이 세 가지가 갖춰지면 장애는 사라지지 않아도 파급이 줄고, 복구는 복잡해도 체감은 단순해집니다.

실무에서 특히 중요한 점은 최적화 순서입니다. 많은 팀이 먼저 렌더링 성능을 더 끌어올리려 하지만, 사용자 불만의 큰 부분은 절대 속도보다 상태 해석의 불확실성에서 발생합니다. 무엇이 진행 중이고 무엇이 실패했는지, 지금 무엇을 하면 되는지 명확하면 사용자는 같은 지연도 더 관대하게 받아들입니다. 반대로 이 신호가 불명확하면 성능 개선이 있어도 신뢰는 회복되지 않습니다.

운영 비용 관점에서도 경계 전략은 ROI가 높습니다. 경계 재설계는 대개 대규모 인프라 투자 없이 적용 가능하며, 적용 직후부터 상위 전파 감소, 복구 성공률 상승, 문의량 감소 같은 효과를 확인할 수 있습니다. 이는 개발팀뿐 아니라 고객지원, 제품운영, 온콜 체계 전체의 부담을 동시에 낮춥니다. 결국 React Router 7의 진짜 성숙도는 API 사용량이 아니라, 실패를 통제 가능한 사건으로 바꾸는 조직의 실행력으로 드러납니다.

지금 서비스가 “가끔 멈춘다”는 평가를 받고 있다면, 먼저 프레임워크를 의심하기보다 경계 계약을 점검해 보시기 바랍니다. 어디서 실패가 시작되고 어디서 포착되는지, 사용자가 어떤 복구 행동을 실제로 선택하는지, 그 과정에서 어떤 문맥이 사라지는지를 추적하면 개선 포인트가 명확해집니다. 기술 스택은 이미 충분히 강력합니다. 남은 것은 그 힘을 사용자가 신뢰할 수 있는 형태로 전달하는 설계와 운영입니다.

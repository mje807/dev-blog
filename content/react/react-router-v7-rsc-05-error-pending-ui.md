## 한눈에 보기

React Router 7과 RSC를 함께 도입한 뒤에도 사용자가 “앱이 자주 멈춘다”고 느끼는 이유는, 대개 렌더링 엔진의 한계가 아니라 **경계(boundary) 설계의 부재**에 있습니다. 특히 Pending 상태와 Error 상태를 동일한 시각적 신호로 처리하면, 사용자는 현재가 “기다리면 회복되는 상태”인지 “명시적 복구 행동이 필요한 실패 상태”인지 구분하지 못합니다.

이 글은 React Router 7을 기준으로 다음 세 가지를 사실 중심으로 정리합니다.

- React Router 7에서 Error Boundary와 Pending UI는 단순 UI 패턴이 아니라 **장애 반경을 제어하는 운영 단위**라는 점
- RSC의 스트리밍/부분 렌더링 특성에서, React Router 7 라우트 계층별 경계를 어떻게 분리해야 하는지
- 팀 단위 운영에서 소유권, 관측 지표, 온콜 대응 절차를 React Router 7 라우트 단위로 고정하는 방법

결론적으로 React Router 7의 도입 효과는 “최신 기능 사용 여부”보다 “실패와 대기를 구분해 운영 가능한 계약으로 만들었는가”에서 결정됩니다.

## 들어가며

React Router 7은 데이터 로딩, 라우트 모듈, 에러 처리, 전환 상태를 라우트 중심으로 모델링하기 때문에 RSC와 결합할 때 구조적 이점을 제공합니다. 그러나 실제 서비스에서는 React Router 7을 도입한 뒤에도 UX가 불안정하다는 보고가 반복됩니다. 이 현상은 모순처럼 보이지만 원인은 비교적 일관됩니다. **React Router 7이 제공하는 경계 모델을 “컴포넌트 렌더링 옵션”으로만 사용하고, “운영 계약”으로 사용하지 않기 때문**입니다.

RSC 환경에서는 서버에서 조합된 결과가 한 번에 완성되어 도착하지 않습니다. 일부 구간은 즉시 표시되고, 일부 구간은 지연되며, 일부 구간은 실패합니다. 이때 사용자에게 필요한 것은 “기술적으로 무엇이 일어났는가”가 아니라 “지금 무엇을 기대하고 어떤 행동을 해야 하는가”입니다. React Router 7은 바로 이 지점을 라우트 단위로 분해해 다룰 수 있게 설계되었습니다.

문제는 많은 구현이 여전히 페이지 전체 성공/실패의 이분법에 머문다는 점입니다. 로딩 중에도 빈 화면, 실패해도 빈 화면을 보여주면 사용자 입장에서는 둘 다 “고장”입니다. React Router 7의 장점은 이런 모호성을 줄일 수 있다는 데 있는데, 경계 위치와 복구 정책이 없으면 이 장점이 사라집니다.

이 글은 React Router 7 + RSC 실무를 전제로, 설계 의도, 런타임 동작, 운영 적용을 하나의 흐름으로 연결합니다. 문법 나열보다 “왜 이렇게 설계해야 하고, 실제로 어떤 문제가 줄어드는가”를 중심으로 설명합니다.

## RSC 환경에서 상태가 섞이는 구조적 이유

RSC에서는 서버 컴포넌트 결과와 클라이언트 상호작용 지점이 분리됩니다. 이 구조 자체는 성능과 유지보수 측면에서 유리하지만, 상태 신호를 섞기 쉬운 조건을 만듭니다. React Router 7을 사용해도 다음 조건이 겹치면 혼합이 발생합니다.

첫째, **동일한 대체 UI를 Pending과 Error에 재사용**하는 경우입니다. Pending은 아직 결과가 확정되지 않은 진행 상태이고, Error는 결과가 실패로 확정된 종료 상태입니다. 상태 기계 관점에서 두 상태는 전이 규칙이 완전히 다릅니다. 그런데 동일한 시각 요소를 쓰면 사용자 행동이 지연됩니다. 기다려야 할 때 이탈하고, 복구해야 할 때 기다리게 됩니다.

둘째, **경계 배치를 화면 구조 중심으로만 결정**하는 경우입니다. 예를 들어 상세 페이지 본문에만 Error Boundary를 두고 상위 레이아웃 복원 전략이 없으면, 실제 실패는 내비게이션·필터·브레드크럼까지 영향을 줍니다. React Router 7은 라우트 계층별 격리가 가능하지만, 배치 기준이 “컴포넌트 트리 보기 편함”이면 장애 반경은 줄지 않습니다.

셋째, **관측 단위가 페이지 기준에 머무르는 경우**입니다. RSC + React Router 7에서는 실패 지점이 서버 fetch, 라우트 loader/action, 클라이언트 hydration 단계로 분리됩니다. 페이지 단위 로그만으로는 원인 위치가 모호해지고 MTTR이 길어집니다.

넷째, **소유권 부재**입니다. React Router 7 라우트마다 정책이 달라지면 사용자는 각 화면에서 다른 규칙을 학습해야 합니다. 같은 앱 안에서 어느 라우트는 스켈레톤, 어느 라우트는 전체 오버레이, 어느 라우트는 복구 버튼 없음이 반복되면 체감 품질은 기술 스택과 무관하게 하락합니다.

즉, React Router 7 + RSC의 불안정은 기능 부족이 아니라 **상태 의미 분리 실패 + 운영 계약 부재**로 설명됩니다.

## 설계 방향과 의도

React Router 7 환경에서 에러 경계와 Pending UI를 설계할 때 핵심 축은 세 가지입니다. **영향 범위**, **복구 가능성**, **문맥 보존 비용**입니다.

### 1) 영향 범위 기준: 경계는 작게, 맥락은 크게 보존합니다

React Router 7 라우트 계층에서 상위 레이아웃은 사용자 여정의 기준점입니다. 내비게이션, 현재 위치, 필터 상태 같은 맥락이 사라지면 사용자는 실패 지점보다 먼저 방향 감각을 잃습니다. 따라서 설계 의도는 “실패를 숨긴다”가 아니라 “실패를 국소화한다”입니다.

- 상위 라우트 경계: 앱 뼈대와 전역 탐색 요소 보존
- 중간 라우트 경계: 섹션 단위 실패 격리
- 하위 콘텐츠 경계: 카드/패널 단위 대체 및 빠른 복구

React Router 7의 라우트 단위 경계는 이 계층화를 구현하기 위한 구조적 도구입니다.

### 2) 복구 가능성 기준: Error는 안내가 아니라 의사결정 UI입니다

Error Boundary의 설계 의도는 “친절한 문구 출력”이 아닙니다. 실패 후 다음 행동을 즉시 선택할 수 있게 하는 것입니다. React Router 7에서 최소 계약은 다음 세 가지입니다.

- 실패 범위: 무엇이 실패했는지 라우트 수준으로 명시
- 즉시 행동: 재시도, 이전, 홈 이동 중 최소 2개 제공
- 상태 보존: 입력값/필터/스크롤 보존 여부를 명확히 표시

이 계약이 없으면 Error UI는 사실상 막다른 화면입니다.

### 3) 문맥 보존 비용 기준: Pending은 “보여주는 것”보다 “안 보여줄 것”을 먼저 정합니다

React Router 7 전환에서 모든 지연에 Pending UI를 노출하면 깜빡임이 증가해 체감 품질이 하락합니다. 설계 의도는 “항상 표시”가 아니라 “의미 있는 지연에서만 표시”입니다. 일반적으로 다음 규칙이 안정적입니다.

- 짧은 지연: 기존 UI 유지, 명시적 Pending 생략
- 중간 지연: 라우트 영역 수준의 스켈레톤/placeholder 노출
- 긴 지연: 진행 상태 + 대체 경로(취소/다른 경로) 안내

React Router 7은 라우트 전환 상태를 구분할 수 있으므로, 지연 시간대별 전략을 구조적으로 적용하기 좋습니다.

### 4) 팀 운영 관점의 의도: 경계는 코드가 아니라 계약 문서입니다

React Router 7 도입 초기에 가장 효과적인 정책은 “라우트별 책임자 + 공통 임계값 + 공통 이벤트 스키마”를 동시에 고정하는 것입니다. 누가 소유하는지 불명확하면 경계는 빠르게 퇴화합니다. 설계 의도는 개인 구현 자유를 제한하는 것이 아니라, **사용자 경험의 변동 폭을 줄이는 것**입니다.

## 실제 구현과 런타임 동작

이 섹션은 React Router 7 + RSC에서 실제로 어떤 이벤트가 어떤 순서로 발생하고, 왜 경계 분리가 필요한지 런타임 관점에서 설명합니다.

### 1) 라우트 전환 시점: Pending은 전환 신호, Error는 종료 신호입니다

사용자가 React Router 7에서 라우트 전환을 트리거하면, 런타임은 새 라우트 트리의 데이터 의존성과 렌더링 준비 상태를 평가합니다. 이때 Pending은 “아직 확정 전” 신호입니다. 성공과 실패 모두 Pending 이후에만 확정됩니다. 따라서 Pending UI는 실패 메시지와 결합하면 의미가 충돌합니다.

RSC에서는 서버에서 조합된 조각이 스트리밍될 수 있으므로, 화면 일부는 즉시 갱신되고 일부는 대기할 수 있습니다. React Router 7 라우트 경계가 적절히 나뉘어 있으면 지연 구간만 대체됩니다. 경계가 없거나 과도하게 상위에 있으면 작은 지연이 전체 화면 대기로 확장됩니다.

### 2) 실패 전파 경로: 가장 가까운 경계에서 흡수되지 않으면 상위로 전파됩니다

React Router 7의 Error Boundary는 계층적으로 동작합니다. 하위 라우트에서 발생한 오류를 해당 계층이 처리하지 못하면 상위 경계로 전파됩니다. 이 특성은 안전장치이지만, 경계가 거칠면 장애 반경이 커집니다.

운영 관점에서 중요한 사실은 “오류 발생 자체”보다 “어느 경계에서 최종 흡수되었는지”입니다. 최종 흡수 위치가 상위일수록 사용자 문맥 손실이 큽니다. 따라서 로그도 `error_origin_route`와 `error_caught_route`를 분리해 기록해야 원인 분석이 가능합니다.

### 3) 스트리밍과 하이드레이션의 시간차: 부분 성공이 기본 시나리오입니다

RSC 런타임에서는 네트워크 상태, 서버 처리량, 캐시 히트율에 따라 각 세그먼트 도착 시간이 달라집니다. React Router 7에서 이를 단일 로딩 상태로 평탄화하면 실제 런타임과 UI 표현이 어긋납니다. 결과적으로 사용자는 이미 이용 가능한 정보를 보지 못하고 불필요하게 대기합니다.

실무에서는 “부분 성공을 허용하는 경계”가 성능 체감에 직접적입니다. 예를 들어 상위 레이아웃과 핵심 요약 정보가 먼저 표시되고, 보조 패널만 Pending인 구조는 전체 차단보다 이탈률이 낮습니다. 이는 프레임워크 취향이 아니라 런타임 도착 순서와 사용자 의사결정 흐름이 맞아떨어지기 때문입니다.

### 4) 재시도 동작: 자동 재시도와 수동 재시도의 책임을 분리합니다

React Router 7 + RSC 환경에서 모든 실패를 자동 재시도로 처리하면, 일시 장애에서는 유리하지만 지속 장애에서는 사용자 대기 시간을 불필요하게 늘립니다. 반대로 즉시 수동 복구만 요구하면 경미한 네트워크 변동에도 사용자가 개입해야 합니다.

런타임 정책은 다음처럼 분리하는 것이 안정적입니다.

- 일시적 실패 가능성이 높은 요청: 제한된 자동 재시도 후 수동 전환
- 사용자 비용이 큰 작업(작성/결제): 상태 보존 우선 + 명시적 복구 선택지
- 비핵심 위젯: 국소 실패 허용, 전체 흐름 유지

React Router 7 경계 설계가 이 정책을 수용할 수 있어야 운영 일관성이 생깁니다.

### 5) 관측 이벤트: 라우트 단위로 수집해야 개선이 가능합니다

페이지 단위 통계만으로는 React Router 7의 경계 효과를 검증할 수 없습니다. 최소 이벤트는 다음과 같습니다.

- `route_pending_started`, `route_pending_resolved`, `pending_duration_ms`
- `route_error_thrown`, `route_error_caught`, `error_boundary_level`
- `recovery_action_clicked`, `recovery_success`, `post_recovery_bounce`

이렇게 수집하면 “어디서 지연이 길고”, “어디서 복구가 실패하며”, “어느 경계가 과도하게 상위인지”를 정량으로 확인할 수 있습니다.

## 어떤 문제를 어떻게 해결하는가

여기서는 React Router 7 + RSC에서 실제로 자주 발생하는 문제와, 경계 설계가 어떤 방식으로 해결하는지 일대일로 정리합니다.

### 문제 1) 로딩과 실패가 같은 화면으로 보입니다
**원인**: Pending UI와 Error UI를 동일 패턴으로 재사용했기 때문입니다.
**해결**: React Router 7 라우트마다 상태 의미를 분리합니다. Pending은 진행 신호(문맥 유지), Error는 행동 신호(복구 경로 제공)로 계약을 분리하면 사용자의 판단 비용이 줄어듭니다.

### 문제 2) 작은 장애가 전체 화면 붕괴로 확장됩니다
**원인**: Error Boundary가 상위 레벨에만 존재해 실패 전파가 넓게 발생합니다.
**해결**: React Router 7 계층형 라우트에 맞춰 중간/하위 경계를 추가해 장애를 국소화합니다. 상위 레이아웃은 가능한 유지하고, 실패 영역만 대체합니다.

### 문제 3) 빠른 응답에서도 로딩 깜빡임이 잦습니다
**원인**: 지연 시간 임계값 없이 Pending을 즉시 노출합니다.
**해결**: React Router 7 전환에서 노출 임계값을 운영 규칙으로 고정합니다. 짧은 지연은 기존 UI 유지, 중간 이상 지연에만 구조화된 Pending을 노출합니다. 깜빡임이 줄고 체감 응답성이 개선됩니다.

### 문제 4) 장애 대응이 사람 의존으로 느립니다
**원인**: 라우트 소유권과 런북이 없어 초기 대응이 지연됩니다.
**해결**: React Router 7 라우트별 책임자, 복구 정책, 알림 기준을 문서화합니다. 탐지-분류-완화-복구-회고 순서를 고정하면 온콜 대응 시간이 단축됩니다.

### 문제 5) 개선 우선순위를 정하지 못합니다
**원인**: 페이지 단위 지표만 있어 경계 품질을 비교할 수 없습니다.
**해결**: React Router 7 라우트 단위 이벤트를 수집하고, 에러율·Pending p95·복구 성공률을 함께 봅니다. “지연은 짧지만 복구가 약한 라우트” 같은 숨은 리스크가 드러납니다.

### 문제 6) 팀마다 구현 스타일이 달라 품질 편차가 큽니다
**원인**: 공통 계약 없이 화면별 자율 구현만 허용합니다.
**해결**: React Router 7 기준의 최소 공통 규칙을 둡니다. 예를 들어 복구 버튼 최소 개수, 상위 맥락 보존 원칙, 이벤트 명세를 강제하면 자율성과 일관성을 동시에 확보할 수 있습니다.

---

## 적용 체크리스트(운영 고정용)

React Router 7 + RSC를 운영 중이라면 아래 항목을 배포 전후에 반복 점검하는 것이 효과적입니다.

- 신규/변경 라우트에 React Router 7 Error Boundary가 계층별로 배치되었는가
- Pending UI가 상위 내비게이션/맥락 요소를 불필요하게 가리지 않는가
- Error 상태에서 최소 2개 이상의 복구 행동이 제공되는가
- 상태 보존 여부(입력값/필터/스크롤)가 사용자에게 명확히 전달되는가
- 라우트 단위 Pending/Error/Recovery 이벤트가 누락 없이 수집되는가
- 라우트별 소유 팀과 온콜 백업 담당이 문서화되어 있는가
- 주간 리뷰에서 React Router 7 라우트별 에러율·복구 성공률·재이탈률을 함께 보는가

이 체크리스트를 CI 게이트나 QA 시나리오에 결합하면, React Router 7 도입 초기의 품질 흔들림을 체계적으로 줄일 수 있습니다.

---

## 마무리하며

React Router 7과 RSC의 조합은 기능적으로 강력하지만, 사용자 신뢰를 높이는지 여부는 경계 설계의 성숙도에 달려 있습니다. 핵심은 단순합니다. Pending과 Error를 같은 사건으로 다루지 않고, React Router 7 라우트 단위에서 **실패 반경을 줄이고 복구 경로를 명확히 하며 문맥을 보존**하면 됩니다.

정리하면 다음이 핵심입니다.

- React Router 7에서 경계는 렌더링 옵션이 아니라 운영 계약입니다.
- RSC 런타임은 부분 성공/부분 지연이 기본이므로, React Router 7 경계도 부분 격리를 전제로 설계해야 합니다.
- 품질은 구현 디테일보다 소유권, 지표, 런북이 고정될 때 안정됩니다.

React Router 7을 이미 도입했는데 체감 품질이 기대에 못 미친다면, 성능 최적화보다 먼저 경계 전략을 점검하는 편이 비용 대비 효과가 큽니다. 경계가 안정되면 장애 반경과 복구 시간, 그리고 사용자 이탈이 함께 줄어듭니다.

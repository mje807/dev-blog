React를 처음 배울 때 우리는 `npm install react react-dom`이라는 명령어를 아무 의심 없이 실행합니다. 두 개의 패키지. 단순해 보입니다. 그런데 React의 GitHub 저장소를 직접 열어보면 전혀 다른 풍경이 펼쳐집니다. `packages/` 디렉토리 아래에는 무려 13개 이상의 패키지가 존재하며, 각각이 명확한 경계와 책임을 가지고 있습니다.

왜 이렇게 나뉘어 있을까요? "관심사 분리"라는 교과서적 답변은 표면에 불과합니다. 진짜 이유를 이해하려면 React가 걸어온 길, 그리고 Meta 규모에서 코드를 운영한다는 것이 무엇을 의미하는지부터 살펴봐야 합니다.

## 패키지들은 독립적으로 보이지만, 사실 하나다

React의 패키지들은 겉으로는 각자 독립적인 것처럼 보입니다. `react`는 컴포넌트 API를, `react-dom`은 브라우저 렌더링을, `scheduler`는 태스크 스케줄링을 담당한다고 알려져 있습니다. 그러나 이 패키지들은 실제로 공개 API 뒤에 숨어 있는 **내부 계약(internal contract)**으로 긴밀하게 얽혀 있습니다.

가장 대표적인 예가 `ReactSharedInternals`입니다. 이 객체는 `react` 패키지 내부에 존재하지만, `react-reconciler`가 렌더링 과정에서 이를 직접 수정합니다. 컴포넌트가 마운트되는 단계인지, 업데이트되는 단계인지, 렌더링 외부에서 Hook이 잘못 호출되고 있는지를 이 공유 객체를 통해 reconciler가 실시간으로 제어합니다.

이 구조에서 핵심적인 문제가 드러납니다. 이 내부 계약은 npm의 semver 규칙에 따른 공개 API가 아닙니다. 즉, 패치 버전에서도 언제든 변경될 수 있는 구현 세부사항입니다. 그런데 여러 패키지가 이 구현 세부사항에 동시에 의존하고 있습니다.

만약 이 패키지들이 각각 별도의 GitHub 저장소에 존재했다면 어떤 일이 벌어졌을까요? `react` 내부의 shared internals 구조를 조금이라도 변경하면, `react-reconciler`를 업데이트하고, 그에 맞춰 `react-dom`을 수정하고, `react-native-renderer`를 변경하고, `react-test-renderer`도 따라가야 합니다. 각각 별도의 PR을 올리고, 리뷰를 받고, CI를 통과시키고, npm에 순서대로 배포해야 합니다. 그 과정에서 사용자가 새 `react`와 아직 업데이트되지 않은 구 `react-dom`을 조합하는 순간, 런타임 에러가 발생합니다.

이것은 이론적 시나리오가 아닙니다. JavaScript 생태계에서 반복되어 온 실제 문제이며, React 팀이 **모노레포(monorepo)**를 선택한 가장 근본적인 이유입니다.

## 원자적 변경: 모노레포라는 생존 전략

모노레포의 핵심 가치는 하나의 커밋이 여러 패키지를 동시에 변경할 수 있다는 점입니다. Fiber 노드에 새로운 필드를 추가하는 변경이 `react-reconciler`, `react-dom`, `react-native-renderer`에 동시에 반영됩니다. 하나의 PR, 하나의 리뷰, 하나의 CI 파이프라인. 실패하면 전체가 실패하고, 성공하면 전체가 성공합니다. 이 원자성이 내부 계약의 불일치로 인한 런타임 에러를 구조적으로 방지합니다.

Robert C. Martin이 제시한 **공통 폐쇄 원칙(Common Closure Principle)**이 이 상황을 정확히 설명합니다. "함께 변경되는 것들은 같은 곳에 있어야 한다." React의 패키지들은 독립적으로 보이지만, 내부 계약으로 묶여 있기 때문에 함께 변경될 수밖에 없습니다. 모노레포는 이 현실을 코드 구조에 정직하게 반영한 것입니다.

모노레포와 폴리레포의 선택은 취향이 아닙니다. 패키지 간 내부 의존성이 강하고, 동시 배포가 필수적인 프로젝트에서 모노레포는 생존 전략입니다.

## peerDependency의 진짜 의미: 싱글톤이 깨지면 모든 것이 깨진다

`react-dom`의 `package.json`을 살펴보면 흥미로운 패턴이 보입니다. `react`는 `peerDependencies`로, `scheduler`는 일반 `dependencies`로 선언되어 있습니다. 이 차이는 단순한 관례가 아니라 물리적 필요성에서 비롯됩니다.

React의 Hook 시스템은 전역 상태에 의존합니다. `useState`를 호출하면 내부적으로 `react` 패키지 모듈 스코프의 싱글톤 객체인 `ReactCurrentDispatcher`를 참조합니다. `react-reconciler`는 렌더링 단계에서 이 dispatcher를 적절한 구현체로 교체합니다. 마운트 시에는 초기 상태를 생성하는 구현체로, 업데이트 시에는 기존 상태를 읽는 구현체로, 렌더링 외부에서는 에러를 던지는 구현체로 동적으로 바꿉니다.

문제는 `react` 패키지의 인스턴스가 두 개 존재하면 dispatcher도 두 개가 된다는 점입니다. 컴포넌트 A가 참조하는 `react`의 dispatcher와 reconciler가 설정하는 `react`의 dispatcher가 서로 다른 메모리 주소를 가리킬 수 있습니다. reconciler는 자신이 접근할 수 있는 dispatcher를 렌더링 구현체로 교체하지만, 컴포넌트는 다른 객체를 바라보고 있어 dispatcher가 여전히 초기화되지 않은 상태입니다.

결과는 개발자라면 누구나 한 번쯤 만나봤을 그 에러입니다.

> **"Error: Invalid hook call. Hooks can only be called inside of the body of a function component."**

React 공식 문서가 이 에러의 원인으로 가장 먼저 언급하는 것이 바로 "앱 안에 React 복사본이 두 개 이상 있을 수 있습니다"입니다. `peerDependencies`는 이 문제를 npm의 의존성 해석 단계에서 방지하는 메커니즘입니다. `react`를 peer dependency로 선언하면, 호스트 애플리케이션이 설치한 단 하나의 `react` 인스턴스를 공유하도록 강제합니다.

반면 `scheduler`는 일반 dependency로 선언해도 괜찮습니다. scheduler는 독립적인 태스크 큐를 관리하며, 여러 인스턴스가 존재해도 비효율적일 수는 있지만 논리적 오류가 발생하지 않습니다. **싱글톤이 필수인 것과 단순히 선호되는 것의 차이**가 peer dependency와 일반 dependency의 선택 기준입니다.

이 싱글톤 요구사항은 `npm link`를 사용한 로컬 패키지 개발, 모노레포 환경에서의 잘못된 hoisting, 마이크로 프론트엔드처럼 독립적으로 빌드된 앱들을 조합할 때 자주 깨집니다. 해결책은 항상 동일합니다. 애플리케이션 전체에서 단 하나의 `react` 인스턴스만 존재하도록 보장하는 것입니다.

## 2015년의 결정: react와 react-dom의 분리가 담고 있는 철학

2013년 JSConf US에서 React가 처음 공개되었을 때, 모든 것이 하나의 `react` 패키지 안에 있었습니다. 컴포넌트 모델, 재조정 알고리즘, DOM 렌더링이 한 곳에 뒤섞여 있었습니다. 당시에는 합리적이었습니다. React는 브라우저 DOM을 위한 라이브러리였으니까요.

결정적 전환점은 2015년 v0.14에서 찾아왔습니다. React Native의 등장이 "React의 핵심은 DOM이 아니다"라는 깨달음을 구체화했습니다. React의 컴포넌트 모델과 선언적 프로그래밍 패러다임이 모바일 네이티브 UI에도 적용될 수 있다는 것이 증명되면서, `react`와 `react-dom`의 분리가 이루어졌습니다.

이 분리는 단순히 코드를 두 npm 패키지로 나눈 것이 아니라 React의 정체성에 대한 근본적인 재정의였습니다.

`react` 패키지에 남은 것들을 살펴보면 패턴이 보입니다. 컴포넌트 정의, JSX 런타임, Hooks API, createContext, Suspense. 이 모든 것이 **선언(declaration)**입니다. "이런 UI가 되어야 한다"는 의도의 표현이지, 실제로 화면에 무언가를 그리는 코드는 한 줄도 없습니다. `react` 패키지만으로는 화면에 아무것도 나타나지 않습니다.

반면 `react-dom`에 있는 것들은 실제 DOM 요소의 생성·수정·삭제, 브라우저 이벤트의 캡처와 위임, SSR을 위한 HTML 문자열 생성, 서버 HTML과 클라이언트 상태를 연결하는 하이드레이션입니다. 모두 브라우저라는 특정 플랫폼에서 실제로 일을 하는 **실행(execution)** 코드입니다.

이 분리 덕분에 `react` 패키지의 API로 작성된 컴포넌트는 어떤 렌더러와도 결합할 수 있습니다. 동일한 `useState`, 동일한 `useEffect`가 브라우저에서도, iOS에서도, 터미널에서도 작동합니다. 렌더러만 교체하면 됩니다.

## 네 가지 질문으로 보는 패키지 구조

React의 패키지 구조를 가장 명확하게 이해하는 방법은 각 패키지가 답하는 **질문**이 다르다는 것을 인식하는 것입니다.

`react` 패키지는 **"무엇을 그릴 것인가(WHAT)"**에 답합니다. 개발자가 JSX로 작성한 선언이 자료구조로 변환되는 곳입니다. 이 단계에서는 실제 렌더링이 일어나지 않습니다. 단지 "이런 버튼이 있어야 하고, 이런 색이어야 한다"는 의도가 트리 형태의 자료구조로 표현될 뿐입니다.

`react-reconciler`는 **"어떻게 변화를 계산할 것인가(HOW)"**에 답합니다. 이전 트리와 새 트리를 비교해서 최소한의 변경 사항을 계산하고, 실제 렌더링 엔진이 수행해야 할 작업 목록을 구성합니다.

`scheduler`는 **"언제 업데이트할 것인가(WHEN)"**에 답합니다. 계산된 변경 사항을 즉시 실행할지, 아니면 브라우저가 현재 프레임을 그리고 난 뒤로 미룰지를 우선순위에 따라 결정합니다.

`react-dom`을 비롯한 각 렌더러는 **"어디에 그릴 것인가(WHERE)"**에 답합니다. 플랫폼별 실제 렌더링이 이루어지는 곳입니다.

이 분리는 Edsger Dijkstra가 1974년에 제시한 관심사 분리 원칙의 정수입니다. 각 관심사를 격리하면 한 부분의 변경이 다른 부분에 미치는 영향을 최소화할 수 있습니다.

### Stack에서 Fiber로: 분리의 촉매

그런데 React가 처음부터 이렇게 깔끔하게 분리되어 있었던 것은 아닙니다. 2013년부터 2017년까지 React의 재조정 엔진은 "Stack Reconciler"였습니다. 이름 그대로 콜 스택 기반으로 동작했으며, 한번 렌더링이 시작되면 중간에 멈출 수 없었습니다. 컴포넌트 트리가 깊으면 메인 스레드가 오랫동안 블로킹되어 사용자 입력이 지연되는 문제가 있었습니다.

이 문제를 해결하려면 "재조정 알고리즘"과 "실행 타이밍"을 분리해야 했습니다. 그러나 Stack Reconciler는 두 관심사가 뒤섞여 있었기 때문에 물리적 분리가 불가능했습니다.

2017년 Fiber 아키텍처의 등장이 이 분리를 가능하게 한 구조적 혁신이었습니다. Fiber는 재조정 작업을 **중단 가능한 단위(unit of work)**로 쪼개는 자료구조입니다. 각 컴포넌트에 해당하는 Fiber 노드가 하나의 작업 단위이며, 스케줄러는 이 작업 단위들을 우선순위에 따라 실행하거나 중단할 수 있습니다. "어떻게 변화를 계산하는가"와 "그 계산을 언제 수행하는가"가 비로소 물리적으로 분리되었고, 이것이 `scheduler` 패키지가 독립적으로 존재하는 이유입니다.

`scheduler`는 5단계 우선순위 시스템을 구현합니다. 즉시 실행해야 하는 작업부터 사용자 입력 처리, 일반 상태 업데이트, 지연 가능한 업데이트, 그리고 브라우저가 완전히 유휴 상태일 때만 실행되는 작업까지입니다. `startTransition`으로 감싼 업데이트가 낮은 우선순위로 처리되어 사용자 클릭 같은 중요한 작업에 양보할 수 있는 것은, 스케줄링이 재조정과 물리적으로 분리되어 있기 때문에 가능한 일입니다.

## react-reconciler: 세상에서 가장 유연한 렌더링 프레임워크

`react-reconciler`는 React 아키텍처에서 가장 흥미로운 패키지입니다. Fiber 기반 재조정 알고리즘의 전체 구현을 담고 있지만, 특정 플랫폼에 대해서는 아무것도 모릅니다. DOM이 무엇인지, Native View가 무엇인지, Canvas가 무엇인지 모릅니다.

대신 **HostConfig**라는 인터페이스를 정의합니다. 약 60개의 메서드로 구성된 이 계약서는 "인스턴스를 어떻게 만드는가", "자식 노드를 어떻게 추가하는가", "노드를 어떻게 삭제하는가", "변경 사항을 어떻게 반영하는가" 같은 질문에 대한 답을 각 렌더러가 직접 구현하도록 요구합니다.

이것은 **의존성 역전 원칙(Dependency Inversion Principle)**의 교과서적 구현입니다. 상위 모듈인 reconciler가 하위 모듈인 각 렌더러에 직접 의존하는 대신, 둘 다 HostConfig라는 추상화에 의존합니다. reconciler는 HostConfig가 어떻게 구현되는지 모르고, 렌더러는 reconciler의 내부 알고리즘을 모릅니다. 둘 사이의 계약만 안정적으로 유지되면 독립적으로 진화할 수 있습니다.

핵심적인 HostConfig 메서드를 살펴보면 패턴이 보입니다.

```javascript
// react-dom의 구현 (단순화)
createInstance(type, props) {
  return document.createElement(type);
}
appendChild(parent, child) {
  parent.appendChild(child);
}
```

이 코드에서 핵심은 `createInstance`가 반환하는 것이 DOM 요소라는 점이 reconciler에게는 완전히 불투명하다는 것입니다. reconciler는 그저 "createInstance가 반환한 불투명한 핸들"을 들고 다니며 appendChild, removeChild 같은 다른 HostConfig 메서드에 전달할 뿐입니다. 이 핸들이 실제로 무엇인지는 아무 상관이 없습니다.

이 아키텍처의 진가는 커뮤니티가 만들어낸 커스텀 렌더러들이 증명합니다. `react-three-fiber`는 React로 Three.js 3D 씬을 선언적으로 구성합니다. `ink`는 터미널에서 React 컴포넌트를 렌더링하여 CLI 도구의 UI를 `useState`와 `useEffect`로 구축할 수 있게 합니다. `react-pdf`는 PDF 문서를, `react-konva`는 HTML5 Canvas 그래픽을 React 방식으로 다룹니다.

이 모든 프로젝트가 가능한 이유는 단 하나입니다. Fiber 기반 재조정, Hook 시스템, Suspense, Concurrent Features 같은 React의 핵심 기능을 각 렌더러가 공짜로 얻기 때문입니다. 렌더러 개발자는 "내 플랫폼에서 인스턴스를 어떻게 만들 것인가"만 답하면 되고, "컴포넌트 트리의 변경을 어떻게 효율적으로 계산할 것인가"는 reconciler가 처리합니다.

`react-reconciler`를 별도 패키지로 분리한 것은 React를 단순한 UI 라이브러리에서 **선언적 UI 프로그래밍을 위한 플러그인 프레임워크**로 격상시킨 결정입니다.

## Feature Flags: Meta 규모에서 코드를 운영하는 법

React를 사용하는 곳은 개인 사이드 프로젝트부터 Meta의 Facebook, Instagram, WhatsApp까지 다양합니다. 새로운 기능을 추가하거나 레거시 코드를 제거할 때, 모든 사용자에게 동시에 적용하는 것은 불가능에 가깝습니다. Meta 내부에서는 수만 개의 컴포넌트가 React에 의존하고 있어, 하나의 breaking change가 예측할 수 없는 범위로 전파될 수 있습니다.

React는 이 문제를 **Feature Flag 시스템**으로 해결합니다. `ReactFeatureFlags.js`라는 파일과 그 포크들이 배포 환경별로 존재합니다. OSS 안정 버전, Meta 내부(facebook.com), React Native OSS, 테스트 렌더러 등 각 환경에 맞는 플래그 파일이 있으며, 동일한 플래그가 환경에 따라 다른 값을 가집니다.

이 시스템은 세 가지 중요한 용도를 가집니다.

### 점진적 마이그레이션

React 역사에서 레거시 Context API에서 `createContext`로의 전환은 수년에 걸쳐 진행되었습니다. 그 동안 두 API가 공존해야 했고, 개발자들이 마이그레이션할 수 있도록 충분한 시간을 주어야 했습니다.

Feature flag는 이 과정을 단계적으로 관리할 수 있게 합니다. 새 API를 플래그 뒤에 숨긴 상태로 실험하고, 마이그레이션 도구를 제공하고, 레거시 API에 경고를 추가하고, 레거시 코드를 플래그로 분기한 뒤, 최종적으로 플래그를 제거하며 레거시 코드를 삭제합니다. Michael Feathers가 설명한 Strangler Fig 패턴과 정확히 일치합니다. 새로운 코드가 오래된 코드를 점진적으로 감싸며 교체하고, 최종적으로 오래된 코드는 제거됩니다.

### 실험적 기능의 격리

`npm install react@experimental`로 설치한 버전은 `react@latest`와 다른 기능이 활성화됩니다. 그런데 이 두 버전은 완전히 다른 소스 코드로 만들어지는 것이 아닙니다. 동일한 소스 코드에서 feature flag의 값만 달리하여 빌드됩니다. 실험적 빌드에서 활성화된 기능이 안정 빌드에서는 비활성화된 상태로 코드 안에 잠들어 있습니다.

### Kill Switch: 즉각적 롤백

Meta 내부에서는 feature flag가 런타임에 동적으로 변경될 수 있는 구조를 가지고 있습니다. 새로운 기능이 프로덕션에서 문제를 일으키면, 코드를 재배포하지 않고도 플래그를 끄는 것만으로 즉각적인 롤백이 가능합니다. 이것이 React 팀이 Meta의 수십억 사용자를 대상으로 매주 새 버전을 배포할 수 있는 이유 중 하나입니다.

## 빌드 타임 최적화: 불필요한 코드를 0바이트로 만드는 방법

Feature flag의 진정한 위력은 빌드 시스템과 결합할 때 나타납니다. React의 빌드 파이프라인은 환경별 플래그 파일을 선택하고, Flow 타입을 제거하고, JSX를 변환한 뒤, **플래그를 리터럴 값으로 치환**합니다. 그 결과물에 Terser나 Closure Compiler의 Dead Code Elimination을 적용합니다.

`enableSchedulingProfiler`라는 플래그가 `false`로 설정된 환경에서는, 빌드 후 해당 플래그를 확인하는 `if` 블록이 `if (false)`로 치환되고, 이어진 Dead Code Elimination 단계에서 완전히 사라집니다. 관련 코드가 최종 번들에서 차지하는 용량은 0바이트입니다.

이 메커니즘은 `__DEV__`, `__EXPERIMENTAL__`, `__PROFILE__` 같은 빌드 타임 매크로에도 동일하게 적용됩니다. React 소스 코드 전체에는 수천 개의 `if (__DEV__)` 블록이 있습니다. 이 블록들 안에는 친절한 에러 메시지, prop 타입 검증, 렌더링 성능 경고 등 개발 경험을 위한 코드가 담겨 있습니다. 개발 환경에서는 이 모든 도구가 활성화되지만, 프로덕션 빌드에서는 완전히 제거됩니다. 그래서 React의 프로덕션 번들은 개발 번들보다 상당히 작습니다.

"모든 코드를 하나의 소스에서 관리하되, 배포 환경별로 다른 바이너리를 생성한다"는 전략입니다. 이것은 모노레포 구조와 완벽하게 맞물립니다. 하나의 저장소에서 관리하는 코드가 배포 시점에 환경에 맞게 최적화된 여러 버전으로 갈라지는 것입니다.

## React 19에서의 진화: 서버와 클라이언트의 경계가 공식화되다

React 19는 패키지 구조에 새로운 차원을 추가했습니다. 가장 큰 변화는 서버와 클라이언트의 경계가 패키지 수준에서 공식화된 것입니다.

`react-dom/server`는 이제 Node.js의 스트림 API를 사용하는 `renderToPipeableStream`과 Web Streams API를 사용하는 `renderToReadableStream`으로 갈라집니다. 이 분리는 서버 환경의 다양화를 반영합니다. Node.js뿐 아니라 Cloudflare Workers, Deno, Vercel Edge Runtime 같은 Edge 환경에서도 SSR이 가능해야 하기 때문에, 각 환경이 지원하는 스트림 API에 맞는 진입점이 필요해진 것입니다.

React Server Components(RSC)는 번들러와의 통합이 필수적이기 때문에 `react-server-dom-webpack`, `react-server-dom-turbopack` 같은 번들러별 패키지가 별도로 존재합니다. 서버에서 렌더링된 컴포넌트 트리를 클라이언트로 스트리밍할 때, "이 부분은 클라이언트 컴포넌트이다"라는 참조를 번들러의 모듈 시스템으로 해석해야 하기 때문입니다.

React 19에서 도입된 또 다른 중요한 변화는 `package.json`의 `exports` 필드에 `react-server`라는 내보내기 조건이 추가된 것입니다. `react-server` 조건으로 해석된 빌드에서는 `useState`, `useEffect`, `useReducer` 같은 클라이언트 전용 API가 아예 존재하지 않습니다. 서버 컴포넌트에서 이런 API를 사용하려고 하면 모듈 가져오기 자체가 실패합니다.

이것은 런타임 에러가 아닌 **빌드 타임 에러**로 잘못된 사용을 잡아내는 전략입니다. "useState is not a function"이라는 혼란스러운 에러 대신, "useState is not exported from 'react'"라는 명확한 에러 메시지로 문제의 원인을 즉시 파악할 수 있습니다.

## 변하는 것과 변하지 않는 것: 패키지 경계라는 방화벽

지금까지 살펴본 React의 패키지 구조를 관통하는 하나의 원칙이 있습니다. David Parnas가 1972년 논문에서 제시한 **정보 은닉(Information Hiding)** 원칙입니다. "변경될 가능성이 있는 설계 결정을 모듈 경계 뒤에 숨겨라"는 것입니다.

`react` 패키지는 변하지 않는 것을 담습니다. 선언적 UI 모델, 컴포넌트 추상화, Hook의 의미론. `react-reconciler`는 변하는 것을 담습니다. Stack에서 Fiber로, 그리고 미래의 무언가로 진화하는 재조정 알고리즘의 세부 구현. `scheduler`는 스케줄링 전략을, `react-dom`은 브라우저 API와 DOM 표준의 진화를 흡수합니다.

React의 공개 API인 `useState`, `useEffect`, JSX는 놀라울 정도로 안정적입니다. 2019년에 도입된 Hook API는 2026년 현재까지 거의 변하지 않았습니다. 반면 내부 구현은 매년 상당한 변화를 겪고 있습니다. Lane 모델의 도입, Suspense의 진화, Server Components의 추가. 이 모든 내부 변화가 사용자 코드를 깨뜨리지 않는 이유는, 변하는 것과 변하지 않는 것이 패키지 경계로 명확하게 분리되어 있기 때문입니다.

이것은 우연이 아닙니다. 의도적인 설계의 결과이며, 패키지 구조가 이 설계를 물리적으로 강제합니다.

## 설계 결정들은 서로를 보강한다

이 글에서 살펴본 설계 결정들을 정리하면 다섯 가지 원칙으로 수렴합니다.

첫째, **What/How/When/Where 분리**. 각 패키지가 하나의 질문에만 답합니다. `react`는 무엇을, `react-reconciler`는 어떻게, `scheduler`는 언제, 각 렌더러는 어디에.

둘째, **의존성 역전**. reconciler가 렌더러에 의존하지 않고, 둘 다 HostConfig 인터페이스에 의존합니다. 이 덕분에 커뮤니티가 react-three-fiber, ink 같은 완전히 새로운 렌더러를 만들 수 있습니다.

셋째, **공통 폐쇄 원칙**. 함께 변경되는 코드가 모노레포 안에서 원자적으로 관리됩니다. 내부 계약의 불일치로 인한 런타임 에러가 구조적으로 방지됩니다.

넷째, **정보 은닉**. 내부 구현의 변경이 공개 API에 전파되지 않도록 패키지 경계가 방화벽 역할을 합니다. 사용자 코드는 `react` 패키지의 안정적인 API에만 의존하고, 그 뒤에서 일어나는 변화는 알 필요가 없습니다.

다섯째, **점진적 배포**. Feature flag가 환경별로 다른 기능 세트를 활성화하고, 빌드 시스템이 불필요한 코드를 제거합니다. 실험은 공격적으로 하되, 실패의 폭발 반경을 최소화합니다.

이것들은 독립적인 결정이 아닙니다. 서로를 보강하는 일관된 아키텍처 전략의 표현입니다. 모노레포이기 때문에 원자적 변경이 가능하고, 원자적 변경이 가능하기 때문에 내부 계약을 자유롭게 진화시킬 수 있으며, 내부 계약이 자유롭게 진화하기 때문에 Feature flag를 통한 점진적 마이그레이션이 가능합니다. 그리고 이 모든 것의 기반에 HostConfig 인터페이스가 있어, React를 특정 플랫폼에 묶이지 않는 범용 선언적 UI 프레임워크로 만들어 줍니다.

`npm install react react-dom`이라는 평범한 명령어 뒤에는 이토록 많은 결정이 숨어 있습니다.

## 한눈에 보기

React Router 7과 RSC를 함께 운영할 때 진짜 난이도는 fetch 위치를 고르는 문제가 아닙니다. 장애가 났을 때 누가 어떤 순서로 복구할지를 미리 정해두는 문제입니다. 이 기준이 없으면 기능은 돌아가는데 운영이 흔들립니다. 사용자 입장에서는 “저장했는데 화면이 예전 상태입니다”, “페이지 이동 때마다 일부만 갱신됩니다”, “가끔 새로고침해야 맞습니다”처럼 보입니다. 그래서 React Router 7 + RSC 실무 운영에서는 성능 미세 최적화보다 책임 경계 합의가 먼저입니다.

실무에서 먼저 고정해야 할 원칙은 네 가지입니다.

- 리소스별 **read owner**를 하나만 둡니다.
- 쓰기의 기준점은 **action**으로 통일합니다.
- **revalidation trigger**를 이벤트 단위로 문서화합니다.
- 데이터 소유 경계와 에러 경계를 같은 단위로 맞춥니다.

이 네 가지를 먼저 합의하면 도입 속도는 약간 느려질 수 있습니다. 대신 릴리즈 이후의 예측 가능성이 크게 올라갑니다. RR7 + RSC 조합은 기능 데모 단계보다 운영 단계에서 성패가 갈리기 때문입니다.

---

## 들어가며

RR7 + RSC를 처음 도입하면 대부분 “서버에서 더 효율적으로 조합하자”, “클라이언트 번들을 줄이자”, “전환 체감을 개선하자”라는 기대를 갖습니다. 모두 맞는 기대입니다. 다만 실무에서는 이 기대를 바로 구현하려고 할수록 책임 경계가 흐려지기 쉽습니다. 특히 React Router 7 + RSC 실무 운영 단계로 넘어가면, 기능 구현 난이도보다 운영 계약의 완성도가 더 크게 성패를 좌우합니다.

기존 Remix 계열 사고에 익숙한 팀은 loader/action 중심 규칙이 이미 몸에 배어 있습니다. 여기에 RSC가 들어오면 데이터 경로가 하나 추가되는 수준이 아니라 설계 질문의 순서가 바뀝니다. 과거에는 “어디서 읽을까”가 첫 질문이었다면, 이제는 “틀렸을 때 누가 복구할까”가 첫 질문이어야 합니다.

이 순서가 중요한 이유는 단순합니다.

첫째, 복잡도는 경로 개수보다 경계 상호작용에서 커지기 때문입니다. loader와 RSC가 각각 잘 동작해도 action 이후 반영 순서가 불명확하면 결과는 랜덤에 가깝게 보입니다.

둘째, 사용자 신뢰는 속도보다 일관성에서 만들어지기 때문입니다. 저장 직후 한 번이라도 오래된 값이 보이면 사용자는 50ms 개선보다 그 불일치를 더 오래 기억합니다.

셋째, 팀 규모가 커질수록 코드 미학보다 운영 계약의 명확성이 중요해지기 때문입니다. 여러 팀이 동시에 배포하는 환경에서는 “누가 소유하고 누가 복구하는지”가 문서화되지 않으면 회귀 버그가 구조적으로 반복됩니다.

그래서 이 글은 API 소개보다 책임 분리를 중심으로 정리합니다. 결론은 단순합니다. RR7과 RSC는 경쟁 기술이 아니라 분업 체계입니다. 문제는 둘 중 무엇을 선택하느냐가 아니라, 어떤 실패를 어느 경계에서 감당할지를 명확히 선언하느냐입니다.

## 본문

### 1) 문제: 왜 RR7 + RSC에서 장애가 "가끔"처럼 보이는가

초기 도입 팀에서 가장 자주 나오는 피드백은 “재현이 어렵다”입니다. 로컬에서는 잘 되는데 스테이징에서 간헐적으로 어긋나고, 사용자는 저장 성공 토스트를 봤는데 목록은 예전 값인 상황이 생깁니다. 기술적으로는 대부분 같은 뿌리입니다.

- 같은 리소스를 loader와 RSC가 동시에 읽습니다.
- action 성공 이후 어떤 경로를 재검증할지 팀마다 다르게 구현됩니다.
- fallback은 상위 경계에서 크게 잡고, 실제 소유 경계는 불분명합니다.

이 세 가지가 결합되면 장애는 “항상 실패”가 아니라 “가끔 틀림”으로 나타납니다. 이 형태가 더 위험합니다. 100번 중 1번만 틀려도 사용자 신뢰는 빠르게 떨어지고, 개발팀은 재현 비용을 계속 지불하게 됩니다.

### 2) 원인: 데이터 위치 중심 의사결정의 한계

실무에서 의사결정이 흔히 이렇게 시작됩니다.

- “이 화면은 서버 조합이 많으니 RSC로 갑시다.”
- “여긴 기존 loader가 안정적이니 유지합시다.”

이 접근은 단기적으로 빠릅니다. 하지만 시간이 지나면 동일 리소스가 서로 다른 경로에서 중복 조회되고, stale 타이밍이 엇갈리며, 에러 복구 지점이 달라집니다. 즉, 화면 단위 최적화는 잘되는데 시스템 단위 일관성이 무너집니다.

핵심 원인은 “지금 빨리 만들 수 있는가”를 최적화하고 “변경이 누적될 때 책임이 유지되는가”를 검증하지 않기 때문입니다. RR7 + RSC 조합에서 중요한 것은 fetch 기술보다 계약 유지력입니다.

### 3) 원리: 책임을 분리하는 기준은 기술 취향이 아니라 실패 반경입니다

운영 가능한 구조는 아래처럼 역할을 분리할 때 만들어집니다.

- **RSC**: 서버 계산 효율, 데이터 조합 품질, 초기 전달 품질을 담당합니다.
- **loader**: 라우트 전환 단위의 읽기 책임과 경계 정렬을 담당합니다.
- **action**: 쓰기 이벤트의 기준점과 후속 revalidation 규칙을 담당합니다.

이 원리의 핵심은 “어디가 더 멋진가”가 아니라 “실패했을 때 반경을 어디까지 제한할 수 있는가”입니다. 예를 들어 라우트 파라미터 변화에 즉시 반응해야 하고 복구 UI가 경계별로 달라야 한다면 loader가 안전합니다. 반대로 서버에서 합쳐야 의미가 커지는 데이터라면 RSC가 맞습니다.

### 4) 운영: 리소스별 소유권 표를 먼저 만들면 구현이 쉬워집니다

아래 표는 실무에서 바로 쓰기 좋은 최소 템플릿입니다.

| 리소스 | Read Owner | Write Owner | Revalidation Owner | Fallback Owner |
|---|---|---|---|---|
| 사용자 프로필 요약 | loader | action | route module | profile route boundary |
| 추천 피드 조합 데이터 | RSC | action | server contract + route trigger | feed segment boundary |
| 계정 설정 폼 데이터 | loader | action | action contract | settings route boundary |

이 표의 목적은 상세 설계 문서를 늘리는 것이 아닙니다. 배포 중 장애가 났을 때 책임 경로를 30초 내로 재구성할 수 있게 만드는 것입니다. 특히 MFE 구조에서는 이 표 하나가 팀 간 경계 충돌을 크게 줄여줍니다.

### 5) action을 "폼 제출 함수"가 아니라 "상태 전환 계약"으로 다뤄야 하는 이유

action은 단순히 write API를 감싸는 함수가 아닙니다. 시스템 상태가 바뀌는 공식 이벤트입니다. 따라서 action에는 성공/실패 이후 규칙이 반드시 붙어야 합니다.

- 성공 시: 어디로 redirect할지
- 성공 시: 어떤 읽기 경계를 재검증할지
- 실패 시: 어떤 boundary에서 어떤 복구 행동을 제공할지

이 계약이 없으면 같은 write 이후에도 화면 반영 방식이 모듈마다 달라집니다. 결국 사용자 입장에서는 “어떤 화면에서는 바로 바뀌고, 어떤 화면에서는 늦게 바뀌는” 비일관성이 쌓입니다.

아래는 최소 패턴입니다.

```ts
export async function action({ request }) {
const formData = await request.formData();
const result = await updateProfile(formData);

if (!result.ok) {
return { ok: false, reason: "validation" };
}

return redirect("/settings/profile?updated=1");
}

export async function loader({ params }) {
return getProfileByRoute(params.userId);
}
```

코드가 핵심이 아니라 계약이 핵심입니다. 같은 도메인을 RSC가 추가 조합하더라도 라우트 핵심 데이터의 소유권을 어디에 둘지 먼저 확정해야 합니다.

### 6) 에러 경계는 "크게"가 아니라 "맞게" 잡아야 합니다

혼합 구조에서 흔한 실수는 에러를 상위에서 한 번에 처리하는 것입니다. 구현은 쉬워 보이지만 실패 반경이 커집니다. 작은 데이터 문제도 페이지 전체 실패로 확장되기 쉽습니다.

실무 원칙은 단순합니다.

- 데이터를 소유한 경계가 fallback을 소유합니다.
- fallback에는 사용자가 즉시 취할 행동(재시도, 이전 화면 복귀, 입력 유지)이 있어야 합니다.
- 경계가 다르면 관측 지표도 분리합니다.

이렇게 하면 장애의 표면적이 줄고, 회고에서 학습이 남습니다. 반대로 소유권 없는 상위 fallback은 매번 임시 패치만 늘립니다.

### 7) 관측성은 디버깅을 위한 로그가 아니라 계약 준수 검사입니다

RR7 + RSC 환경에서 로그는 “에러를 봤다”를 넘어서 “계약이 지켜졌는가”를 확인해야 의미가 있습니다. 최소 필드는 아래를 권장합니다.

- routeId
- sourceType(RSC/loader/action)
- revalidationReason
- boundaryId
- traceId(request correlation)

이 다섯 가지가 있으면 장애 시나리오를 역추적하기 쉬워집니다. 특히 “write는 성공했는데 read 반영이 늦은” 유형에서 원인 분리가 빨라집니다. 반대로 이 정보가 없으면 사람 경험에 의존한 추정 디버깅이 반복됩니다.

### 8) 점진 마이그레이션: 기능 전환보다 책임 전환을 먼저 해야 합니다

v6/Remix 계열에서 RR7 + RSC로 넘어갈 때, 핵심 화면을 통째로 바꾸는 방식은 위험합니다. 성공하면 화려하지만 실패하면 롤백 반경이 큽니다. 안전한 순서는 다음과 같습니다.

1. 기존 loader/action 흐름을 리소스 단위로 인벤토리화합니다.
2. 중복 조회가 있는 리소스를 먼저 표시합니다.
3. 읽기 전용이며 서버 조합 이점이 큰 영역부터 RSC로 이동합니다.
4. action 성공/실패 후 revalidation 규칙을 문서화합니다.
5. boundary 단위 로딩/에러 복구를 계약 테스트로 검증합니다.

이 순서의 장점은 기술 리스크보다 조직 리스크를 먼저 줄인다는 점입니다. 팀이 바뀌고 코드가 바뀌어도 계약이 유지되면 시스템은 안정적으로 진화합니다.

## 트레이드오프

아래는 RR7 + RSC 운영에서 자주 맞닥뜨리는 선택지를 실무 관점으로 정리한 것입니다.

| 선택 | 얻는 것 | 잃는 것 | 언제 적합한가 |
|---|---|---|---|
| RSC 비중 확대 | 서버 조합 효율, 초기 전달 품질, 번들 경량화 | 라우터 밖 읽기 경로 증가, 재검증 정책 복잡도 | 조합 로직이 무겁고 읽기 중심 화면이 많은 경우 |
| loader 중심 유지 | 라우트 전환 예측 가능성, 디버깅 단순성 | 서버 조합 효율 한계, 초기 전달 최적화 여지 축소 | 경계별 복구와 운영 안정성이 최우선인 경우 |
| 중복 fetch 허용 | 단기 개발 속도 | stale 불일치, 요청량 증가, 장애 분석 비용 급증 | 프로토타입 단계에서만 제한적으로 허용 |
| action 계약 엄격화 | write 이후 일관성, 회귀 방지 | 초기에 문서/체크리스트 비용 | 다팀 병렬 배포, 데이터 일관성 민감 도메인 |

표를 실제 운영으로 바꾸려면 다음 세 가지를 체크리스트로 고정하면 됩니다.

- 신규 PR에서 동일 리소스 중복 조회를 허용할지 명시했는가
- action 이후 stale 정의와 revalidation 경로가 적혔는가
- 실패 시 사용자 복구 경로가 boundary 단위로 확인되었는가

이 체크리스트는 개발 속도를 늦추기 위한 장치가 아닙니다. 릴리즈 이후 반복되는 수정 비용을 줄이기 위한 최소 보험입니다.

## 마무리하며

RR7 + RSC 운영의 핵심은 최신 기능을 많이 쓰는 것이 아닙니다. 상태 전환의 책임을 선명하게 유지하는 것입니다. 기술적으로는 복합 스택이지만 운영 관점에서는 오히려 단순한 원칙으로 정리할 수 있습니다.

- 읽기 소유자는 리소스마다 하나입니다.
- 쓰기의 기준점은 action입니다.
- revalidation은 이벤트 계약으로 다룹니다.
- fallback은 데이터 소유 경계와 일치시킵니다.

이 네 가지가 지켜지면 팀은 속도와 안정성을 동시에 가져갈 수 있습니다. 반대로 하나라도 빠지면 성능 이점은 있어도 운영 혼란이 빠르게 커집니다. 결국 사용자에게 중요한 것은 “빠른 화면”보다 “항상 맞는 화면”입니다.

오늘 바로 적용할 수 있는 시작점은 거창한 리팩터링이 아닙니다. 리소스 소유권 표 하나, action 후 규칙 하나, boundary 정렬 원칙 하나를 팀 규약으로 만드는 것입니다. 이 작은 계약이 RR7 + RSC를 복잡한 실험에서 예측 가능한 운영 체계로 바꿉니다. 결국 React Router 7 + RSC 실무 운영의 본질은 신기술 채택이 아니라 책임의 일관성 유지이며, 이 일관성이 사용자 신뢰와 팀 생산성을 동시에 지켜줍니다.

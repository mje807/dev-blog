## 한눈에 보기

React Router 7과 RSC를 함께 쓰는 팀이 흔히 겪는 문제는 “무엇을 어디에서 fetch할까”가 아닙니다. 본질은 “실패했을 때 누가 책임지고 복구할까”입니다. 이 관점을 놓치면 초반에는 빨라 보이지만, 몇 주 뒤에는 중복 조회·재검증 누락·경계 불일치가 동시에 터집니다. 결국 사용자 경험은 “저장했는데 안 바뀜”, “이동하면 깜빡임”, “가끔 새로고침 필요” 같은 신뢰 하락으로 나타납니다.

이 글의 핵심 요지는 단순합니다.

- RSC는 **서버 계산 효율과 전달 품질**을 담당합니다.
- loader/action은 **라우트 전환 책임과 재검증 규칙**을 담당합니다.
- 둘은 대체 관계가 아니라 **분업 관계**입니다.
- 분업 기준은 기술 취향이 아니라 **실패 반경, 관측성, 운영 가능성**입니다.

실무에서 바로 적용하려면 아래 네 가지를 먼저 고정하는 것이 좋습니다.

1. 리소스별 read owner를 하나로 정합니다(RSC 또는 loader).
2. write owner는 action으로 고정합니다.
3. revalidation trigger를 문서로 선언합니다.
4. 데이터 소유 경계와 에러 경계를 같은 단위로 맞춥니다.

이 네 가지만 합의해도 팀 생산성과 장애 대응 속도는 눈에 띄게 달라집니다. 왜냐하면 성능 이슈는 튜닝으로 늦출 수 있어도, 책임 경계가 깨진 시스템은 시간이 갈수록 반드시 운영 비용이 폭증하기 때문입니다.

## 들어가며

React Router 7 + RSC를 도입할 때 팀이 처음 느끼는 감정은 대체로 비슷합니다. “이제 서버에서 더 똑똑하게 조합할 수 있겠다”, “클라이언트 번들을 줄일 수 있겠다”, “라우팅과 데이터 전략을 한 단계 올릴 수 있겠다” 같은 기대입니다. 이 기대는 틀리지 않습니다. 문제는 기대가 실현되는 조건이 생각보다 까다롭다는 점입니다.

특히 v6/Remix 계열 흐름에 익숙한 팀은 loader/action 중심의 사고가 이미 몸에 배어 있습니다. 여기에 RSC가 들어오면 데이터 경로가 하나 더 생기는 수준이 아니라, 설계의 기준축 자체가 흔들립니다. 과거에는 “라우트 진입 시 어떤 데이터를 가져오나”가 주 질문이었는데, 이제는 “이 데이터는 라우트 책임인가, 서버 조합 책임인가”를 먼저 물어야 합니다. 질문 순서가 바뀐 것입니다.

왜 이 순서가 중요할까요?

첫째, 데이터 흐름의 복잡도는 경로 수의 합이 아니라 **경계 간 상호작용**으로 증가하기 때문입니다.
loader와 RSC가 각각 잘 작동해도, action 이후 어떤 쪽이 먼저 반영되고 어느 경계에서 fallback 되는지 불분명하면 시스템은 곧 “가끔 틀리는 시스템”이 됩니다. 사용자는 100번 중 99번 성공해도 1번의 불일치를 더 강하게 기억합니다.

둘째, 성능 최적화보다 신뢰성 설계가 선행되어야 하기 때문입니다.
많은 팀이 RSC를 “더 빠른 렌더링”의 관점으로 먼저 도입합니다. 맞는 접근이지만, 실무에서는 빠름보다 먼저 **일관성**이 확보되어야 합니다. 저장 직후 화면이 일관되게 갱신되는 경험은 50ms 빠른 TTFB보다 체감 가치가 큽니다. “변경하면 바뀐다”는 신뢰가 깨지면 어떤 최적화도 사용자에게는 무의미해집니다.

셋째, 팀 구조와 릴리즈 속도는 기술 선택보다 훨씬 강력한 제약이기 때문입니다.
30명 규모, MFE 전환, 여러 팀 동시 배포 환경에서는 코드의 우아함보다 운영 규칙의 명확함이 성패를 가릅니다. 오늘은 A팀이 loader에서 가져오고, 내일 B팀이 같은 리소스를 RSC에서 조합하고, 모레 C팀이 action만 추가하면, 각자 로컬에서는 정상인데 통합 환경에서는 재현 불가 버그가 생깁니다. “누가 고칠지”부터 회의가 길어지는 구조입니다.

그래서 이 글은 API 기능 소개보다 **책임 설계의 이유**를 파고듭니다.
핵심 질문은 하나입니다.

> “이 데이터는 어디에서 가져오면 좋은가?”가 아니라
> “이 데이터가 틀렸을 때, 어느 경계가 책임지고 복구해야 하는가?”

이 질문으로 설계를 시작하면, 기술적 선택은 오히려 간단해집니다.

## 트레이드오프

### 1) “데이터 위치” 중심 설계의 함정 vs “전환 책임” 중심 설계의 이점

실무에서 가장 흔한 출발점은 “이 화면은 RSC가 더 맞아 보인다”, “이건 기존 loader 유지하자” 같은 위치 중심 의사결정입니다. 빠르게 시작하기엔 좋지만, 시간이 지나면 같은 리소스가 여러 경로로 복제됩니다.

왜 이런 일이 반복될까요?
위치 중심 설계는 “지금 이 화면을 빨리 만들 수 있는가”를 최적화하지만, “이후 변경이 누적될 때 책임이 유지되는가”를 검증하지 않기 때문입니다. 초기 생산성은 높아도 누적 변경 비용이 커집니다.

반대로 전환 책임 중심 설계는 시작이 조금 느립니다. 대신 다음이 명확해집니다.

- 라우트 전환이 바뀌면 누가 fetch를 책임지는가
- 쓰기 이후 어떤 데이터가 stale 되는가
- 실패 시 어느 경계에서 복구해야 하는가

즉, 단기 속도를 일부 포기하고 장기 예측 가능성을 얻는 선택입니다. 대규모 팀일수록 이 트레이드오프는 거의 항상 후자가 유리합니다.

---

### 2) RSC를 넓게 쓰는 전략의 장점과 비용

RSC를 넓게 적용하면 분명한 장점이 있습니다.

- 서버 근처에서 데이터 조합을 수행해 네트워크 왕복을 줄일 수 있습니다.
- 클라이언트 번들 부담을 낮춰 초기 체감 품질을 개선할 수 있습니다.
- SEO/초기 렌더 품질을 높이기 쉬워집니다.

하지만 왜 많은 팀이 중도에 흔들릴까요?
RSC 확장은 곧 **라우터 밖 데이터 경로 확대**를 의미하기 때문입니다. 읽기 경로가 분산되면 action 이후 재검증 규칙이 더 중요해지는데, 이 규칙을 문서화하지 않으면 “암묵적 최신화 기대”가 생깁니다. 그리고 암묵성은 장애의 다른 이름입니다.

따라서 RSC는 “많이 쓰는가”보다 “무엇을 맡기는가”가 중요합니다.
서버 조합 비용이 크고, 라우트 경계보다 콘텐츠 조합 품질이 우선인 읽기에는 RSC가 매우 강력합니다. 반면 라우트 파라미터 변경에 즉시 반응해야 하고, 경계 단위 에러 복구가 중요하면 loader가 더 안전합니다.

---

### 3) loader를 유지하는 전략의 안정성과 한계

loader 중심 전략은 팀이 이미 익숙하고 디버깅 포인트가 명확하다는 장점이 있습니다. route 단위 로딩/에러 경계와 자연스럽게 정렬되기 때문에 운영 관점에서 예측 가능성이 높습니다.

그런데 왜 loader만으로는 부족해질까요?
서버에서 조합해야 할 데이터가 커질수록, 그리고 클라이언트 번들 경량화 요구가 강해질수록, loader만으로는 “전환 안정성”은 확보해도 “전달 효율”에서 손해를 보기 쉽기 때문입니다. 즉, loader는 운영 안정성에 강하고, RSC는 전달 효율에 강합니다. 둘 중 하나만 고집하면 다른 축에서 비용을 치르게 됩니다.

---

### 4) action을 단순 API 호출로 취급할 때 생기는 구조적 문제

많은 팀에서 action은 “폼 제출용 엔드포인트”로만 다뤄집니다. 그런데 React Router 7 맥락에서 action의 더 중요한 역할은 **재검증의 기준점**입니다. 쓰기가 일어난 순간이야말로 데이터 일관성을 다시 맞출 유일한 공식 이벤트입니다.

왜 action을 중심축으로 봐야 할까요?

- 쓰기 성공/실패는 시스템 상태가 바뀌는 사건입니다.
- 상태 변화 사건에는 후속 규칙(redirect, revalidate, rollback)이 필요합니다.
- 규칙이 없으면 화면은 우연히 맞거나, 우연히 틀립니다.

결국 action은 “요청 처리 함수”가 아니라 “상태 전환 계약”입니다. 이 계약을 문서화하지 않으면 팀마다 후속 처리가 달라지고, 버그는 랜덤처럼 보이기 시작합니다.

---

### 5) 중복 fetch를 허용했을 때 얻는 단기 속도 vs 잃는 장기 신뢰

중복 fetch는 왜 이렇게 쉽게 발생할까요?
각 팀이 자신의 경계 안에서만 “빠르게 안전하게” 구현하면, 전체 관점에서는 같은 리소스를 두 번 읽는 구조가 자연스럽게 만들어지기 때문입니다.

단기적으로는 개발이 빠릅니다. 독립적으로 작업하면 되니까요.
하지만 장기적으로는 다음 비용이 누적됩니다.

- 요청량 증가와 캐시 정책 충돌
- stale 타이밍 불일치
- 장애 시 원인 추적 시간 증가
- 관측성 로그 해석 난이도 상승

즉, 중복 fetch는 기술 부채가 아니라 **운영 부채**입니다. 운영 부채는 트래픽 증가보다 팀 규모 증가에서 더 빠르게 폭발합니다.

---

### 6) “왜”를 기준으로 한 책임 분리 규칙

아래는 기능이 아니라 이유 중심의 규칙입니다.

**RSC에 두는 이유**
- 이 데이터는 서버에서 합쳐야 의미가 커지기 때문입니다.
- 클라이언트에 계산 책임을 넘기면 번들/지연 비용이 커지기 때문입니다.
- 초기 렌더 품질이 핵심 KPI이기 때문입니다.

**loader에 두는 이유**
- 이 데이터는 라우트 전환 이벤트와 강하게 결합되기 때문입니다.
- 실패 시 route boundary에서 복구해야 UX가 안정적이기 때문입니다.
- action 이후 재검증 경로를 라우터 정책으로 통제해야 하기 때문입니다.

**action에 두는 이유**
- 쓰기 작업은 사용자 의도의 원천 이벤트이기 때문입니다.
- 시스템 일관성을 다시 맞출 기준점이 필요하기 때문입니다.
- 성공/실패 후 분기 정책이 명시되어야 예측 가능한 UX가 되기 때문입니다.

이 규칙의 장점은 코드 스타일과 무관하다는 점입니다. 팀이 바뀌어도 유지됩니다.

---

### 7) 에러 경계: “어디서 잡을까”가 아니라 “누가 소유하나”

RSC/loader/action 혼합 구조에서 가장 위험한 오해는 “에러는 일단 상위에서 크게 잡자”입니다. 단기적으로는 구현이 쉬워 보이지만, 실제로는 작은 실패를 전체 다운으로 확장시킵니다.

왜 소유권 정렬이 중요한가요?

- 에러 메시지의 정확도는 소유권과 비례합니다.
- 복구 액션의 품질은 데이터 맥락에 좌우됩니다.
- 책임이 분산되면 장애 회고에서 학습이 남지 않습니다.

따라서 원칙은 간단합니다.
**데이터를 소유한 경계가 fallback까지 소유합니다.**
이 원칙만 지켜도 “문제는 보이는데 고칠 팀이 없다”는 상황이 크게 줄어듭니다.

---

### 8) 관측성: 로그를 남기는 이유는 디버깅이 아니라 계약 검증

실무에서 로그는 종종 사후 디버깅 도구로만 취급됩니다. 그러나 RR7 + RSC 조합에서는 로그가 “계약이 지켜졌는지”를 검증하는 수단입니다.

최소한 아래 필드는 반드시 남겨야 합니다.

- route id
- source type(RSC/loader/action)
- revalidation reason
- boundary id
- 요청 상관관계 식별자(trace/request id)

왜냐하면 장애의 질문이 달라지기 때문입니다.
“에러가 났다”가 아니라 “계약된 경계에서 계약된 재검증이 수행되었는가”를 확인해야 합니다. 이 관점이 없으면 문제를 감으로 추정하게 되고, 동일 장애가 반복됩니다.

---

### 9) 운영 모델: 코드보다 먼저 합의해야 할 것들

대규모 팀에서 아키텍처는 코드가 아니라 규칙으로 유지됩니다. 아래 세 가지가 없으면 설계는 문서에서만 존재합니다.

1. **소유권 명세서**
리소스별 read owner, write owner, revalidation owner, fallback owner를 한 줄로 고정합니다.

2. **PR 체크리스트 강제**
- 동일 리소스 중복 조회 여부
- action 이후 stale 정의 여부
- 실패 시 사용자 복구 경로 유무

3. **회고 템플릿 표준화**
장애 발생 시 “어느 계약이 비어 있었는가”를 기록합니다.
사람 실수보다 계약 누락을 먼저 찾는 문화가 중요합니다.

왜 이렇게 운영 중심으로 가야 할까요?
기술 선택은 한번에 끝나지 않기 때문입니다. 팀이 커질수록, 새 인원이 합류할수록, 도메인이 분할될수록 아키텍처는 반복적으로 재해석됩니다. 재해석 비용을 줄이는 유일한 방법은 규칙을 시스템화하는 것입니다.

---

### 10) 점진 마이그레이션: 한 번에 옮기지 않는 이유

v6/Remix에서 RR7 + RSC로 갈 때 가장 위험한 전략은 “핵심 화면을 통째로 새 방식으로 갈아타기”입니다. 성공하면 화려하지만 실패하면 복구 비용이 큽니다.

안전한 순서는 다음과 같습니다.

1. 기존 loader/action 흐름을 인벤토리화합니다.
2. 중복 조회가 발생하는 리소스를 먼저 표시합니다.
3. 읽기 전용이면서 서버 조합 비용이 큰 화면부터 RSC로 옮깁니다.
4. action 성공/실패 후 revalidation 정책을 명시적으로 고정합니다.
5. route boundary별 로딩/에러 fallback을 계약 테스트로 검증합니다.

왜 이 순서가 유효할까요?
기능 전환이 아니라 **책임 전환**을 단계적으로 수행하기 때문입니다. 단계별로 “누가 소유하는가”를 확인하면, 기술 리스크보다 조직 리스크를 줄일 수 있습니다.

---

### 11) 실무에서 바로 쓸 수 있는 최소 패턴

아래는 코드보다 책임 흐름을 보여주는 최소 예시입니다.

```ts
// action: 쓰기와 후속 정책의 기준점
export async function action({ request }) {
const form = await request.formData();
const result = await updateProfile(form);

if (!result.ok) return { ok: false, reason: "validation" };
return redirect("/settings/profile?updated=1");
}
```

```ts
// loader: 라우트 전환 책임 데이터
export async function loader({ params }) {
return getRouteBoundProfile(params.userId);
}
```

핵심은 구현 난이도가 아니라 계약의 명확성입니다.
RSC가 같은 도메인의 추가 조합 데이터를 읽더라도, “라우트 전환 핵심 데이터는 loader가 소유한다” 혹은 반대로 “도메인 읽기 소유자는 RSC다”를 먼저 고정해야 합니다. 코드 자체보다 소유권 선언이 선행되어야 합니다.

---

### 12) 자주 묻는 질문: “그럼 무엇이 정답인가”

정답은 하나의 기술이 아닙니다. 정답은 **일관된 경계**입니다.
RSC를 많이 써도 되고, loader를 넓게 유지해도 됩니다. 다만 아래 질문에 팀이 같은 답을 해야 합니다.

- 이 리소스의 read owner는 누구인가?
- write 이후 누가 stale을 선언하고 누가 재검증하는가?
- 실패 시 사용자는 어디서 무엇을 할 수 있는가?
- 장애가 나면 어떤 로그로 경로를 재구성할 수 있는가?

이 질문에 즉시 답하지 못하면, 현재 구조는 기능은 돌아가도 운영은 불안정한 상태입니다.

---

## 마무리하며

React Router 7 + RSC 조합은 단순한 신기능 도입이 아닙니다. 데이터 아키텍처의 철학을 바꾸는 일입니다. 과거에는 “페이지가 뜨는가”가 중심이었다면, 이제는 “상태 전환이 신뢰 가능하게 유지되는가”가 중심입니다.

왜 이 변화가 중요한가요?
사용자 경험의 핵심이 점점 “반응성”에서 “일관성”으로 이동하고 있기 때문입니다. 빠른 화면은 인상적이지만, 믿을 수 있는 화면은 습관이 됩니다. 제품 신뢰는 결국 일관성에서 쌓입니다.

실무 관점에서 기억할 한 줄은 이것입니다.

> RSC는 서버 효율을 올리고, loader/action은 전환 질서를 세웁니다.
> 둘의 경계를 문서화하지 않으면 성능 이점도 결국 운영 혼란에 잠식됩니다.

팀이 오늘 당장 할 수 있는 가장 큰 개선은 거창한 리팩터링이 아닙니다. 리소스 소유권 표 하나, action 후 재검증 규칙 하나, boundary 정렬 원칙 하나를 합의하는 것입니다. 이 작은 합의가 쌓이면, RR7 + RSC는 “복잡한 스택”이 아니라 “예측 가능한 시스템”이 됩니다.

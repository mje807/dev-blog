서버가 HTML을 만들어 브라우저에 보내는 순간, 사용자는 콘텐츠를 눈으로 확인할 수 있습니다. 그런데 그 HTML은 아직 "살아있지 않습니다." 버튼을 클릭해도 반응이 없고, 입력창에 타이핑해도 상태가 변하지 않습니다. React가 관리하는 모든 동적 행위—이벤트 처리, 상태 변경, 재조정(Reconciliation)—가 아직 연결되지 않은 채로 놓여있습니다.

이 간극을 메우는 과정이 **Hydration**입니다. 직역하면 "수분 공급"인데, 딱 맞는 비유입니다. 말라붙은 정적 문서에 React라는 생명수를 공급해 살아 움직이게 만드는 것이니까요.

그런데 Hydration이 단순히 이벤트 리스너를 달아주는 과정이라고 생각하면 오산입니다. React 18의 Hydration 시스템은 Fiber 트리 구축, DOM 트리 동시 순회, 불일치 감지와 복구, Suspense 경계 단위의 점진적 처리, 이벤트 큐잉과 재생까지 아우르는 정교한 메커니즘입니다. 이 글은 그 복잡성의 이유를 묻는 탐구입니다.

## 왜 Hydration이 필요한가: 두 세계의 간극

SSR(Server-Side Rendering)의 역설을 먼저 이해해야 합니다. 서버는 React 컴포넌트를 실행해 HTML을 만들어냅니다. 클라이언트는 그 HTML을 받아 화면에 표시하고, 다시 React를 실행해 인터랙티브하게 만들어야 합니다. 즉, **동일한 컴포넌트 코드가 두 번 실행됩니다.** 한 번은 서버에서 HTML을 만들기 위해, 한 번은 클라이언트에서 이벤트를 연결하기 위해.

문제는 이 두 번의 실행이 서로 다른 환경에서 일어난다는 점입니다. 서버에는 `window`가 없고, 클라이언트에는 서버의 요청 컨텍스트가 없습니다. 타임스탬프, 랜덤값, 로케일 설정이 서버와 클라이언트에서 다를 수 있습니다. 두 번의 실행이 완벽히 동일한 결과를 만들어야 Hydration이 올바르게 작동하지만, 현실에서는 크고 작은 불일치가 항상 존재합니다.

Hydration 시스템의 설계는 이 긴장감 위에서 만들어졌습니다. 서버 DOM을 최대한 재사용하되, 불일치를 감지하고, 필요하면 클라이언트 렌더링으로 폴백하는 전략입니다.

## 초기화: 두 개의 악보를 동시에 읽는 방법

Hydration의 시작점은 `hydrateRoot(container, <App />)` 호출입니다. 겉으로는 `createRoot`와 비슷해 보이지만, 내부에서는 결정적으로 다른 일이 벌어집니다.

`createRoot`는 빈 도화지에 그림을 그립니다. 기존 DOM 따위는 신경 쓰지 않습니다. 반면 `hydrateRoot`는 이미 그려진 그림 위에서 작업합니다. DOM을 파괴하지 않고, React 트리를 기존 DOM 구조에 "접합"해야 합니다. 이 차이 하나가 시스템 전체 복잡성의 출발점입니다.

초기화 과정에서 React는 Fiber Root를 만들면서 특수한 상태를 설정합니다. `isDehydrated: true`라는 플래그인데, 이것이 "이 Root는 아직 서버 DOM에 접합되지 않은 상태"라는 신호입니다. 이후 렌더링 과정 전반에서 이 플래그 값에 따라 완전히 다른 코드 경로를 타게 됩니다.

한 가지 주목할 설계 결정이 있습니다. `hydrateRoot`는 Fiber 트리 구축을 시작하기 전에 이벤트 위임을 먼저 등록합니다. Hydration이 완료되기 전이라도 사용자가 페이지와 상호작용할 수 있고, 그 이벤트를 잃어버리면 안 되기 때문입니다. 이것이 이벤트 리플레이 시스템의 전제 조건입니다—이벤트 위임이 먼저 있어야 이벤트를 캡처하고 큐에 저장할 수 있습니다.

또한 Hydration 초기 렌더에는 별도의 스케줄링 함수(`scheduleInitialHydrationOnRoot`)가 사용됩니다. 일반적인 `scheduleUpdateOnFiber`를 사용하지 않는 이유가 있습니다. Hydration의 초기 렌더는 "서버 렌더 결과와 반드시 일치해야 한다"는 특수한 제약 조건 하에 있습니다. 일반 업데이트 경로의 최적화 로직—진행 중인 렌더 인터럽트, 배칭 처리 등—이 이 제약을 깨뜨릴 수 있으므로, 최소한의 스케줄링만 수행하는 전용 함수가 필요합니다.

```javascript
// isDehydrated가 true로 설정된 초기 상태
var _initialState = {
  element: initialChildren,
  isDehydrated: hydrate,  // hydrateRoot에서는 true
  cache: null,
};
uninitializedFiber.memoizedState = _initialState;
```

이 코드에서 핵심은 `isDehydrated` 플래그입니다. 이 단 하나의 불리언 값이 이후 렌더링 전체의 흐름을 결정합니다. `beginWork`에서 HostRoot를 처리할 때 이 값이 `true`이면 DOM을 새로 생성하는 대신 기존 DOM을 재사용하는 경로로 진입합니다.

## Hydration Context: 두 트리를 동시에 탐색하는 설계

Hydration의 핵심 작동 방식을 이해하려면, React가 무엇을 동시에 하고 있는지를 파악해야 합니다.

일반적인 클라이언트 렌더링에서 React는 Fiber 트리를 구축하면서 DOM을 새로 만듭니다. 순서가 단순합니다. 하지만 Hydration에서는 두 가지 작업이 동시에 진행됩니다. Fiber 트리를 구축하면서, 동시에 기존 서버 DOM 트리를 순회하며 각 Fiber에 맞는 DOM 노드를 찾아 연결합니다.

마치 두 개의 악보를 동시에 읽으며 연주하는 것과 같습니다. 한 손으로는 React 컴포넌트 트리를 따라 Fiber를 만들고, 다른 손으로는 실제 DOM 노드를 하나씩 짚어가며 "이 Fiber는 이 DOM 노드입니다"라고 연결합니다. 두 악보가 일치하면 아름다운 연주가 되지만, 어느 한 쪽이 틀리면 불협화음이 납니다.

이 병렬 탐색을 구현하기 위해 React는 세 개의 모듈 레벨 변수를 사용합니다. `hydrationParentFiber`는 현재 처리 중인 부모 Fiber를, `nextHydratableInstance`는 다음으로 매칭할 DOM 노드를, `isHydrating`은 현재 hydration 중인지를 나타냅니다. 전역 상태를 사용하는 것이 다소 위험해 보일 수 있지만, React의 렌더링은 단일 스레드에서 동기적으로 진행되므로(Concurrent Mode에서도 각 작업 단위는 동기적) 이 패턴이 안전합니다.

Hydration이 시작되면 `enterHydrationState`가 호출되어 이 전역 상태를 초기화합니다. `nextHydratableInstance`는 컨테이너의 첫 번째 자식을 가리키게 됩니다. 그리고 각 Fiber가 `beginWork`를 통해 처리될 때마다 `tryToClaimNextHydratableInstance`가 호출되어 현재 DOM 노드와의 매칭을 시도합니다.

매칭 로직은 생각보다 관대합니다. React는 태그 이름만으로 DOM 노드를 매칭합니다. 속성(props) 비교는 이 단계에서 하지 않습니다. 예를 들어 `<div className="container">` Fiber와 서버의 `<div class="wrapper">` DOM은 태그가 같으므로 일단 매칭됩니다. 속성 차이는 나중에 `completeWork` 단계에서 따로 감지하고, 필요하면 커밋 단계에서 패치합니다. 이런 분리는 명확한 이유가 있습니다—빠른 매칭을 우선하고, 세부 검증은 뒤로 미루는 것입니다.

매칭이 실패하면 React는 한 번 더 시도합니다. 다음 형제 DOM 노드로 이동해서 매칭을 재시도합니다. 소스 코드 주석에 흥미로운 문구가 있습니다: "This is based on intuition and not data." 서버가 클라이언트와 약간 다른 DOM을 생성했을 때, 한 칸 건너뛰면 나머지가 정상 매칭될 확률이 높다는 경험적 판단입니다. 데이터 없이 직관으로 만들어진 휴리스틱이 수백만 개의 React 앱에서 작동하고 있다는 사실이 흥미롭습니다.

`completeWork` 단계에서 `popHydrationState`가 호출되면 hydration 커서를 부모 방향으로 이동시킵니다. 이 시점에서 남아있는 hydratable 자식이 있으면 어떻게 할까요? 대부분의 경우 삭제 예약을 합니다. 단, `<head>`와 `<body>` 내부는 예외입니다. 브라우저 확장이나 브라우저 자체가 자동으로 삽입하는 노드들이 있을 수 있기 때문입니다. 이것은 React가 실제 웹 환경의 복잡성을 수용한 실용적 결정입니다.

## 속성 비교: 서버와 클라이언트가 정말 같은가

태그 이름으로 DOM 노드를 매칭한 후, React는 서버가 만든 속성과 클라이언트 props를 비교합니다. `diffHydratedProperties`라는 함수가 이 역할을 담당하며, 200줄이 넘는 복잡한 함수입니다.

이 비교 과정은 흥미로운 비대칭성을 가집니다. 서버 DOM에는 있지만 클라이언트 props에는 없는 속성은 경고를 발생시킵니다. 반대로 클라이언트 props에는 있지만 서버 DOM에는 없는 속성은 `updatePayload`에 기록됩니다. `updatePayload`가 null이 아니면 커밋 단계에서 실제 DOM을 수정합니다.

특히 텍스트 콘텐츠는 단순 문자열 비교가 아닌 정규화(normalize) 과정을 거칩니다. 공백 차이 등 사소한 불일치는 무시하는 것이 목적입니다. React가 완벽한 일치를 요구하는 대신 "합리적으로 같음"을 허용하는 설계 철학을 보여줍니다.

`suppressHydrationWarning` prop도 이 맥락에서 이해할 수 있습니다. 서버와 클라이언트가 다른 값을 렌더링한다는 것을 개발자가 알고 있을 때—예를 들어 타임스탬프나 광고 배너—경고를 억제할 수 있는 탈출구입니다. 단, 중요한 제한이 있습니다. `suppressHydrationWarning`은 **경고만** 억제합니다. Concurrent Mode에서 실제 mismatch로 인한 클라이언트 렌더 폴백은 이 prop으로 막을 수 없습니다.

## Mismatch: 악보가 맞지 않을 때

두 악보가 맞지 않을 때 React는 어떻게 반응할까요? React 18에서 답은 렌더 모드에 따라 극적으로 다릅니다.

Legacy Mode에서는 경고를 출력하고 DOM을 in-place 수정합니다. 불일치가 있어도 앱은 계속 동작합니다. 하위 호환성을 위한 타협입니다.

Concurrent Mode에서는 훨씬 강경합니다. 불일치가 감지되면 에러를 throw하고, 가장 가까운 Suspense 경계에서 해당 서브트리를 클라이언트 렌더링으로 폴백합니다. "일관성이 깨진 UI를 표시하는 것보다 클라이언트 렌더가 더 안전하다"는 판단입니다.

```javascript
function shouldClientRenderOnMismatch(fiber) {
  return (fiber.mode & ConcurrentMode) !== NoMode &&
         (fiber.flags & DidCapture) === NoFlags;
}
```

이 함수가 true를 반환하면 `throwOnHydrationMismatch`가 호출되어 Concurrent Mode의 에러 처리 경로를 타게 됩니다. 에러가 Suspense 경계에서 포착되면 그 경계 내부 전체가 클라이언트에서 다시 렌더링됩니다.

가장 극단적인 경우, Suspense 경계 밖에서 mismatch가 발생하면 전체 Root가 클라이언트 렌더링으로 전환됩니다. 이때 에러는 즉시 크래시를 내는 대신 `onRecoverableError` 콜백을 통해 애플리케이션 레벨로 전달됩니다. "복구 가능한 에러"로 분류되는 것입니다. 사용자 경험을 망치지 않으면서도 개발자에게 문제를 알릴 수 있는 균형점입니다.

Mismatch의 가장 흔한 원인들은 예측 가능합니다. `Date.now()`, `Math.random()`, `window.innerWidth` 같은 브라우저 전용 API나 런타임 의존적 값들입니다. 해결 원칙도 일관됩니다: 서버와 클라이언트가 다를 수밖에 없는 값은 초기 렌더에서 제외하고, `useEffect`를 통해 클라이언트에서만 설정합니다. 초기 렌더의 일관성을 보장한 뒤, 상태 업데이트로 값을 바꾸는 것입니다.

## Selective Hydration: 모든 것을 한 번에 처리하지 않는 이유

React 17까지의 Hydration은 전체 트리를 한 번에 처리했습니다. 이것은 큰 페이지에서 치명적인 문제를 만듭니다. 수십 개의 복잡한 컴포넌트를 순차적으로 Hydrate하는 동안 메인 스레드가 블록되어, 사용자는 버튼을 클릭해도 반응을 얻지 못합니다. HTML은 보이지만 인터랙션이 불가능한 이 기간이 바로 TTI(Time to Interactive)와 FCP(First Contentful Paint) 사이의 간극입니다.

React 18의 Selective Hydration은 이 문제를 근본적으로 다르게 접근합니다. Suspense 경계를 단위로 Hydration을 분할하고, 사용자 상호작용이 발생한 영역을 우선 처리합니다.

비유하자면, 여러 환자가 동시에 응급실에 실려온 상황입니다. 예전 방식은 입장 순서대로 치료합니다—누가 더 위중한지 상관없이. React 18의 방식은 트리아지(triage)입니다. 사용자가 클릭한 버튼이 있는 영역이 가장 위중한 환자입니다. 그 영역을 먼저 Hydrate하고 이벤트를 처리합니다. 나머지는 유휴 시간에 처리합니다.

이것이 가능한 이유는 이벤트 위임이 Hydration 완료 전에 이미 등록되어 있기 때문입니다. 사용자가 dehydrated 영역을 클릭하면, React는 그 이벤트를 가로채서 해당 Suspense 경계의 Hydration을 즉시 시작합니다. 클릭 같은 discrete 이벤트는 동기적으로 처리됩니다—Hydration이 완료될 때까지 기다렸다가 즉시 이벤트를 재실행합니다.

우선순위 체계도 정교합니다. 동기 우선순위(클릭, 키보드 입력), 연속 우선순위(마우스 오버, 스크롤), 일반 우선순위(프로그래밍 방식의 요청)로 나뉩니다. 이 세 단계는 단순히 빠름/느림의 문제가 아니라, 각각 다른 사용자 경험 시나리오를 겨냥합니다.

## 이벤트 리플레이: 시간을 되돌리는 메커니즘

Selective Hydration의 가장 정교한 부분은 이벤트 리플레이 시스템입니다. 아이디어는 단순합니다. Hydration이 완료되기 전에 발생한 이벤트를 큐에 저장했다가, Hydration이 완료된 후 재실행합니다.

하지만 구현은 섬세합니다. 이벤트 종류에 따라 다른 전략을 씁니다.

**Discrete 이벤트**(클릭, 키보드 입력, 드래그 등)는 모두 배열에 저장됩니다. 사용자가 버튼을 다섯 번 클릭했다면, 다섯 번 모두 기록됩니다. 하나라도 잃어버리면 안 되기 때문입니다.

**Continuous 이벤트**(마우스 이동, 포인터 이동 등)는 최신 것 하나만 유지합니다. 마우스를 100px 이동하는 동안 발생한 50개의 mousemove 이벤트 중 중간 49개는 의미가 없습니다. 마지막 상태만 중요합니다.

이 비대칭적 처리가 메모리와 정확성 사이의 균형입니다. Discrete 이벤트를 잃으면 사용자 액션이 무시됩니다. Continuous 이벤트의 중간 상태를 모두 보존하면 메모리 낭비입니다.

Hydration이 완료되면 `retryIfBlockedOn`이 호출되어 블록 해제를 트리거합니다. 그러면 Scheduler를 통해 `replayUnblockedEvents`가 스케줄링되고, 저장된 이벤트들이 재실행됩니다. 재실행 방식도 흥미롭습니다—원본 네이티브 이벤트를 클론하여 원래 타겟 DOM 노드에 직접 `dispatchEvent`를 호출합니다. React의 이벤트 시스템이 정상적인 경로로 이 이벤트를 처리하게 됩니다.

## Dehydrated Suspense: 마커 시스템의 설계 철학

서버 렌더링 결과에 Suspense 경계는 어떻게 표현될까요? React는 HTML 주석을 마커로 사용합니다.

`<!--$-->` ... `<!--/$-->` 사이는 Suspense가 resolve된 콘텐츠입니다. `<!--$?-->` ... `<!--/$-->` 사이는 서버에서 아직 대기 중인 콘텐츠(스트리밍 SSR에서 주로 나타남)입니다. `<!--$!-->` ... `<!--/$-->` 사이는 서버에서 에러나 타임아웃이 발생해 fallback이 표시 중인 상태입니다.

이 주석 마커 시스템은 영리한 설계 결정의 산물입니다. HTML 표준을 벗어나지 않으면서, 클라이언트의 JavaScript가 "이 영역은 React Suspense 경계입니다"라는 정보를 읽을 수 있습니다. 커스텀 HTML 속성이나 `data-*` 속성을 쓸 수도 있었겠지만, 주석 노드는 렌더링에 아무 영향을 주지 않으면서 메타데이터를 전달하는 깔끔한 방법입니다.

중첩된 Suspense 경계는 `depth` 카운터로 처리됩니다. DOM을 역순으로 탐색하면서 `<!--/$-->`를 만나면 깊이를 하나 늘리고, `<!--$-->`를 만나면 깊이를 하나 줄입니다. 깊이가 0일 때 `<!--$-->`를 만나면 그것이 현재 Suspense 경계의 시작 마커입니다. 간단하지만 효과적인 알고리즘입니다.

`$?` 마커로 표시된 pending Suspense 경계는 특별히 처리됩니다. React는 이 경계를 즉시 Hydrate하려 하지 않고, `_reactRetry` 콜백을 등록해 서버 응답이 도착할 때까지 대기합니다. 서버가 콘텐츠를 스트리밍으로 보내면, 클라이언트 런타임이 `_reactRetry`를 호출해 Hydration을 트리거합니다. 이것이 React Server Components의 스트리밍과 Selective Hydration이 맞물리는 지점입니다.

## 아키텍처의 트레이드오프: 왜 이렇게 복잡한가

React Hydration 시스템의 복잡성을 이해하려면, 그것이 해결하려는 문제의 본질을 봐야 합니다.

**첫째, 두 환경의 결과를 하나로 합치는 것 자체가 복잡합니다.** 서버는 HTML 문자열만 생산합니다. 클라이언트는 이벤트와 상태를 관리해야 합니다. 이 두 세계를 연결하는 다리를 놓는 과정에서 불일치 가능성, 에러 처리, 복구 전략이 필연적으로 따라옵니다.

**둘째, 성능과 정확성 사이의 균형입니다.** 전체 트리를 한 번에 동기적으로 Hydrate하면 구현이 단순하지만 사용자 경험이 나빠집니다. Selective Hydration은 사용자 경험을 위해 복잡성을 감수한 트레이드오프입니다.

**셋째, 아키텍처 경계를 지키는 비용입니다.** Hydration 우선순위 함수들(`attemptSynchronousHydration`, `attemptContinuousHydration`)이 `setAttemptSynchronousHydration` 같은 setter로 주입되는 방식은 의존성 역전(IoC)의 결과입니다. 이벤트 시스템과 reconciler가 서로를 직접 참조하지 않도록 설계된 것입니다. 이 분리가 코드를 복잡하게 만들지만, 각 레이어가 독립적으로 테스트되고 진화할 수 있게 합니다.

Hydration의 비용도 명확히 인식해야 합니다. 서버 DOM을 재사용한다고 해서 클라이언트 작업이 없는 것이 아닙니다. 모든 컴포넌트를 실행해 Fiber 트리를 구축해야 하고, DOM 트리를 순회하며 매칭해야 하며, 속성을 비교해야 합니다. 순수 클라이언트 렌더보다 추가 작업이 있습니다. SSR의 이점은 HTML이 먼저 표시된다는 것이지, 클라이언트 작업이 줄어든다는 것이 아닙니다.

## 핵심 포인트 정리

React 18의 Hydration 시스템이 이전보다 훨씬 복잡해진 데는 명확한 이유가 있습니다.

**재사용하되, 검증한다.** 서버 DOM을 재사용하면서도 속성 불일치를 감지하고 필요하면 패치합니다. 속성이 완벽히 일치하지 않아도 앱은 올바르게 동작합니다.

**실패를 안전하게 처리한다.** Mismatch가 발생하면 전체를 포기하는 대신, 가능한 한 작은 단위(Suspense 경계)에서 클라이언트 렌더로 폴백합니다. 사용자는 에러 화면 대신 콘텐츠를 봅니다.

**이벤트를 잃지 않는다.** Hydration이 완료되기 전에 발생한 이벤트는 큐에 저장되어 나중에 재실행됩니다. 사용자의 클릭이 Hydration 타이밍 때문에 무시되는 일은 없습니다.

**우선순위를 고려한다.** 사용자가 상호작용한 영역이 먼저 Hydrate됩니다. 나머지는 유휴 시간에 처리됩니다. 전체가 준비될 때까지 기다리지 않아도 사용자는 원하는 기능을 쓸 수 있습니다.

Hydration은 SSR이 존재하는 한 필요한 기술입니다. 서버에서 빠르게 보이고, 클라이언트에서 자연스럽게 상호작용 가능해지는 경험—이것이 React Hydration 시스템이 그 모든 복잡성을 감수하며 달성하려는 목표입니다.

## 한눈에 보기

React Server Components(RSC)를 도입하면 많은 팀이 “이제 라우터 중요도는 줄어드는 것 아닌가?”라는 질문을 던집니다. 겉으로 보면 타당한 의문입니다. 서버에서 더 많이 렌더링하고, 데이터도 서버 근처에서 가져오며, 클라이언트 번들도 줄어들기 때문입니다.
하지만 실무에서는 반대로 느끼는 순간이 빨리 옵니다. RSC를 붙인 뒤부터 장애, 느린 전환, 중복 패칭, 에러 격리 실패가 “라우팅 경계 설계”에서 터지기 시작하기 때문입니다.

핵심만 먼저 정리하면 아래와 같습니다.

- RSC는 **렌더링 위치를 재편**하지만, Router는 **전환 경험의 일관성**을 책임집니다.
- React Router 7은 화면 이동 도구가 아니라 **경계 오케스트레이터**에 가깝습니다.
- 대규모 팀에서는 “누가 어떤 컴포넌트를 작성하느냐”보다 “누가 URL/에러/재검증 경계를 소유하느냐”가 품질을 좌우합니다.
- RSC와 loader/action은 대체 관계가 아니라, 라우트 경계 아래에서 목적이 다른 협력 관계입니다.
- 결국 질문은 “RSC를 쓸 것인가”가 아니라 “우리 제품에서 경계를 어디에 두고, 운영 책임을 어떻게 나눌 것인가”입니다.

## 들어가며

RSC 논의가 확산되면서 프론트엔드 아키텍처 대화의 초점이 빠르게 이동했습니다. 이전에는 “CSR이냐 SSR이냐”, “번들 최적화를 어떻게 하느냐”가 주된 논점이었다면, 이제는 “어떤 UI를 서버에서 계산하고 어떤 상호작용을 클라이언트에 남길 것인가”가 중심이 되었습니다. 기술적으로는 큰 진전입니다. 하지만 조직과 제품 운영 관점에서는 새로운 부담이 생깁니다. 경계가 늘어났기 때문입니다.

여기서 말하는 경계는 단순히 컴포넌트 분할선이 아닙니다.
- URL이 어떤 상태를 표현하는지,
- 전환 중 어떤 데이터가 취소되고 어떤 데이터가 유지되는지,
- 실패를 어디에서 격리하고 어디까지 복구할지,
- 어떤 타이밍에 재검증하여 “새로움”과 “안정성”을 균형 맞출지,
이 모든 의사결정의 집합입니다.

RSC는 이 문제를 자동으로 해결하지 않습니다. 오히려 문제를 더 선명하게 드러냅니다. 서버가 똑똑해질수록 사용자의 기대치도 올라가기 때문입니다. 예전에는 페이지 전체 새로고침이 당연하던 구간에서 이제 사용자는 부분 전환, 즉각 반응, 안정적 복구를 기대합니다. 기대치가 올라간 환경에서 라우터는 “경로 매칭 도구”를 넘어 “사용자 경험의 트랜잭션 관리자”로 기능하게 됩니다.

React Router 7이 중요한 이유도 여기에 있습니다. v7은 단순히 API 추가 버전이 아니라 Framework/Data/Library 관점을 함께 가져가며, 팀이 처한 현실(점진적 전환, 혼합 구조, MFE 조직 구조)을 버틸 수 있는 선택지를 제공합니다. 다시 말해, 기술의 순수함보다 운영의 현실성을 우선하는 라우팅 모델입니다.

## 왜 RSC 이후에 Router가 더 중요해지는가

### 1) “어디서 렌더링”보다 “어떻게 전환”이 사용자 체감에 더 크게 작용하기 때문입니다

RSC의 장점은 분명합니다. 서버에서 컴포넌트를 계산해 초기 부담을 줄이고, 데이터에 가까운 위치에서 조합해 전달 효율을 높입니다. 다만 사용자는 내부 구조를 보지 않습니다. 사용자가 체감하는 것은 전환입니다.
- 링크를 눌렀을 때 얼마나 자연스럽게 이동되는지,
- 이전 요청이 취소되어야 할 때 정확히 버려지는지,
- 실패했을 때 앱 전체가 무너지는지 일부만 복구되는지,
이런 경험은 대부분 Router 경계에서 결정됩니다.

즉 RSC가 성능 여지를 열어주는 기술이라면, Router는 그 여지를 체감 가능한 품질로 변환하는 기술입니다.

### 2) RSC 도입은 “경계 삭제”가 아니라 “경계 재배치”이기 때문입니다

실무에서 자주 생기는 오해는 “RSC를 쓰면 loader/action이 줄고, 그만큼 라우팅도 단순해진다”는 기대입니다. 일부 구간에서는 맞습니다. 그러나 전체 제품에서는 경계가 사라지지 않습니다.
서버 컴포넌트로 이동한 로직이 늘어날수록, 오히려 다음 질문이 더 중요해집니다.

- 이 URL이 가리키는 상태는 어떤 데이터 계약을 가져야 하는가?
- 이 전환에서 stale 데이터를 허용할 것인가, 즉시 재검증할 것인가?
- 폼 액션 후에 어떤 라우트 조각만 갱신할 것인가?
- 실패 시 전체 화면 오류로 보낼 것인가, 섹션 단위 fallback으로 복구할 것인가?

이 질문은 렌더링 엔진의 문제가 아니라 라우팅 정책의 문제입니다. 그래서 “RSC 도입 이후 라우팅 논의가 줄어야 한다”가 아니라 “라우팅을 운영 정책 수준으로 끌어올려야 한다”가 더 정확합니다.

### 3) 대규모 팀에서는 기술 선택보다 소유권 설계가 먼저 무너지기 때문입니다

30인 규모 이상의 조직, 특히 MFE 전환 중인 조직에서는 코드보다 계약이 먼저 깨집니다. 예를 들어 각 팀이 독립적으로 데이터 로딩 전략을 최적화하면 단기 속도는 올라갈 수 있습니다. 그러나 URL 쿼리 스키마, 에러 처리 형태, 로딩 UI 기준이 제각각이 되면 제품은 빠르게 “조각난 앱”이 됩니다.

React Router 7 관점에서 이 문제를 풀려면 라우팅을 기능이 아니라 거버넌스로 봐야 합니다.
- URL 계약 소유자,
- 에러/로딩 UX 표준 소유자,
- 재검증 정책 승인자,
가 명확해야 RSC의 장점이 조직 전체의 장점으로 전환됩니다.

## React Router 7 관점에서 다시 정의한 Router의 책임

RSC 시대의 Router 책임을 한 문장으로 말하면 다음과 같습니다.

**Router는 데이터의 출처를 정하는 도구가 아니라, 전환의 일관성과 경계의 복구력을 설계하는 런타임 계층입니다.**

이를 실무 언어로 풀면 다음 네 가지가 핵심입니다.

### 1) URL을 제품 상태의 계약으로 유지합니다

URL은 공유, QA 재현, 로그 분석, 고객지원, 실험 추적의 공통 언어입니다.
RSC로 데이터 위치가 바뀌어도 URL 계약이 흔들리면 운영 비용이 폭증합니다. 특히 검색/필터/정렬/탭 상태가 많은 제품에서 URL 계약은 “기능 요구사항”이 아니라 “운영 안정성 요구사항”입니다.

왜 중요하냐고 묻는다면 답은 단순합니다.
문제가 생겼을 때 가장 먼저 의존하는 것이 재현 가능한 URL이기 때문입니다. 재현이 안 되면 개선도 느려지고, 책임 소재도 흐려집니다.

### 2) 전환 중 취소·중단·경합을 통제합니다

사용자는 기다려주지 않습니다. 빠르게 탭을 바꾸고, 뒤로 가고, 다른 링크를 연속으로 누릅니다. 이때 오래 걸리는 요청이 늦게 도착해 최신 상태를 덮어쓰면 사용자는 “랜덤 버그”를 경험합니다.
실제로는 랜덤이 아니라, 전환 경합 제어 실패입니다.

React Router 7의 강점은 이 전환 라이프사이클을 라우트 경계 단위로 다룰 수 있다는 점입니다. 결국 사용자는 “데이터가 어디서 왔는지”보다 “지금 내가 보고 있는 화면이 최신 의도와 일치하는지”를 기준으로 품질을 판단합니다.

### 3) 실패를 격리하고 복구 경로를 설계합니다

RSC가 있다고 해서 에러 격리가 자동화되지는 않습니다. 실패를 어디서 끊고 무엇을 유지할지는 여전히 설계 결정입니다.
라우트 단위 에러 경계가 없으면 작은 실패가 전체 레이아웃 붕괴로 번집니다. 반대로 경계를 너무 잘게 자르면 fallback이 남발되어 경험이 분절됩니다.

왜 어렵냐면, 이것은 기술 최적화 문제가 아니라 제품 철학 문제이기 때문입니다.
“사용자에게 지금 무엇을 보여주는 것이 최선인가”를 정해야 하며, 그 결정이 Router 경계에 코드로 남습니다.

### 4) 재검증 정책을 명시해 데이터 신뢰도를 운영합니다

RSC/loader/action/fetcher가 혼합된 앱에서 가장 흔한 운영 이슈는 stale 데이터입니다. “가끔 안 바뀐다”, “새로고침하면 맞다” 같은 피드백은 대부분 재검증 정책 부재에서 옵니다.
정책이 없으면 개발자는 각자 방어 코드를 넣고, 사용자 경험은 우연에 의존하게 됩니다.

중요한 이유는 명확합니다.
데이터 정합성 문제는 기능 버그보다 신뢰 버그로 받아들여지기 때문입니다. 사용자는 틀린 숫자를 한 번 보면 그 화면 전체를 의심합니다.

## 실무에서 자주 틀리는 판단과 교정 포인트

### 오해 1) “RSC 도입 = loader/action 축소 = 단순화”입니다

현실은 “일부 단순화 + 다른 구간 복잡화”입니다.
읽기 중심 화면은 단순해질 수 있지만, 쓰기/검증/롤백/재시도 흐름은 여전히 Router 계층에서 명확하게 설계하는 편이 안정적입니다. 특히 폼 액션 이후 후속 갱신은 라우팅 문맥이 있을 때 예측 가능성이 높습니다.

### 오해 2) “Router는 네비게이션 UI 도구”입니다

v7 실무에서는 Router가 전환 상태 머신에 가깝습니다. 로딩 표시 시점, 취소 처리, 경계별 에러 복구, 재검증 트리거가 모두 사용자 신뢰와 직결됩니다.
따라서 Router는 “보기 좋은 URL”을 만드는 도구가 아니라 “의도한 상태로 안전하게 도달”하게 만드는 도구입니다.

### 오해 3) “MFE + RSC면 경계가 자동 정리”입니다

오히려 자동 정리가 가장 어렵습니다. MFE 환경에서는 각 팀이 자체 최적화를 시도하며 중복 패칭, 권한 중복 확인, 로딩 플리커, 에러 전파 충돌이 발생하기 쉽습니다.
RSC는 이를 해결하는 마법이 아니라, 잘 설계된 경계 위에서 효율을 극대화하는 증폭기입니다. 기반 경계가 불안하면 문제도 증폭됩니다.

## 트레이드오프

RSC와 React Router 7을 함께 도입할 때의 핵심은 “정답 선택”이 아니라 “손실을 어디서 감수할지”를 명확히 하는 일입니다. 주요 트레이드오프를 정리하면 다음과 같습니다.

### 1) 초기 속도 vs 운영 일관성

팀별 자율 최적화를 허용하면 초기 개발 속도는 빠릅니다. 하지만 URL 계약, 에러 포맷, 재검증 타이밍이 흩어지면 운영 비용이 급격히 상승합니다.
반대로 공통 규약을 먼저 만들면 온보딩과 초반 속도는 다소 느려지지만, 장애 대응과 품질 유지가 훨씬 안정적입니다.

### 2) 세밀한 경계 vs 사용자 흐름의 연속성

경계를 세밀하게 나누면 부분 실패 복구가 쉬워집니다. 그러나 지나치게 잘게 나누면 로딩/fallback이 과다 노출되어 사용자가 흐름을 잃습니다.
너무 큰 경계는 단순하지만 작은 실패가 전체 화면을 무너뜨릴 수 있습니다. 제품의 핵심 여정에서 어디까지 연속성을 보장할지 우선순위를 정해야 합니다.

### 3) 즉시 재검증 vs 체감 성능

모든 전환에서 즉시 재검증하면 최신성은 높아지지만 응답 지연이 늘어날 수 있습니다. 반대로 재검증을 늦추면 빠르게 느껴지지만 stale 노출 위험이 커집니다.
여기서 중요한 것은 기술적 정답이 아니라 데이터의 성격입니다. 가격·재고·권한처럼 민감한 데이터는 최신성을 우선하고, 설명·메타데이터처럼 변화가 느린 데이터는 체감 성능을 우선하는 식의 구분이 필요합니다.

### 4) 중앙 통제 vs 도메인 자율성

플랫폼 팀이 모든 라우팅 결정을 통제하면 일관성은 올라갑니다. 하지만 도메인 팀의 실험 속도가 떨어질 수 있습니다.
반대로 완전 자율을 주면 실험은 빨라져도 제품 전체 경험의 일관성이 깨집니다.
현실적인 해법은 “계약은 중앙, 구현은 분산”입니다. URL 스키마·오류 규격·재검증 원칙은 중앙에서 고정하고, 실제 화면 구성과 데이터 조합은 도메인 팀이 자율적으로 가져가는 구조가 효과적입니다.

## 실무 적용을 위한 최소 운영 가이드

긴 설계를 바로 도입하기 어렵다면, 아래 네 가지부터 고정하는 것이 좋습니다.

1. **라우트 책임 문서화**
각 라우트에 대해 데이터 소스, 실패 경계, 로딩 규칙, 권한 규칙을 명시합니다. 문서가 없으면 논쟁은 감으로 흐릅니다.

2. **전환 경합 테스트 추가**
빠른 연속 이동, 취소, 뒤로가기, 느린 네트워크를 포함한 시나리오를 자동화합니다. 버그는 대체로 이 경합 구간에서 재현됩니다.

3. **재검증 정책 표준화**
“언제 stale로 판단하는가”를 데이터 유형별로 나눠 정의합니다. 사람마다 다르게 판단하면 운영이 즉시 불안정해집니다.

4. **MFE 경계 승인 절차 설정**
URL 계약 변경은 승인 절차를 거치게 합니다. 각 팀이 독립적으로 쿼리 구조를 바꾸기 시작하면 복구 비용이 매우 커집니다.

코드는 최소화하되, 흐름은 반드시 시각화해두는 것이 좋습니다. 예를 들면 다음과 같은 수준이면 충분합니다.

```text
URL 변경 → Router 전환 시작 → 라우트 경계 선택
→ (RSC 경로 / loader·action 경로) 병행
→ UI 반영 → 재검증 여부 결정
→ 실패 시 경계 단위 복구
```

이 정도만 팀 합의로 고정해도 “왜 여기서 이렇게 동작하는가”를 설명할 수 있게 되고, 설명 가능성은 곧 유지보수 가능성으로 이어집니다.

## 마무리하며

RSC 시대에 Router의 역할은 줄어들지 않습니다. 정확히 말하면 역할이 이동합니다.
과거에는 “화면을 어디로 보낼 것인가”가 중심이었다면, 이제는 “사용자를 어떤 상태 전환 경험으로 데려갈 것인가”가 중심입니다. 이 변화에서 React Router 7은 단순한 이동 도구가 아니라 경계 설계의 실행 기반이 됩니다.

실무에서 중요한 것은 기술 유행을 빠르게 따라가는 일이 아닙니다.
우리 팀의 제품 여정에서 어떤 실패를 허용하지 않을지, 어떤 최신성을 보장할지, 어떤 계약을 조직적으로 지킬지를 먼저 정의하는 일입니다. RSC는 그 결정을 더 잘 실행하게 만드는 수단입니다. Router는 그 수단을 일관된 사용자 경험으로 바꾸는 장치입니다.

결국 질문은 하나로 수렴합니다.

- “RSC를 도입했는가?”가 아니라
- “RSC 이후 경계를 운영 가능한 형태로 설계했는가?”입니다.

이 질문에 명확히 답할 수 있다면, React Router 7은 단순한 프레임워크 선택을 넘어 팀의 품질 체계를 강화하는 기반이 됩니다.

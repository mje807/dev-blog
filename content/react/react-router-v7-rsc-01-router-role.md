## 한눈에 보기

RSC(React Server Components)가 도입되면 서버 렌더링 비중이 커지기 때문에, 라우터 역할이 줄어든다고 오해하기 쉽습니다. 그러나 운영 관점의 사실은 반대입니다. React Router 7은 URL 계약, navigation concurrency, error boundary 단위 격리, mutation 이후 revalidation 범위 결정처럼 “사용자 이동의 일관성”을 실행하는 계층이기 때문입니다.

즉 RSC는 “어디서 렌더링할지”를 바꾸고, React Router 7은 “이동 과정에서 무엇을 보장할지”를 고정합니다. 이 글은 React Router 7을 중심으로 설계 방향과 의도, 실제 구현과 런타임 동작, 그리고 어떤 문제를 어떻게 해결하는지를 팩트 기반으로 정리합니다.

---

## 들어가며

React 공식 문서는 RSC를 서버에서 실행되는 컴포넌트 모델로 설명하며, 클라이언트 번들 크기 축소와 데이터 접근 경로 단축을 핵심 효과로 제시합니다. 이 설명은 렌더링 비용 최적화에는 정확하지만, “사용자 이동” 전체를 다루지는 않습니다. 실제 제품은 화면 렌더링 이전에 URL 해석, 데이터 요청, 취소, 재시도, 오류 복구, 상태 재검증을 연속적으로 처리합니다.

React Router 7 문서에서 중요한 축은 route matching 자체보다 Data Router 모델입니다. loader/action/revalidation/error boundary/navigation state를 하나의 전환 모델로 다루기 때문입니다. 따라서 RSC 도입 이후에도 다음과 같은 운영 질문은 계속 남습니다.

- 연속 클릭에서 마지막 사용자 의도(last intent)가 보장되는가
- 하위 세그먼트 실패가 전체 레이아웃 붕괴로 번지는가
- mutation 이후 어떤 route를 언제 다시 검증하는가
- URL이 공유·재현·관측 가능한 상태 계약으로 유지되는가

이 질문은 컴포넌트를 서버에서 렌더링하는지 여부로 자동 해결되지 않습니다. React Router 7이 전환 경계를 정책으로 정의해야 해결됩니다. 이 지점이 RSC 시대에 Router를 재해석해야 하는 이유입니다.

---

## 문제 정의: RSC 도입 이후에도 전환 장애가 남는 이유

### 1) Intent inversion: 늦게 끝난 이전 요청이 최신 화면을 덮는 현상

문제의 본질은 렌더링 기술이 아니라 concurrency 제어입니다. 사용자가 `/orders?page=2`를 누른 직후 `/orders?page=3`을 누르면, 네트워크 지연 차이 때문에 먼저 보낸 요청이 나중에 도착할 수 있습니다. 이때 “응답 도착 순서”를 기준으로 화면을 갱신하면 최신 의도가 역전됩니다. React Router 7은 전환 단위를 기준으로 취소와 무효화를 관리해 이 문제를 제어합니다.

### 2) Failure blast radius: 부분 실패가 전체 실패로 확대되는 현상

라우트별 오류 격리가 없으면 상세 패널 하나의 실패가 페이지 전체 오류로 증폭됩니다. 이는 단순 예외 처리 부족이 아니라 경계 설계 부재입니다. React Router 7은 `errorElement`를 라우트 트리 단위로 배치해 실패 반경을 줄일 수 있도록 설계되어 있습니다.

### 3) Revalidation inconsistency: mutation 이후 최신성 규칙 불일치

동일 도메인에서 어떤 화면은 즉시 최신화되고, 어떤 화면은 오래된 상태를 노출하는 경우가 발생합니다. 원인은 재검증 정책이 팀 규칙이 아니라 개인 구현 습관으로 남아 있기 때문입니다. React Router 7은 action 이후 loader 재실행 경로를 구조적으로 연결하기 때문에, 정책만 명시하면 일관된 동작을 재현할 수 있습니다.

### 4) URL semantic drift: URL 의미 표류

URL이 제품 상태 계약이 아니라 임시 UI state 저장소처럼 쓰이면, 링크 공유와 QA 재현성이 급격히 떨어집니다. 동일 기능이라도 쿼리 파라미터 의미가 팀마다 달라지고, 로그 상관관계가 약해집니다. React Router 7 환경에서 URL은 경로 탐색 수단이 아니라 “시스템 간 공통 인터페이스”입니다.

---

## 설계 방향과 의도

React Router 7을 RSC와 결합할 때 핵심 의도는 “라우팅 기능 추가”가 아니라 “운영 경계 명세화”입니다. 실무에서 효과가 검증되는 설계 방향은 아래 네 축입니다.

### 1) URL을 공유 가능한 제품 계약으로 고정합니다

URL에 남겨야 할 것은 복원 가능하고 협업 가능한 상태입니다. 필터, 정렬, 페이지네이션, 리소스 식별자처럼 재현 가능한 값은 URL에 배치합니다. 반대로 hover, 패널 임시 접힘, 드래그 중간값처럼 순간적 UI state는 URL 바깥에 둡니다.

이 분리가 중요한 이유는 세 가지입니다.
첫째, QA가 URL만으로 동일 조건을 재현할 수 있습니다.
둘째, 분석 이벤트와 서버 로그를 동일 경로 키로 상관 분석할 수 있습니다.
셋째, 외부 공유 링크의 신뢰도가 유지됩니다.

React Router 7은 경로 파라미터와 search params를 일관되게 취급할 수 있으므로, URL semantic contract를 문서화하면 운영 품질이 안정됩니다.

### 2) 전환 제어를 구현 디테일이 아니라 정책으로 올립니다

사용자 이동은 성공/실패 이분법이 아닙니다. 실제로는 시작, pending, 중단, 대체, 완료가 연속적으로 발생합니다. React Router 7의 navigation state 모델은 이 과정을 노출합니다. 따라서 팀은 최소한 아래를 정책으로 정의해야 합니다.

- 마지막 의도 우선(last-intent-wins) 적용 범위
- pending UI 표시 조건과 timeout 기준
- 취소된 요청 결과 무효화 규칙
- 중복 네비게이션 디바운싱 또는 병합 전략

정책이 문서화되어 있으면 네트워크 편차가 큰 환경에서도 동일 UX를 재현할 수 있습니다.

### 3) 오류를 라우트 경계에서 격리합니다

RSC를 도입해도 API timeout, 권한 오류, 데이터 스키마 불일치는 계속 발생합니다. 중요한 것은 “오류가 발생하느냐”가 아니라 “오류가 어디까지 전파되느냐”입니다. React Router 7은 라우트 단위 경계 복구를 지원하므로, 예를 들어 상세 라우트 실패 시 목록과 상위 레이아웃은 유지할 수 있습니다.

이 방식의 실질 효과는 사용자 맥락 유지입니다. 전체 페이지 재시작이 아니라 부분 재시도와 부분 복구가 가능해지며, 장애 체감 시간을 줄입니다.

### 4) 재검증을 도메인 위험도로 분류합니다

모든 mutation 이후 전체 재검증은 단순하지만 비용이 큽니다. 반대로 과도한 선택 재검증은 stale 노출 위험이 커집니다. 따라서 React Router 7에서는 도메인 위험도 기반 분류가 필요합니다.

- High risk: 결제, 권한, 주문 상태 → 보수적 재검증
- Medium risk: 재고 요약, 사용자 설정 목록 → 범위 제한 재검증
- Low risk: 추천, 통계 카드 → 지연 허용 + 배치 재검증

이 분류는 성능 튜닝이 아니라 데이터 정합성 계약입니다.

## 실제 구현과 런타임 동작

아래는 코드 문법 자체가 아니라, React Router 7이 런타임에서 어떤 순서로 동작하는지에 대한 사실 중심 설명입니다.

### 1) Navigation 시작: URL 기준으로 실행 범위 계산

사용자가 새로운 URL로 이동하면 Router는 route tree를 매칭하고, 어떤 loader가 재실행 대상인지 계산합니다. 이때 “현재 route state + target URL”이 입력으로 사용됩니다. 핵심은 컴포넌트 렌더 순서가 아니라 라우트 전환 단위가 먼저 결정된다는 점입니다.

### 2) Pending 상태 노출: 사용자 피드백과 작업 지속성 분리

전환 중에는 navigation state가 pending으로 바뀌며, UI는 로딩 인디케이터를 표시할 수 있습니다. 이때 중요한 설계 포인트는 전체 블로킹을 피하는 것입니다. React Router 7의 상태 노출을 활용하면 화면의 안정 영역(stable shell)을 유지한 채 변경 영역만 전환할 수 있습니다.

### 3) Concurrency 처리: 이전 전환의 무효화

연속 네비게이션이 발생하면 이전 전환 컨텍스트와 최신 전환 컨텍스트가 경쟁합니다. React Router 7의 concurrency 모델은 최신 전환 기준으로 결과 반영 여부를 판단합니다. 따라서 오래 걸린 이전 요청이 나중에 완료돼도 최신 상태를 덮지 않도록 제어할 수 있습니다. 이 지점이 intent inversion 방지의 핵심입니다.

### 4) Action 실행과 재검증: write 이후 read 일관성 복원

mutation(action) 성공 이후에는 관련 loader 재실행이 트리거됩니다. 여기서 팀이 정의한 재검증 정책이 직접 적용됩니다. 예를 들어 주문 상세 변경 후 목록 요약을 재조회할지, 상세만 갱신할지, 상위 통계까지 확장할지를 route 구조와 정책으로 일치시킬 수 있습니다.

### 5) Error boundary 동작: 실패 반경 제한

특정 라우트의 loader/action/render 단계에서 오류가 발생하면 해당 경계의 `errorElement`가 활성화됩니다. 올바르게 분리된 경우 실패는 하위 세그먼트에 국한되고 상위 레이아웃은 유지됩니다. 이는 사용자 세션 맥락 보존과 복구 시간 단축에 직접 연결됩니다.

### 6) RSC와의 경계: 렌더링 책임과 전환 책임 분리

RSC는 서버에서 컴포넌트와 데이터 결합을 수행해 클라이언트 부담을 낮춥니다. React Router 7은 그 위에서 URL 계약, 전환 상태, 오류 격리, 재검증 타이밍을 관리합니다. 따라서 두 기술은 대체 관계가 아니라 직교 관계입니다. 실제 운영 문제는 이 경계를 분리해 설계했는지 여부로 갈립니다.

### 7) 관측 가능성(Observability): “잘 된다”를 수치로 검증

React Router 7 운영에서는 다음 지표를 수집해야 정책 작동 여부를 검증할 수 있습니다.

- route별 navigation 취소율
- older-over-newer 역전 발생 건수
- boundary별 복구 성공률과 평균 복구 시간
- mutation 이후 stale 노출 시간(p95)
- 경로 파라미터/쿼리 파라미터 유효성 실패율

이 지표는 감각이 아니라 실행 품질을 증명하는 근거입니다.

## 어떤 문제를 어떻게 해결하는가

### 문제 A: 빠른 연속 클릭에서 화면이 이전 상태로 되돌아가는 현상

- **원인**: 응답 도착 순서 기반 갱신, 전환 무효화 규칙 부재
- **해결 방식**: React Router 7 전환 컨텍스트 기준으로 최신 intent 우선 반영
- **결과**: 지연 변동이 커도 마지막 사용자 행동과 화면 상태가 일치합니다.

### 문제 B: 하위 데이터 실패가 전체 앱 중단으로 이어지는 현상

- **원인**: 페이지 단일 오류 처리 구조, 라우트 경계 부재
- **해결 방식**: 라우트 트리 기반 `errorElement` 배치, 복구 UI 분리
- **결과**: 핵심 레이아웃과 탐색 맥락을 유지한 채 부분 장애만 노출합니다.

### 문제 C: mutation 이후 최신성 불일치로 사용자 혼란이 생기는 현상

- **원인**: 재검증 범위가 팀 규칙이 아니라 구현자별 임의 판단
- **해결 방식**: 도메인 위험도 분류 + route 단위 revalidation 정책 고정
- **결과**: 정합성 요구가 높은 화면은 빠르게 최신화되고, 비용 민감 화면은 선택 갱신으로 균형을 유지합니다.

### 문제 D: URL 공유 시 동일 화면 재현이 실패하는 현상

- **원인**: URL semantic contract 미정의, 임시 UI 상태의 무분별한 URL 저장
- **해결 방식**: URL 포함 대상/제외 대상 기준 문서화, 파라미터 스키마 검증
- **결과**: 공유 링크 신뢰도, QA 재현성, 로그 추적 가능성이 함께 개선됩니다.

### 문제 E: RSC 도입 후 책임 경계 혼선으로 디버깅 비용이 증가하는 현상

- **원인**: 서버 렌더링과 클라이언트 전환 책임 혼재
- **해결 방식**: RSC=렌더링/데이터 결합, Router=전환/경계/정책으로 역할 분리
- **결과**: 장애 분석 시 원인 위치가 명확해지고 수정 리드타임이 줄어듭니다.

## 마무리하며

RSC 시대의 React Router 7은 축소되는 계층이 아니라, 이동 일관성을 보장하는 핵심 계층입니다. 사실 기준으로 보면 RSC는 렌더링 경로를 최적화하고, React Router 7은 URL 계약·전환 제어·오류 격리·재검증 정책을 실행합니다. 운영 품질은 “서버에서 얼마나 많이 렌더링했는가”보다 “전환 경계를 얼마나 명시적으로 설계했는가”로 결정됩니다.

정리하면 React Router 7의 실무 가치는 다음 네 가지로 수렴합니다.
첫째, URL을 제품 계약으로 고정합니다.
둘째, concurrency를 정책으로 제어합니다.
셋째, 실패 반경을 라우트 경계에서 제한합니다.
넷째, 재검증을 도메인 위험도로 운영합니다.

이 네 축이 문서와 구현, 관측 지표로 연결될 때 React Router 7 + RSC 조합은 기능 조합을 넘어 재현 가능한 품질 체계가 됩니다.

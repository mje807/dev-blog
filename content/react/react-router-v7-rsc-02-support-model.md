## 한눈에 보기

- React Router 7에서 RSC를 해석할 때 핵심은 기능 체크리스트가 아니라 **운영 모델**입니다.
- Framework / Data / Library 모드는 API 취향이 아니라, **책임 경계(런타임·데이터·장애 대응·배포 검증)**를 어디에 두는지에 대한 선택입니다.
- 많은 팀이 RSC 도입을 렌더링 기술 변경으로 시작하지만, 실제 성패는 **라우트 계약(데이터 소유권·재검증·에러 경계)**을 먼저 고정했는지에 의해 갈립니다.
- 대규모 조직과 MFE 전환 환경에서는 `Data Mode로 경계 표준화 → Framework Mode로 운영 통합`이 리스크 대비 효율이 높은 경로입니다.
- Library Mode는 빠른 시작에 강점이 있지만, 기본값으로 확장되면 장기 운영에서 규약 부채를 키우기 쉬우므로 **예외 모드로 제한**하는 전략이 현실적입니다.

## 들어가며

이 글의 중심 주제는 **React Router 7 지원 모델**입니다.

"React Router 7은 RSC를 지원하나요?"라는 질문은 자주 등장하지만, 실무 의사결정에는 충분히 정확하지 않습니다. 같은 "지원"이라는 단어 안에 전혀 다른 운영 의미가 섞여 있기 때문입니다. 어떤 팀은 서버 렌더링 파이프라인까지 통합된 운영을 원하고, 어떤 팀은 기존 클라이언트 중심 앱을 유지하면서 데이터 경계만 먼저 정리하려고 합니다. 또 어떤 조직은 MFE 구조에서 팀 자율성을 유지하되, 공통 규약을 최소 비용으로 강제하고 싶어 합니다.

React Router v7은 이 서로 다른 요구를 Framework Mode, Data Mode, Library Mode라는 세 가지 선택지로 제공합니다. 즉, React Router 7 지원 모델은 단일 기능의 on/off가 아니라 운영 책임의 배치도입니다. 중요한 점은 이것이 단순한 기능 단계표가 아니라는 사실입니다. 세 모드는 "무엇을 할 수 있는가"보다 "누가 무엇을 책임지는가"를 다르게 정의합니다. RSC는 이 책임 배치를 더 명확하게 드러내는 촉매입니다.

이 글은 React Router v7 지원 모델을 RSC 운영 관점에서 다시 읽습니다. 왜 모드 선택에서 반복적으로 혼란이 생기는지, 왜 많은 팀이 도입 초기에 비슷한 장애를 겪는지, 그리고 어떤 순서로 전환해야 조직 비용을 줄일 수 있는지를 탐구합니다. 결론은 단순한 권장안이 아니라, 팀이 직접 판단할 수 있는 기준을 제공하는 것입니다.

## React Router v7 지원 모델에서 혼란이 반복되는 이유

React Router v7 문서만 읽으면 "세 모드 모두 결국 라우팅을 하는 도구"처럼 보일 수 있습니다. 하지만 운영 현장에서는 기능보다 경계가 먼저 충돌합니다. 실제로 혼란이 발생하는 지점은 대체로 아래 네 가지입니다.

- 서버 렌더링과 스트리밍 경로를 누가 소유하는가
- 데이터 로딩과 재검증 규칙을 누가 표준화하는가
- 타입/라우트 계약을 누가 깨지지 않게 보증하는가
- 장애 시 디버깅 동선을 누가 설계하고 유지하는가

이 네 질문에 대한 답은 모드별로 다릅니다. 그런데 의사결정 회의에서는 종종 "RSC 지원 여부" 한 문장으로 축약됩니다. 그 결과, Data Mode로도 해결 가능한 문제를 "불완전"하다고 오해해 전면 전환을 시도하거나, 반대로 Framework Mode가 필요한 규모에서 Library Mode를 유지하며 팀별 규약을 중복 생산하는 상황이 생깁니다.

문제의 본질은 기술 우열이 아니라 운영 비용의 분배 구조입니다. React Router v7 지원 모델을 이해한다는 것은 곧, 우리 조직의 책임 체계를 설계하는 일입니다.

## 왜 RSC를 렌더링 기술로만 보면 실패하는가

RSC는 서버에서 컴포넌트를 렌더링하는 기능으로 소개되곤 합니다. 이 설명은 맞지만 충분하지 않습니다. 실무에서 RSC가 만드는 가장 큰 변화는 렌더링 결과보다 **경계의 강제**입니다. 서버 전용 코드와 클라이언트 전용 코드를 구분해야 하고, 데이터가 어느 레이어에서 보장되는지 계약해야 하며, 로딩과 에러의 처리 단위를 명시해야 합니다.

경계가 정리되지 않은 팀에서 RSC를 먼저 적용하면, 코드 레벨 데모는 성공해도 운영은 오히려 복잡해집니다. 흔한 징후는 다음과 같습니다.

- 동일 데이터에 대한 중복 fetch와 비일관 캐시
- hydration 불일치 재현이 어려운 간헐 장애
- 라우트/컴포넌트 간 책임 경계 모호로 인한 리뷰 충돌
- 배포 후 회귀가 발생해도 원인 소유팀을 특정하기 어려움

즉 React Router v7의 모드 선택은 "어떤 렌더링을 쓸지"보다 "경계를 어떤 계약으로 운영할지"에 가깝습니다. RSC는 새로운 기능이라기보다, 기존에 암묵적으로 덮어뒀던 운영 문제를 표면으로 끌어올리는 장치입니다.

## React Router v7의 세 모드를 RSC 운영 모델로 다시 읽기

### Framework Mode: 런타임과 규약을 함께 통합하는 선택

Framework Mode는 라우팅, 데이터, SSR 경로, 타입 생성, 빌드/배포 파이프라인을 하나의 운영 흐름으로 결합합니다. RSC를 제품 핵심 경로에 두고 장기적으로 운영해야 하는 팀에게 가장 일관된 선택입니다.

강점은 규약의 강제력입니다. 라우트 모듈 경계가 명확해지고, 데이터 로딩과 재검증 정책이 분산되지 않으며, 팀별 관례 차이가 시스템 레벨에서 줄어듭니다. 장애 대응에서도 관측 지점이 집중되기 때문에 MTTD/MTTR 개선 여지가 큽니다.

다만 대가도 큽니다. 기존 인프라와의 접점 정리가 필요하고, 팀별 커스텀 패턴을 표준 관례로 통일하는 데 조정 비용이 듭니다. 따라서 Framework Mode는 "빠르게 붙이는 기능 모드"가 아니라, 운영 일관성을 장기 자산으로 전환하려는 조직적 선택에 가깝습니다.

### Data Mode: 현실적인 점진 도입의 중심축

Data Mode는 loader/action/revalidation을 라우트 단위 계약으로 명시합니다. 프레임워크 전체 전환 부담은 낮추면서도, 운영 사고 비용이 큰 데이터 경계를 먼저 고정할 수 있다는 점이 핵심입니다.

많은 조직에서 Data Mode가 강력한 이유는 기존 코드베이스를 뒤집지 않고도 구조적 이득을 만들기 때문입니다. 중복 요청이 줄고, 에러/재시도 정책이 라우트 단위로 정렬되며, 테스트 기준이 컴포넌트 내부 구현이 아니라 계약 중심으로 이동합니다. 이 변화는 나중에 Framework Mode로 이동할 때 사고방식과 설계를 재사용하게 해 줍니다.

즉 Data Mode는 "타협안"이 아니라, 불확실성이 큰 전환기에 리스크를 낮추는 전략적 거점입니다.

### Library Mode: 빠른 시작의 대가를 미래로 이연하는 선택

Library Mode는 가볍고 유연하며 도입 장벽이 낮습니다. 작은 범위, 짧은 수명, 단일 팀 맥락에서는 높은 생산성을 냅니다. 문제는 이 모드가 조직 기본값이 될 때입니다.

표준 계약이 약한 상태에서 서비스가 확장되면 팀마다 로딩/에러/캐시 정책이 달라지고, 같은 장애를 다른 언어로 설명하는 상황이 반복됩니다. 초기 속도는 빨랐지만, 시간이 지날수록 규약 부채가 누적됩니다. 특히 MFE 전환 조직에서는 이 편차가 릴리즈 리스크로 직결됩니다.

따라서 Library Mode는 나쁜 선택이 아니라 **범위 관리가 필요한 선택**입니다. 예외 모드로 설계하면 장점이 살아나고, 기본 모드로 확장하면 운영 난이도가 급격히 올라갑니다.

## 네트워크·데이터 흐름 관점에서 본 모드 차이

RSC 운영에서는 코드 구조만큼 네트워크 흐름 설계가 중요합니다. 같은 UI라도 요청 분할 방식과 재검증 정책에 따라 체감 성능과 장애 양상이 크게 달라집니다.

HTTP/2 이상의 멀티플렉싱 환경에서 라우트 단위 데이터 계약이 정리되어 있으면, 병렬 요청 효율이 높아지고 waterfall 구간이 줄어듭니다. 반대로 경계가 불명확하면 요청 수는 늘고 캐시 적중률은 낮아집니다. 예를 들어 동일 화면에서 팀별로 API 호출 책임이 흩어지면 요청 횟수가 2~3배까지 증가하고, 사용자에게는 "가끔 느린" 불안정한 경험으로 나타납니다.

RSC 스트리밍 역시 마찬가지입니다. 스트리밍은 응답 시작 시점을 앞당길 수 있지만, 데이터 소유권과 fallback 정책이 정리되지 않으면 부분 렌더링이 오히려 일관성 문제를 키웁니다. React Router v7 지원 모델을 고를 때는 "스트리밍 가능" 여부보다, "스트리밍 실패 시 어떤 경계에서 복구할지"를 먼저 정의해야 합니다.

정리하면, 모드 선택은 API 디자인 취향이 아니라 데이터 흐름의 제어권을 어디에 둘 것인지에 대한 선택입니다. 이 제어권이 명확할수록 사용자 경험의 편차가 줄어듭니다.

## 플랫폼·빌드 관점에서 본 지원 모델의 진짜 차이

RSC 도입 비용은 런타임 코드보다 빌드·배포 체계에서 크게 발생합니다. 특히 모노레포, 다수 스쿼드, MFE 환경에서는 "어떻게 실행하느냐"보다 "어떻게 검증하고 롤백하느냐"가 더 비쌉니다.

Framework Mode는 타입/라우트 계약을 파이프라인에 연결하기 쉽고, 규약 위반을 빌드 단계에서 조기에 차단하기 유리합니다. 반면 초기 설정 복잡도와 도구 의존성이 올라갑니다. Data Mode는 도입 부담이 낮지만, 계약 검증 자동화를 의식적으로 설계하지 않으면 팀별 관례가 다시 분기될 수 있습니다. Library Mode는 초기 속도는 빠르지만, 시간이 지나면 검증 책임이 사람에게 남고 회귀 탐지가 늦어지기 쉽습니다.

이 관점에서 가장 중요한 질문은 "어떤 모드가 더 멋진가"가 아닙니다. "우리 조직이 실패를 가장 빨리 감지하고 가장 싸게 복구할 수 있는가"입니다. React Router v7 지원 모델은 결국 복구 비용 구조를 결정합니다.

## MFE 전환 조직을 위한 현실적인 도입 순서

### 1단계: 모드 논쟁 전에 라우트 계약부터 문서화

먼저 합의해야 하는 것은 기술 선택이 아니라 경계 계약입니다.

- 라우트별 데이터 소유권과 변경 책임
- 재검증 트리거와 우선순위
- 에러 경계 단위(페이지/섹션/컴포넌트)
- 공통 로딩 UX와 실패 시 복구 정책

이 계약이 없으면 어떤 모드를 써도 팀마다 다른 정답이 생깁니다.

### 2단계: Data Mode로 계약을 코드로 고정

다음으로 loader/action/revalidation 중심 패턴을 정착시킵니다. 이 단계의 목적은 "RSC 도입"이 아니라 "데이터 경계 표준화"입니다.

```tsx
// app/routes/project.$id.tsx
export async function loader({ params }: LoaderArgs) {
const project = await getProject(params.id)
return json({ project })
}

export async function action({ request, params }: ActionArgs) {
const form = await request.formData()
await updateProject(params.id, form)
return redirect(`/project/${params.id}`)
}

export default function ProjectRoute() {
const { project } = useLoaderData<typeof loader>()
return <ProjectView project={project} />
}
```

이 코드는 기교가 아니라 계약의 샘플입니다. 핵심은 팀이 "데이터 책임은 라우트에서 선언한다"는 공통 언어를 갖게 된다는 점입니다.

### 3단계: Framework Mode 요소를 선택적으로 흡수

Data Mode가 안정화되면, 운영 자동화 효과가 큰 요소부터 흡수합니다.

- 타입/라우트 계약 자동 검증
- SSR 경로와 배포 파이프라인 결합
- 라우트 단위 성능/오류 지표 표준화
- 장애 재현 절차와 롤백 동선 통일

이 단계부터는 기능 추가보다 운영 비용 절감 효과가 더 크게 나타납니다.

### 4단계: Library Mode를 예외 정책으로 제한

Library Mode를 완전히 금지할 필요는 없습니다. 다만 아래처럼 예외 조건과 만료 조건을 함께 둬야 합니다.

- 단기 실험 기능, 캠페인 페이지, 내부 도구 등으로 범위 제한
- "언제 Data/Framework 표준으로 흡수할지" 명시
- 예외가 누적되면 정기적으로 회수(backlog cleanup) 실행

예외는 허용하되 방치하지 않는 것이 핵심입니다.

## AI 자동화 관점: 어디까지 자동화하고 무엇을 남길 것인가

React Router v7 지원 모델 운영에서 AI 도구는 문서 생성이나 코드 보일러플레이트 작성에 유용하지만, 책임 경계 결정 자체를 대신할 수는 없습니다. 자동화가 효과적인 영역은 패턴이 안정적인 구간입니다.

- 라우트 템플릿 생성(loader/action 기본 구조)
- 계약 문서 초안 생성(입출력·재검증 규칙)
- 규약 점검 체크리스트 자동화(누락된 에러 경계 탐지)
- 릴리즈 전 회귀 시나리오 생성 보조

반대로 자동화에 의존하면 위험한 영역은 다음과 같습니다.

- 비즈니스 정책 우선순위 결정
- 팀 간 책임 분쟁 조정
- 장애 시 의사결정(완화 vs 롤백 vs 기능 제한)

즉 AI는 속도를 올리는 레버이지만, 운영 책임의 소유권을 없애주지는 않습니다. RSC 전환에서 중요한 것은 "더 많이 자동화"가 아니라 "자동화 가능한 경계를 식별"하는 능력입니다.

---

## 장애 대응 시나리오로 검증하는 모드 적합성

정상 시나리오에서는 어떤 모드든 어느 정도 동작합니다. 차이는 장애 시나리오에서 드러납니다. 아래 질문에 얼마나 빠르게 답할 수 있는지가 모드 적합성을 보여줍니다.

- 관측 지표가 라우트 단위로 수집되는가
- 재현 경로가 계약 단위로 정의되어 있는가
- 데이터 불일치 원인을 경계 위반으로 추적 가능한가
- 배포 회귀를 자동 검증하고 즉시 롤백 가능한가

Framework Mode는 구조적으로 이 질문에 유리합니다. Data Mode는 규약 설계가 갖춰져 있으면 대부분 달성할 수 있습니다. Library Mode는 팀 성숙도에 따라 편차가 큽니다. 따라서 조직 규모가 커질수록 "평균 성능"보다 "최악 상황의 복구 비용"으로 모드를 평가해야 합니다.

---

## 트레이드오프

| 항목 | Framework Mode | Data Mode | Library Mode |
|---|---|---|---|
| RSC 운영 적합성 | 매우 높음. 런타임·규약 통합 | 높음. 데이터 경계 중심 최적화 | 낮음~중간. 범위 통제 시 유효 |
| 초기 도입 비용 | 높음 | 중간 | 낮음 |
| 점진 전환 용이성 | 중간 | 가장 높음 | 높음(표준화는 지연) |
| 팀 간 일관성 | 매우 높음 | 규약 수준에 따라 높음 | 팀 편차 큼 |
| 장애 복구 예측 가능성 | 높음 | 중간~높음 | 낮음~중간 |
| 장기 유지보수 비용 | 낮아질 가능성 큼 | 관리 수준에 따라 안정 | 누적 시 급증 가능 |

핵심 해석은 단순합니다.

- 제품 핵심에 RSC를 두고 장기 운영할 계획이면 Framework Mode가 유리합니다.
- 기존 서비스가 크고 리스크가 높다면 Data Mode가 가장 현실적인 시작점입니다.
- Library Mode는 빠른 실험에는 좋지만, 기본값으로 확장하면 규약 부채를 키웁니다.

---

## 마무리하며

React Router 7 지원 모델을 RSC 관점에서 해석하면, 기술 호환성 표가 아니라 조직 운영 설계도라는 결론에 도달합니다. "지원하느냐"보다 중요한 질문은 "어떤 책임을 어디에 둘 것인가"입니다. 이 질문에 먼저 답한 팀은 모드 선택이 단순해지고, 반대로 기능 비교부터 시작한 팀은 전환 후에 경계 부채를 크게 치르게 됩니다.

실무적으로 가장 안전한 경로는 명확합니다. 라우트 계약을 먼저 문서화하고, Data Mode로 데이터 경계를 고정한 뒤, Framework Mode의 통합 이점을 필요한 시점에 흡수하는 방식입니다. Library Mode는 예외적으로 활용하되 수명과 회수 계획을 함께 관리해야 합니다.

결국 React Router v7과 RSC의 조합에서 경쟁력은 "최신 기능을 빨리 켰는가"가 아니라, "장애를 예측 가능한 비용으로 다루는 운영 모델을 만들었는가"에서 결정됩니다. 이 관점으로 보면 모드 선택은 취향 문제가 아니라, 제품과 조직의 생존 전략입니다.

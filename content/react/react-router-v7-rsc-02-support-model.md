## 한눈에 보기

React Router 7 + RSC 실무 운영을 시작할 때 가장 먼저 정리해야 할 질문은 기술 스택이 아닙니다. 운영 경계입니다. 실무에서 실패하는 지점은 대부분 "RSC를 쓸 수 있느냐"가 아니라 "누가 어디서 무엇을 책임지느냐"가 불명확할 때 발생합니다.

핵심만 압축하면 다음과 같습니다.

- React Router 7은 RSC를 단일 방식으로 강제하지 않고, **Framework / Data / Library** 세 가지 운영 모델을 제공합니다.
- Framework Mode는 팀 전체의 경계 규칙을 구조로 고정하기 좋고, Data Mode는 기존 서비스 안정성을 유지하며 점진 전환하기 좋습니다.
- Library Mode는 빠르고 가볍지만, RSC 시대에는 자율이 곧 운영 편차가 되기 쉬워 별도 가드레일이 필수입니다.
- 모드 선택의 정답은 기술 취향이 아니라 **조직 복잡도, 전환 여력, 릴리스 리듬, 장애 허용도**로 결정됩니다.

실무에서는 다음 순서가 안전합니다.

1. 라우트별 데이터 소유권 문서화
2. loader/action/revalidation 규칙 통일
3. 에러/로딩/스트리밍 UX의 책임 계층 고정
4. 모드 전환과 배포 파이프라인 정렬

즉, React Router 7 + RSC의 성패는 기능 조합보다 운영 설계의 선명도에서 갈립니다.

## 들어가며

React Router 7 + RSC 실무 운영이 어려운 이유는 단순히 서버에서 렌더링한다는 문장 때문이 아닙니다. 프론트엔드 팀이 오랫동안 암묵적으로 넘겨온 질문, 즉 "이 로직은 어디에서 실행되어야 하는가"를 더 이상 미룰 수 없게 만들었기 때문입니다.

기존 SPA 중심 개발에서는 화면 전환과 상태 동기화가 주된 난제였습니다. 하지만 RSC를 고려하기 시작하면 문제의 축이 이동합니다.

- 데이터는 서버에서 확정할 것인지, 클라이언트에서 보정할 것인지
- 사용자 액션 이후 어떤 단위에서 재검증을 수행할 것인지
- 로딩·에러·부분 스트리밍을 누가 책임지고 어디서 관찰할 것인지
- 팀이 커져도 같은 규칙이 유지될 것인지

이 질문에 조직 차원의 답이 없으면, 기술적으로는 동작해도 운영적으로는 금방 흔들립니다. 특히 MFE 전환 중이거나 도메인 팀이 분리된 환경에서는 문제가 더 빠르게 드러납니다. 각 팀이 "최적"이라 믿는 방식으로 경계를 따로 설계하기 때문입니다.

React Router 7의 가치는 바로 이 지점에서 드러납니다. 단일 API를 던져주고 알아서 조합하라고 하지 않습니다. 대신 모드라는 형태로 운영 모델을 제공합니다. 중요한 점은, 이 모드가 단순 개발 경험의 차이가 아니라 책임 분배 방식의 차이라는 사실입니다.

따라서 질문은 이렇게 바뀌어야 합니다.

> React Router 7이 RSC를 지원하느냐가 아니라, 우리 조직이 어떤 모드에서 어떤 책임 모델을 고정할 수 있느냐입니다.

이 글은 모드를 기능 목록이 아니라 실무 운영 관점으로 해석합니다. 어디서 비용이 발생하고, 어디서 속도가 붙으며, 어떤 순서로 전환해야 실패 확률이 낮아지는지에 집중합니다.

## 왜 RSC 논의는 "모드"부터 시작해야 하는가

RSC 자체는 성능과 개발 경험 모두에 잠재적 이점이 있습니다. 서버에 더 가까운 위치에서 데이터 결정을 내릴 수 있고, 클라이언트 번들 부담을 줄일 수 있으며, 필요한 단위만 전송하는 설계도 가능합니다. 문제는 "좋은 기술"이라는 사실이 "좋은 운영"을 보장하지 않는다는 점입니다.

실패 패턴은 대부분 비슷합니다.

- 기존 클라이언트 fetch가 남아 있는데 서버 경로에서도 같은 데이터를 조회합니다.
- loader와 컴포넌트 훅이 동일 리소스를 각자 소유하려고 합니다.
- 액션 이후 재검증 규칙이 팀마다 달라서 데이터 일관성이 깨집니다.
- 에러 경계가 페이지마다 달라 장애 시 사용자 경험이 불안정해집니다.

이 상황에서 "RSC가 어렵다"고 결론 내리기 쉽지만, 실제 원인은 경계 합의 부재입니다. 기능을 추가했지만 책임 배치를 통합하지 않았기 때문입니다.

React Router 7의 모드는 바로 이 통합의 강도를 다르게 제공합니다.

- **Framework Mode**: 라우트 모듈, 실행 경계, 빌드 관례까지 묶어 운영 규칙을 강하게 고정합니다.
- **Data Mode**: loader/action/revalidation 중심으로 데이터 경계부터 표준화합니다.
- **Library Mode**: 최소 라우팅 도구를 제공하고, 운영 규칙은 팀이 별도로 구축합니다.

결국 모드 선택은 개발자 취향이 아니라 운영 통제 전략입니다.

---

## Framework Mode: 경계 일관성을 시스템 기본값으로 만들 때

Framework Mode는 "잘하는 사람이 버티는 팀"에서 "누가 와도 같은 결과가 나오는 팀"으로 넘어갈 때 가장 강력합니다. RSC 도입이 길어질수록 인력 교체, 도메인 확장, 릴리스 압박이 반복되는데, 이때 개별 숙련도에 의존한 설계는 빠르게 한계를 드러냅니다.

Framework Mode의 실무적 장점은 다음처럼 정리할 수 있습니다.

- 라우트 단위 책임 구조가 프로젝트 전체에서 일관됩니다.
- 에러/로딩/스트리밍 처리 방식이 공통 계약으로 고정됩니다.
- 배포 및 런타임 관례가 정렬되어 팀 간 편차가 줄어듭니다.
- 신규 인력 온보딩 시 "코드 읽기"보다 "규칙 이해"가 쉬워집니다.

반대로 초기 비용도 분명합니다.

- 기존 코드의 책임 위치를 재배치해야 합니다.
- 팀 컨벤션 합의와 문서화가 필요합니다.
- 빌드/배포 파이프라인에서 규약 위반을 감지하는 장치를 추가해야 합니다.

하지만 이 비용은 장기 운영 관점에서 선투자 성격이 강합니다. 특히 도메인 팀이 많거나 릴리스 빈도가 높은 조직에서는, 초기에 통합한 규칙이 이후 장애 비용과 조정 비용을 크게 줄입니다. RSC를 제품 핵심 역량으로 가져갈 계획이라면 Framework Mode는 "무거운 선택"이 아니라 "운영 리스크를 앞당겨 정리하는 선택"에 가깝습니다.

---

## Data Mode: 서비스 안정성을 지키며 전환 속도를 확보할 때

실무에서 가장 현실적인 출발점은 종종 Data Mode입니다. 이유는 간단합니다. 이미 운영 중인 서비스는 항상 일정과 트래픽, 레거시 의존성을 갖고 있기 때문입니다. 아키텍처적으로 더 나은 길이 보여도, 한 번에 바꾸면 사업 리스크가 커집니다.

Data Mode의 핵심 가치는 "전면 개편 없이 경계부터 정렬"할 수 있다는 점입니다.

- 읽기 책임을 loader에서 명확히 선언합니다.
- 쓰기 책임과 후속 동기화를 action 중심으로 통합합니다.
- 재검증 조건을 라우트 계약으로 표준화합니다.
- 에러/로딩 상태를 라우트 단위로 일관되게 표현합니다.

이 구조는 RSC를 즉시 전면 도입하지 않아도 효과가 있습니다. 팀이 먼저 데이터 경계 언어를 공유하게 만들기 때문입니다. 경계 언어가 정리되면 이후 RSC 확장 시 논쟁이 줄어듭니다. "어디서 실행할지"보다 "이미 정한 책임을 어떤 런타임으로 옮길지"의 문제로 단순화되기 때문입니다.

주의할 점도 있습니다. Data Mode를 오래 중간 상태로 유지하면, 모드 혼합 구간에서 복잡도가 누적됩니다. 따라서 Data Mode는 종착지가 아니라 전환 단계로 관리하는 편이 안전합니다. 전환 목표와 종료 조건을 미리 합의해야 합니다.

예를 들어 아래처럼 기준을 명확히 두는 방식이 좋습니다.

- 핵심 도메인 라우트 80% 이상이 loader/action 계약을 충족하면 2단계 전환 시작
- 재검증 규칙 위반 건수가 주간 기준 임계치 이하일 때 Framework 관례 도입
- 공통 에러 경계 템플릿 적용률이 일정 수준을 넘으면 서버 경계 확대

이렇게 운영 지표와 연결하면 전환이 선언이 아니라 실행이 됩니다.

---

## Library Mode: 빠른 시작의 장점과 자율 비용의 현실

Library Mode는 여전히 유효한 선택입니다. 작은 서비스, 단일 팀, 제한된 도메인에서는 가장 빠르게 가치를 만들 수 있습니다. 필요한 기능만 가져다 쓰고 기존 인프라를 유지할 수 있기 때문입니다.

다만 RSC를 본격 운영하는 환경에서는 자율의 비용이 커집니다. 별도 통제 장치가 없으면 다음 문제가 반복됩니다.

- 팀마다 데이터 접근 패턴이 달라 디버깅 난도가 올라갑니다.
- 액션 이후 갱신 타이밍이 제각각이라 사용자 화면이 불안정해집니다.
- 에러/로딩 UX 표준이 무너져 제품 품질 인상이 약해집니다.
- 코드 리뷰가 기능 중심으로 흐르며 경계 위반을 놓치기 쉽습니다.

따라서 Library Mode를 택했다면 "최소 도구"만 선택한 것이 아니라 "운영 규약을 직접 설계할 책임"도 함께 선택한 것입니다. 안전하게 쓰려면 최소한 아래 네 가지는 필요합니다.

- 라우트 데이터 계약 문서 템플릿
- 재검증 정책 체크리스트
- 공통 에러/로딩 표현 규약
- 코드 리뷰 시 경계 위반 탐지 항목

정리하면 Library Mode는 나쁜 선택이 아니라 조건부 선택입니다. 범위가 작고 책임 경계가 명확하며, 팀이 운영 규칙을 지속적으로 유지할 자신이 있을 때 가장 효율적입니다.

## 실무 운영의 핵심: 기술 우열보다 전환 순서

모드 선택 토론은 종종 "어느 모드가 더 진보적이냐"로 흐릅니다. 하지만 실제로 장애를 줄이고 생산성을 높이는 질문은 다릅니다.

- 지금 우리 팀의 가장 큰 리스크는 성능인가, 경계 불일치인가
- 릴리스 일정 안에서 허용 가능한 구조 변경 폭은 어느 정도인가
- 팀 간 계약을 강제할 운영 장치가 이미 있는가
- 6개월 뒤 팀 확장 시 현재 구조가 버틸 수 있는가

이 질문에 대한 답이 불분명하다면, 최신 기술을 빠르게 채택하는 것보다 운영 일관성을 먼저 확보하는 편이 낫습니다. RSC는 화려한 기능이 아니라 책임 재배치 기술이기 때문입니다. 책임 재배치 없이 기능만 도입하면 복잡도만 증가합니다.

## MFE 조직에서 특히 주의할 패턴

MFE 환경에서는 팀마다 배포 주기와 우선순위가 다릅니다. 이때 가장 위험한 패턴은 "전사 모드 합의 없이 팀별 최적화"입니다. 단기적으로는 빨라 보이지만 통합 시점에 비용이 폭발합니다.

흔한 실패 흐름은 다음과 같습니다.

1. 팀별로 RSC·Data API를 부분 도입합니다.
2. 라우트 경계 정책이 서로 달라집니다.
3. 공통 레이어를 각 팀이 중복 구현합니다.
4. 통합 릴리스에서 충돌과 장애가 발생합니다.

안전한 전환은 반대로 진행해야 합니다.

1. 전사 공통으로 라우트 경계 언어를 정의합니다.
2. loader/action/revalidation 계약을 문서와 리뷰 기준에 반영합니다.
3. 공통 에러/로딩/관측 포맷을 통일합니다.
4. 그다음 팀별 속도에 맞춰 모드 전환을 진행합니다.

핵심은 기술 도입 순서보다 조직 합의 순서입니다. RSC는 코드 문제처럼 보이지만 실제로는 협업 프로토콜 문제인 경우가 훨씬 많습니다.

## 라우트 경계를 고정하는 최소 예시

아래 예시는 문법보다 책임 선언에 초점을 둔 형태입니다. 읽기와 쓰기를 같은 레이어에서 우연히 처리하지 않고, 라우트 계약으로 분리하는 것이 목적입니다.

```tsx
// routes/product.tsx
import { json } from "react-router";
import type { LoaderFunctionArgs, ActionFunctionArgs } from "react-router";

export async function loader({ params }: LoaderFunctionArgs) {
const product = await getProduct(params.id!); // 읽기 책임
return json({ product });
}

export async function action({ request, params }: ActionFunctionArgs) {
const form = await request.formData();
await updateProduct(params.id!, form); // 쓰기 책임
return json({ ok: true });
}
```

이 방식의 실무적 이점은 세 가지입니다.

- 데이터 흐름의 의도를 라우트 수준에서 읽을 수 있습니다.
- 재검증 규칙을 액션 결과와 연결해 테스트하기 쉽습니다.
- 이후 RSC 경계 확장 시 중복 fetch 가능성을 줄일 수 있습니다.

코드는 짧지만 운영 효과는 큽니다. 중요한 것은 API 활용 자체가 아니라 책임 위치를 명문화하는 습관입니다.

## 트레이드오프

아래 표는 React Router 7 + RSC를 모드별로 선택할 때 발생하는 교환 관계를 실무 관점으로 정리한 것입니다.

| 모드 | 얻는 것 | 지불하는 것 | 적합한 상황 |
|---|---|---|---|
| Framework Mode | 경계 일관성, 팀 간 계약 안정성, 장기 유지보수성 | 초기 재구조화 비용, 컨벤션 합의 시간, 마이그레이션 부담 | 다수 팀이 함께 운영하고 RSC/SSR을 핵심 역량으로 삼아야 할 때 |
| Data Mode | 서비스 안정성 유지, 점진 전환, 데이터 경계 표준화 | 중간 상태 장기화 위험, 모드 혼합 복잡도, 목표 흐림 가능성 | 운영 중 제품을 크게 흔들지 않고 전환 기반을 만들 때 |
| Library Mode | 빠른 도입, 낮은 침습성, 높은 유연성 | 표준 부재 시 파편화, 품질 편차, 팀 확장 시 운영 부채 | 소규모 범위·명확한 책임의 서브앱 또는 실험 트랙 |

표를 볼 때 가장 중요한 포인트는 우열이 아니라 맥락입니다.

- 조직 복잡도가 빠르게 증가하는 시기에는 Framework Mode의 선투자가 오히려 비용을 줄입니다.
- 사업 일정이 빡빡하고 안정성이 절대 조건이면 Data Mode가 가장 현실적입니다.
- 실험 속도가 목표이고 범위가 제한적이면 Library Mode가 효율적입니다.

추가로, 어떤 모드를 택하든 공통으로 지켜야 할 원칙이 있습니다.

- 경계 합의는 문서가 아니라 리뷰·테스트·배포 단계에서 강제되어야 합니다.
- 재검증 정책은 팀별 자율 항목이 아니라 제품 품질 항목으로 다뤄야 합니다.
- 에러/로딩/스트리밍 UX는 기능팀이 아닌 플랫폼 계약으로 관리해야 합니다.

이 세 가지를 놓치면 모드 장점이 빠르게 상쇄됩니다.

## 운영 체크리스트: 전환 전에 반드시 합의할 질문

아래 질문에 팀이 명확히 답할 수 있다면 전환 성공 확률이 높아집니다.

1. 라우트별 데이터 소유권을 문서와 코드에서 동시에 확인할 수 있는가
2. 액션 이후 재검증 정책이 전역에서 일관되게 동작하는가
3. 에러/로딩/스트리밍 UX 책임 계층이 명확한가
4. MFE 팀 간 입출력 계약과 실패 시나리오가 정의되어 있는가
5. 신규 입사자가 1주 내 라우트 경계를 설명할 수 있는가
6. Library Mode 예외 허용 기준이 문서화되어 있는가
7. 관측 지표(재검증 실패율, 중복 fetch 비율, 경계 위반 PR 비율)를 추적하고 있는가

이 질문에 대한 답이 약하다면, 프레임워크 기능을 더 붙이기 전에 운영 계약부터 강화하는 편이 안전합니다.

## 마무리하며

React Router 7과 RSC를 함께 다룰 때 가장 큰 오해는 "지원 여부"에만 집중하는 것입니다. 실무에서는 지원 여부보다 운영 일관성이 더 큰 차이를 만듭니다.

React Router 7의 강점은 단일 정답을 강요하지 않는 점입니다. Framework, Data, Library라는 선택지를 통해 조직 상황에 맞는 전환 경로를 설계할 수 있습니다. 대신 대가도 분명합니다. 어떤 모드든 책임 배치에 대한 합의 없이 도입하면, 기술 이점보다 운영 혼선이 먼저 드러납니다.

React Router 7 + RSC 실무 운영에서 결국 좋은 선택은 최신 기술을 가장 빨리 쓰는 선택이 아닙니다. 우리 조직이 감당 가능한 변경 비용 안에서 경계 일관성을 가장 빠르게 확보하는 선택입니다. 이 기준으로 보면 모드 선택은 프론트엔드 취향 토론이 아니라 제품 운영 전략입니다.

RSC 시대의 경쟁력은 특정 API를 아는지보다, 경계를 어떻게 설계하고 어떻게 지키는지에서 결정됩니다. React Router 7은 그 경계를 설계할 수 있는 좋은 도구입니다. 이제 필요한 것은 도구 사용법보다 운영 설계의 해상도입니다.

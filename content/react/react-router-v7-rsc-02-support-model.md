## 한눈에 보기

React Router 7에서 RSC를 이야기할 때 가장 먼저 붙잡아야 하는 사실은 단순합니다.
**React Router 7은 “RSC on/off 스위치”를 제공하는 제품이 아니라, 서로 다른 운영 모델(Framework/Data/Library) 위에 RSC와의 접점을 다르게 배치하는 라우팅 시스템**이라는 점입니다.

실무에서 문제가 되는 지점도 늘 비슷합니다.

- “우리도 RSC 지원하나요?”라는 질문은 많지만,
- “우리는 어떤 모드에서 어떤 책임 분리를 선택했나요?”라는 질문은 적습니다.

그래서 팀은 기술 자체보다 운영에서 흔들립니다.
중복 fetch, 경계 중복(서버와 클라이언트에서 둘 다 데이터 소유), 에러 처리 일관성 붕괴, 재검증 정책 충돌이 반복됩니다.
이 글은 바로 그 지점을 “왜” 중심으로 정리합니다.

핵심 결론은 다음과 같습니다.

1. **Framework Mode**는 RSC를 포함한 서버-클라이언트 경계 운영을 가장 일관되게 다룰 수 있는 선택입니다.
2. **Data Mode**는 기존 앱을 크게 흔들지 않으면서, loader/action/revalidation이라는 데이터 경계를 먼저 표준화하는 현실적 발판입니다.
3. **Library Mode**는 빠르고 가볍지만, RSC 시대의 핵심인 “경계의 합의”를 팀 차원에서 별도로 강제하지 않으면 파편화 리스크가 큽니다.
4. 따라서 모드 선택은 “기술 취향”이 아니라 “조직의 운영 성숙도와 변경 비용”의 함수입니다.

## 들어가며

1편에서 다뤘던 메시지는 분명했습니다.
RSC 시대에는 컴포넌트 설계보다 **경계 설계**가 더 중요해진다는 점입니다.

왜냐하면 RSC는 본질적으로 “어디서 실행할 것인가”의 문제를 전면으로 끌어올리기 때문입니다.
과거에는 클라이언트 중심 렌더링에서 라우터가 주로 화면 전환을 담당했다면, 이제 라우팅은 곧 다음의 질문을 동반합니다.

- 이 데이터는 서버에서 소유할 것인가, 클라이언트에서 소유할 것인가?
- 사용자 상호작용 이후 어떤 계층이 재검증을 트리거할 것인가?
- 로딩/에러/스트리밍의 사용자 경험을 누가 책임질 것인가?
- 팀이 바뀌어도 이 규칙이 유지되는가?

이 지점에서 React Router 7은 중요한 변화를 제공합니다.
“라우터 API 세트”를 주는 것을 넘어, **운영 모델 자체를 모드로 제공**합니다.
그리고 RSC와의 실제 궁합은 바로 이 모드에서 갈립니다.

실무에서는 여기서 오해가 시작됩니다.
많은 팀이 “React Router 7이 RSC를 지원한다”는 문장을 “우리 앱에 바로 얹을 수 있다”로 해석합니다.
하지만 실제로는 “우리 팀의 현재 모드에서 어떤 책임을 어디로 배치할지”를 먼저 결정하지 않으면, 지원 여부가 곧바로 생산성으로 이어지지 않습니다.

결국 질문은 이렇게 바뀌어야 합니다.

> “React Router 7이 RSC를 지원하냐”가 아니라
> “우리 조직은 어떤 모드를 통해 RSC 시대의 경계를 관리할 것이냐”입니다.

이 글은 그 질문에 답하기 위해, 모드를 기능 비교표가 아니라 **운영 철학의 차이**로 해석합니다.

---

## 왜 모드 구분이 RSC 논의의 출발점인가

RSC의 장점은 잘 알려져 있습니다.
서버에서 더 많은 일을 처리해 클라이언트 부담을 줄이고, 데이터 접근을 서버에 가깝게 배치하며, 전송 단위를 효율화할 수 있습니다.

그런데 팀이 체감하는 현실은 다릅니다.
좋은 점보다 먼저 “복잡해졌다”를 느끼는 경우가 많습니다.
그 이유는 기술 난이도만이 아닙니다. **책임의 경계가 재편되기 때문**입니다.

예를 들어 보겠습니다.

- 기존에는 페이지 진입 시 클라이언트 훅에서 fetch했습니다.
- RSC를 도입하면 서버 경로에서 일부 데이터를 미리 가져옵니다.
- 그런데 기존 loader/action 또는 클라이언트 캐시 전략이 그대로 남아 있습니다.
- 결과적으로 동일 리소스에 대한 중복 요청과 불일치가 생깁니다.

문제의 본질은 “RSC가 어렵다”가 아닙니다.
**경계를 통합할 운영 모델 없이 기능만 추가했기 때문**입니다.

React Router 7의 모드는 이 통합 수준을 다르게 제공합니다.

- Framework Mode: 런타임/라우트 모듈/빌드 관례까지 한 묶음으로 강하게 정렬합니다.
- Data Mode: 데이터 경계(loader/action/revalidation)를 중심으로 먼저 질서를 세웁니다.
- Library Mode: 최소 도구를 제공합니다. 질서는 팀이 외부 규약으로 만들어야 합니다.

그래서 같은 “RSC 도입”이라도 팀마다 결과가 다릅니다.
도구가 아니라 운영 모델이 달랐기 때문입니다.

## React Router 7 + RSC를 모드별로 해석하기

### 1) Framework Mode: RSC 시대의 “표준 운영 체계”를 원하는 팀

Framework Mode를 실무 관점에서 한 문장으로 정의하면 이렇습니다.
**“기술 기능”보다 “팀 운영 일관성”을 먼저 확보하는 선택**입니다.

왜 Framework Mode가 RSC와 잘 맞느냐는 질문에 답하려면, RSC의 실패 패턴을 보면 됩니다.

- 서버/클라이언트 경계가 팀마다 달라짐
- 라우트 단위 데이터 소유권이 문서화되지 않음
- 에러와 로딩 UX가 라우트마다 제각각
- 타입과 모듈 경로 규약이 깨지며 온보딩 비용 증가

Framework Mode는 이 패턴을 “개인 역량”이 아니라 “시스템 구조”로 제어합니다.
즉, 잘하는 사람이 있어서 버티는 구조가 아니라, 평균적인 팀 생산성을 끌어올리는 구조입니다.

특히 규모가 커질수록(예: 20~30명 이상의 프론트엔드 조직) 이 차이는 더 커집니다.
개발자 개인이 아니라 **조직의 변동성**이 문제의 중심이 되기 때문입니다.
신규 인원이 들어와도 동일한 라우트 계약, 동일한 데이터 책임, 동일한 배포 파이프라인을 따를 수 있어야 합니다.

물론 비용이 없습니다라고 말하면 거짓입니다.
Framework Mode의 초기 비용은 분명합니다.

- 기존 구조를 재정렬해야 하고
- 팀 컨벤션을 합의해야 하며
- 빌드/배포/타입 생성 흐름을 맞춰야 합니다.

하지만 RSC를 제품 핵심으로 밀 계획이라면, 이 비용은 “초기 도입세”에 가깝습니다.
나중에 터질 불일치를 앞당겨 한 번에 정리하는 것에 가깝습니다.

---

### 2) Data Mode: “당장 뒤집지 않되, 경계부터 맞추는” 전환 전략

Data Mode는 실무에서 가장 자주 선택되는 중간 지대입니다.
이 선택이 유효한 이유는 간단합니다. 대부분의 팀은 “지금 돌아가는 서비스”를 운영 중이기 때문입니다.

RSC의 철학이 맞다는 것을 알아도, 전면 전환은 현실적으로 어렵습니다.

- 릴리스 일정이 고정되어 있고
- 레거시 화면이 많고
- MFE나 다수 도메인 팀이 동시에 움직이고
- 인프라 변경 여력이 제한적입니다.

이때 Data Mode는 “기술 타협”이 아니라 “운영 순서의 최적화”가 됩니다.
즉, RSC를 바로 전면 도입하지 않더라도, 먼저 다음을 정렬할 수 있습니다.

- loader/action 책임 분리
- 재검증 규칙 통일
- 라우트 단위 에러/로딩 표준화
- 데이터 소유권 문서화

이 단계가 중요한 이유는 RSC의 본질과 맞닿아 있기 때문입니다.
RSC는 결국 데이터 흐름과 실행 위치를 명확히 나누는 방식인데, Data Mode는 그 전제를 미리 준비하게 만듭니다.

그래서 Data Mode는 “덜 진보한 선택”이 아닙니다.
오히려 많은 팀에서 **실패 확률을 낮추는 현실적인 시퀀스**입니다.
운영을 흔들지 않고 사고방식을 먼저 바꾸는 방법입니다.

---

### 3) Library Mode: 빠르고 가볍지만, RSC 시대에는 “자율의 비용”이 커짐

Library Mode는 여전히 유효합니다.
작은 앱, 단순한 도메인, 명확한 팀 책임에서는 매우 효율적입니다.
필요한 만큼만 라우터를 쓰고 나머지는 기존 인프라와 패턴을 유지할 수 있습니다.

문제는 RSC 관점에서입니다.
RSC는 자동으로 경계를 정리해주지 않습니다.
오히려 경계를 잘못 설계하면 복잡성을 더 노출합니다.

Library Mode에서 흔한 실무 리스크는 다음과 같습니다.

- 데이터 패턴이 팀마다 달라짐
- 재검증 트리거 기준이 제각각
- 에러/로딩 UX 일관성이 무너짐
- 컴포넌트 단위 최적화가 시스템 단위 비효율로 전환됨

즉, Library Mode는 자유를 많이 주지만, RSC 시대에는 그 자유가 곧 **운영 부채**가 되기 쉽습니다.
그래서 Library Mode를 선택한다면 반드시 보완이 필요합니다.

- 라우트 계약 문서
- 데이터 소유권 정책
- 공통 에러/로딩 규약
- 코드리뷰 체크리스트

이 보완 장치가 없다면, 처음엔 빠르지만 일정 시점 이후 속도가 급격히 떨어집니다.
코드가 느려지는 것이 아니라 의사결정이 느려집니다.

## 실무 의사결정: “어떤 모드가 더 좋은가”가 아니라 “우리에게 어떤 순서가 맞는가”

실무에서는 기술 우열 논쟁이 자주 벌어집니다.
하지만 모드 선택에서 더 중요한 것은 우열이 아니라 **순서**입니다.

질문을 이렇게 바꾸면 훨씬 선명해집니다.

- 우리는 지금 경계가 무너져서 장애를 겪고 있는가?
- 조직은 공통 규약을 강제할 준비가 되어 있는가?
- 서비스 안정성을 해치지 않고 바꿀 수 있는 단위는 어디인가?
- 6개월 뒤 인원/도메인 확장을 견딜 수 있는가?

이 질문들에 “아직”이 많다면 Data Mode 출발이 합리적입니다.
반대로 이미 표준화 요구가 강하고 RSC/SSR을 핵심 역량으로 가져가야 한다면 Framework Mode가 더 빠른 길일 수 있습니다.

Library Mode는 “아무 때나”가 아니라 “조건이 맞을 때만” 안전합니다.
작은 범위, 낮은 복잡도, 명확한 책임 경계가 있을 때만 그렇습니다.

## MFE 전환 조직에서의 적용: 왜 단계적 전환이 특히 중요한가

MFE 전환 조직에서는 각 도메인 팀의 릴리스 리듬이 다릅니다.
이 구조에서 가장 위험한 패턴은 다음입니다.

1. 모드 결정 없이 팀별로 기능 도입
2. 라우트 경계 정책 미합의
3. 공통 레이어(에러/로딩/재검증) 중복 구현
4. 통합 시점에 충돌 폭발

RSC 도입은 이 충돌을 더 빨리 드러냅니다.
즉, 숨겨진 불일치를 조기에 노출하는 “스트레스 테스트”가 됩니다.

그래서 MFE 조직에서는 아래 순서가 안전합니다.

- **1단계: Data Mode 관점의 경계 문서화**
- 라우트별 데이터 소유권
- 액션 이후 재검증 기준
- 실패 시 에러 경계 책임자
- **2단계: 공통 계약 자동화**
- 타입/테스트/리뷰 체크에 계약 반영
- **3단계: Framework Mode 요소 점진 흡수**
- 라우트 모듈 관례
- 빌드/배포 표준화
- 팀 간 온보딩 비용 최소화
- **4단계: Library Mode 사용 조건 명시**
- 단순 서브앱 예외로 제한
- 본선 도메인에는 운영 규약 강제

핵심은 기술 도입이 아니라 **운영 전환 설계**입니다.
RSC는 기능이 아니라 체계의 문제이기 때문입니다.

## 라우트 경계를 먼저 고정하는 예시

아래 예시는 Data Mode에서 읽기/쓰기 책임을 라우트 레벨에 명확히 두는 방식입니다.

```tsx
// routes/product.tsx
import { json } from "react-router";
import type { LoaderFunctionArgs, ActionFunctionArgs } from "react-router";

export async function loader({ params }: LoaderFunctionArgs) {
const product = await getProduct(params.id!); // 읽기 책임
return json({ product });
}

export async function action({ request, params }: ActionFunctionArgs) {
const form = await request.formData();
await updateProduct(params.id!, form); // 쓰기 책임
return json({ ok: true });
}
```

이 코드의 포인트는 API 문법이 아닙니다.
**읽기(loader)와 쓰기(action), 그리고 이후 재검증의 책임이 라우트 경계에서 명시된다**는 점입니다.
RSC를 당장 전면 도입하지 않더라도, 이러한 책임 모델이 정리되어야 다음 단계가 안전해집니다.

## 트레이드오프

React Router 7 + RSC에서 중요한 것은 “무조건 좋은 모드”가 아니라, 팀이 어떤 비용을 감수할지 명확히 아는 것입니다.
아래 표는 모드별 교환 관계를 실무 관점으로 압축한 것입니다.

| 모드 | 얻는 것 | 지불하는 것 | 적합한 팀 상황 |
|---|---|---|---|
| Framework Mode | 라우트/데이터/런타임/배포 일관성, 팀 간 계약 안정성, 장기 유지보수성 | 초기 도입 비용, 규약 합의 시간, 기존 코드 재배치 | 팀 규모가 크고(다수 스쿼드), RSC/SSR을 핵심 역량으로 운영해야 하는 경우 |
| Data Mode | 기존 서비스 안정성 유지, 점진 전환 가능, 경계 표준화 빠른 시작 | 중간 상태 장기화 가능성, 모드 혼합 구간 복잡도, 전환 지연 리스크 | 운영 중인 제품을 흔들지 않으면서 경계 모델을 먼저 고정해야 하는 경우 |
| Library Mode | 최소 침습, 빠른 도입, 높은 유연성 | 표준 부재 시 파편화, 장기 운영 비용 증가, 팀 확장 시 편차 확대 | 범위가 작고 책임 경계가 명확한 서브앱/실험 영역 |

표에서 핵심은 우열이 아니라 **순서와 맥락**입니다.
- 조직 복잡도를 시스템으로 흡수해야 하면 Framework Mode가 유리합니다.
- 당장 안정성을 지키며 전환해야 하면 Data Mode가 현실적입니다.
- 빠른 실험이 목표라면 Library Mode가 유효하지만, 본선 도메인에는 별도 가드레일이 필요합니다.

## 실무 체크리스트: 도입 전 반드시 답해야 할 질문

RSC 도입 혹은 React Router 7 모드 전환을 시작하기 전에, 아래 질문에 팀이 합의되어야 합니다.

1. 우리 팀은 라우트별 데이터 소유권을 문서로 설명할 수 있는가?
2. 액션 이후 재검증 정책이 전역에서 일관적인가?
3. 에러/로딩 UX의 책임 계층이 명확한가?
4. MFE 팀 간 경계 계약(입력/출력/실패 시나리오)이 있는가?
5. 신규 입사자가 1주 내에 라우트 구조를 이해할 수 있는가?
6. “Library 예외”를 허용할 기준이 문서화되어 있는가?

이 질문에 대한 답이 약할수록, 기술 도입 속도보다 **운영 합의 속도**를 먼저 끌어올려야 합니다.

## 마무리하며

React Router 7의 RSC 수용을 “지원/미지원”으로 말하면 대부분 틀립니다.
정확한 표현은 이것입니다.

> React Router 7은 RSC 시대를 위한 단일 해법을 강제하지 않고,
> 서로 다른 운영 모델(Framework/Data/Library)을 통해 팀이 책임 배치를 선택하도록 만든 구조입니다.

그래서 좋은 선택은 “최신 기술을 가장 빨리 쓰는 선택”이 아닙니다.
**우리 조직이 감당 가능한 변경 비용 안에서, 경계의 일관성을 가장 빨리 확보하는 선택**입니다.

RSC는 마법이 아닙니다.
라우터도 자동 정답 생성기가 아닙니다.
결국 성패는 경계를 어디에 두고, 그 경계를 누가 어떻게 지키는지에 달려 있습니다.

실무 관점에서 보면, React Router 7은 그 경계를 설계할 수 있는 매우 좋은 도구입니다.
다만 도구만으로는 부족하고, 모드 선택을 포함한 운영 설계가 반드시 따라와야 합니다.

다음 단계에서 진짜 중요한 질문은 이것입니다.

- loader/action과 RSC 데이터 흐름의 책임을 어떻게 분리할 것인가?
- 중복 fetch와 캐시 충돌을 조직적으로 어떻게 차단할 것인가?
- “개발자 개인의 숙련도”가 아니라 “시스템 기본값”으로 어떻게 고정할 것인가?

이 질문에 답하기 시작하면, React Router 7 + RSC는 유행어가 아니라 팀의 경쟁력이 됩니다.

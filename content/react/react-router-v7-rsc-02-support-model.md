## 한눈에 보기

- React Router 7에서 RSC를 이야기할 때 핵심은 "지원 여부"가 아니라 **어떤 모드에서 어떤 운영 책임을 가져가느냐**입니다.
- Framework / Data / Library 모드는 API 취향 차이가 아니라 **런타임, 데이터 경계, 배포 복잡도, 장애 대응 방식**의 차이입니다.
- 실무에서 가장 먼저 해야 할 일은 RSC 도입이 아니라 **라우트 경계 계약(데이터 소유권·재검증 규칙·에러 경계)을 문서화**하는 것입니다.
- 대규모 팀에서는 대개 `Data Mode로 경계 표준화 → Framework Mode로 운영 통합` 순서가 리스크 대비 효율이 좋습니다.
- MFE 전환 팀이라면 Library Mode를 기본값으로 두기보다, **예외 허용 모드**로 제한하는 편이 장기 유지보수에 유리합니다.

## 들어가며

RSC(React Server Components)를 처음 검토할 때 많은 팀이 같은 질문을 던집니다.

> “그래서 React Router 7은 RSC를 지원하나요, 안 하나요?”

문제는 이 질문이 너무 넓다는 점입니다. 실제 운영에서는 지원/미지원 이분법이 거의 도움이 되지 않습니다. 같은 "지원"이라는 단어 안에도 서버 렌더링 경로를 누가 책임지는지, 데이터 재검증은 어디서 표준화하는지, 장애가 났을 때 팀이 어디를 봐야 하는지 같은 현실적인 차이가 크게 숨어 있기 때문입니다.

특히 MFE 전환 중인 조직에서는 이 차이가 더 크게 드러납니다. 팀마다 라우트 경계를 다르게 해석하면, RSC를 붙이기도 전에 중복 fetch, hydration 불일치, 캐시 충돌, 배포 시점 불일치 같은 문제가 먼저 터집니다. 그래서 React Router 7 + RSC를 다룰 때는 “기능 비교”보다 “운영 모델 설계”가 우선입니다.

이 글은 그 관점에서 React Router 7의 세 가지 모드(Framework, Data, Library)를 다시 정리합니다. 목표는 간단합니다. **우리 팀이 어느 모드를 고를지, 그리고 어떤 순서로 갈지 판단 기준을 명확하게 만드는 것**입니다.

## 본문

### 1) 문제: 왜 모드 선택에서 항상 혼란이 생기는가

React Router 7 문서를 빠르게 읽으면 같은 라우팅 라이브러리 안에서 다양한 기능이 제공되는 것처럼 보입니다. 하지만 실무에서는 기능 목록보다 운영 경계가 먼저 갈립니다.

- 누가 서버 렌더링 파이프라인을 관리하는가
- 누가 데이터 로딩과 재검증 타이밍을 통제하는가
- 누가 타입/라우트 계약을 보장하는가
- 장애 발생 시 어느 팀이 어느 계층을 디버깅하는가

이 네 가지에 대한 답이 모드별로 다르기 때문에, “RSC 지원”이라는 단일 문장으로 정리하면 실제 의사결정이 왜곡됩니다. 예를 들어 Data Mode에서 충분히 안정적인 데이터 경계를 만들 수 있는데도, 팀이 이를 “반쪽 지원”으로 오해해 불필요한 전면 전환을 시도하는 경우가 있습니다. 반대로 Framework Mode가 필요한 규모인데 Library Mode를 유지하다가 운영 규약 비용을 각 스쿼드가 중복으로 지불하는 경우도 흔합니다.

핵심은 기술 스펙이 아니라 **조직의 운영 비용 분배**입니다.

---

### 2) 원인: RSC를 렌더링 기술로만 좁게 보는 습관

RSC를 "서버에서 컴포넌트 렌더링하는 기술" 정도로만 해석하면, 실제로는 더 큰 문제를 놓칩니다. RSC가 팀에 가져오는 변화는 렌더링 방식 자체보다 **경계의 명시화**입니다.

- 어떤 코드는 서버 전용인지
- 어떤 데이터는 라우트 단에서 보장되는지
- 어떤 상호작용은 클라이언트 전용으로 유지하는지
- 로딩/에러/재시도 정책을 어디서 일관되게 처리하는지

이 경계를 설계하지 않은 채 RSC만 붙이면, 코드는 돌아가도 팀 운영은 더 복잡해집니다. 실제로는 컴포넌트 하나를 서버로 옮기는 일보다, “이 라우트의 데이터 책임은 누구인가”를 합의하는 일이 훨씬 어렵습니다.

즉 React Router 7의 모드 선택은 렌더링 엔진 선택이 아니라, **경계와 책임의 배치 설계**에 가깝습니다.

---

### 3) 원리: 세 가지 모드를 RSC 운영 관점으로 해석하기

#### Framework Mode: 런타임과 규약을 함께 가져가는 방식

Framework Mode는 라우팅·데이터·SSR 경로·타입 생성 흐름을 하나의 운영 체계로 묶습니다. RSC를 실제 제품 핵심으로 밀어야 하는 팀에서는 이 모드가 가장 자연스럽습니다.

장점은 명확합니다.

- 라우트 모듈 경계가 구조적으로 강제되어 팀 간 해석 차이를 줄입니다.
- 데이터 로딩과 재검증 규칙이 분산되지 않아 장애 대응 동선이 짧아집니다.
- 빌드/배포/타입 계약이 한 흐름으로 연결되어 "환경별 다르게 동작하는" 문제를 줄입니다.

단점도 분명합니다.

- 초기 학습 비용이 있습니다.
- 팀마다 다르게 쓰던 관례를 맞추는 조정 비용이 큽니다.
- 기존 인프라와 충돌할 경우 전환 설계가 필요합니다.

결국 Framework Mode는 "빠르게 붙이는 모드"가 아니라, **운영 일관성을 장기 자산으로 만들려는 모드**입니다.

#### Data Mode: 점진 도입을 위한 실무형 중심축

Data Mode는 `createBrowserRouter` 기반 데이터 라우팅을 통해 loader/action/revalidation을 명시적으로 다룹니다. 프레임워크 전체 전환 부담은 낮추면서도, 가장 중요한 경계(데이터 책임)를 먼저 고정할 수 있다는 점이 강점입니다.

현실적인 장점은 다음과 같습니다.

- 기존 앱 구조를 크게 흔들지 않고 시작할 수 있습니다.
- 라우트 단위 데이터 계약을 먼저 정리해 중복 요청을 줄일 수 있습니다.
- 추후 Framework Mode로 올라갈 때 사고방식과 구조를 재활용할 수 있습니다.

제약도 있습니다.

- 런타임 통합 수준은 Framework Mode보다 낮습니다.
- 팀 규약을 스스로 관리하지 않으면 "반쯤 표준화된 상태"에 머물 수 있습니다.

그래도 대부분의 조직에서 첫 단추로 가장 안전한 선택은 Data Mode입니다. 이유는 간단합니다. **가장 큰 사고 비용을 내는 영역(데이터 경계)을 먼저 통제**할 수 있기 때문입니다.

#### Library Mode: 유연하지만 표준화 비용이 뒤로 넘어가는 방식

Library Mode는 가볍고 유연합니다. 작은 앱이나 실험성 서브앱에는 빠른 생산성을 제공합니다. 다만 RSC 실무 운영 관점에서는 "초기 속도"가 장기적으로 "운영 부채"가 되기 쉽습니다.

자주 발생하는 패턴은 이렇습니다.

- 팀별로 로딩/에러/캐시 정책이 달라집니다.
- 라우트 경계 문서가 없는 상태에서 기능이 누적됩니다.
- 장애가 발생하면 원인 추적이 팀 간 핑퐁으로 번집니다.

즉 Library Mode 자체가 나쁜 것이 아닙니다. 문제는 **기본값으로 넓게 사용될 때**입니다. 규모가 커질수록 "유연성의 비용"을 누가 부담할지 정해야 합니다.

### 4) 운영: MFE 전환 팀에서의 현실적인 도입 순서

MFE 환경에서는 기술 스택이 이미 다변화되어 있기 때문에, 새 모드를 도입할 때 더 엄격한 단계 설계가 필요합니다. 경험상 아래 순서가 실패 확률을 낮춥니다.

#### 1단계: 모드 결정 전에 경계 계약부터 고정하기

먼저 문서로 합의해야 할 항목입니다.

- 라우트별 데이터 소유권(누가 로딩하고 어디까지 책임지는가)
- 에러 경계 레벨(페이지/섹션/컴포넌트)
- 재검증 트리거(폼 제출, 포커스 복귀, 네비게이션 등)
- 공통 로딩 UX 기준(스켈레톤, optimistic UI, 실패 시 복귀)

이 문서가 없으면 어떤 모드를 써도 팀마다 다른 정답이 생깁니다.

#### 2단계: Data Mode로 데이터 흐름 통일하기

다음으로 loader/action/revalidation을 기준으로 데이터 흐름을 정리합니다. 이 단계에서 얻는 효과는 큽니다.

- 중복 fetch 감소
- 네트워크 오류 처리 일관화
- 테스트 대상 명확화(라우트 단위)

아래처럼 "라우트 계약 중심"으로 최소 패턴을 맞추면 이후 전환이 쉬워집니다.

```tsx
// routes/project.$id.tsx
export async function loader({ params }: LoaderArgs) {
const project = await getProject(params.id)
return json({ project })
}

export async function action({ request, params }: ActionArgs) {
const form = await request.formData()
await updateProject(params.id, form)
return redirect(`/project/${params.id}`)
}

export default function ProjectRoute() {
const { project } = useLoaderData<typeof loader>()
return <ProjectView project={project} />
}
```

코드 자체보다 중요한 점은, 이 패턴이 "데이터는 라우트에서 계약한다"는 팀 공통 언어를 만든다는 사실입니다.

#### 3단계: Framework Mode 요소를 선택적으로 흡수하기

Data Mode가 안정화되면 Framework Mode의 장점을 순차적으로 가져옵니다.

- 타입 생성 자동화
- 라우트 모듈 관례 통일
- SSR 경로 및 배포 파이프라인 연결
- 운영 관측 지표(응답시간, 실패율, 재시도율) 표준화

이 시점에서는 "기능 도입"보다 "운영 자동화"의 가치가 커집니다. 사람의 암묵지에 의존하던 규칙을 파이프라인으로 이동시키는 단계입니다.

#### 4단계: Library Mode를 예외 정책으로 관리하기

MFE에서는 Library Mode가 완전히 사라지지 않습니다. 다만 범위를 좁혀야 합니다.

- 단기 캠페인성 페이지
- 수명 주기가 짧은 실험 기능
- 데이터 경계가 단순한 내부 도구

그리고 반드시 만료 조건을 둬야 합니다. "언제 Data/Framework 표준으로 흡수할지"가 없으면 예외가 기본값이 됩니다.

---

### 5) 장애 대응 관점에서 보는 모드별 차이

RSC 운영에서 진짜 비용은 정상 시나리오보다 장애 시나리오에서 발생합니다. 아래 질문으로 모드 적합성을 점검하면 선택이 쉬워집니다.

- 장애가 났을 때 관측 포인트가 한곳으로 모이는가
- 라우트 단위 재현이 가능한가
- 데이터 불일치 원인을 계약 위반으로 추적할 수 있는가
- 배포 후 회귀를 자동 검증할 수 있는가

Framework Mode는 이 네 질문에 구조적으로 유리하고, Data Mode는 규약을 잘 설계하면 대부분 충족합니다. Library Mode는 팀 역량에 크게 의존하므로, 초기에는 빨라도 장애 비용 편차가 큽니다.

### 6) 실무 운영 체크포인트: 합의가 없으면 기술이 아니라 조직이 흔들린다

React Router 7 + RSC 실무 운영에서 가장 먼저 무너지는 지점은 코드가 아니라 합의입니다. 아래 항목은 도입 초기에 반드시 확인해야 하는 운영 체크포인트입니다.

- 라우트별 데이터 책임자와 리뷰 책임자가 지정되어 있는가
- 재검증 정책이 문서와 코드에서 동일하게 유지되는가
- 에러 경계가 사용자 경험 기준으로 설계되어 있는가
- 관측 지표(응답시간, 실패율, 재시도율)가 라우트 단위로 보이는가
- 기능팀과 플랫폼팀의 장애 대응 핸드오프가 정의되어 있는가

여기서 중요한 점은 체크리스트 자체보다 반복 가능한 운영 리듬입니다. React Router 7 + RSC 실무 운영은 한 번의 마이그레이션으로 끝나는 프로젝트가 아니라, 배포·관측·회고가 계속되는 운영 체계입니다. 따라서 월 단위로 경계 계약 위반 사례를 모아 규약에 반영하는 루프를 만드는 것이 효과적입니다.

또한 도입 성공 여부를 "RSC 컴포넌트를 몇 개 만들었는가"로 측정하면 방향이 쉽게 틀어집니다. 실제로는 중복 fetch 감소, 장애 복구 시간 단축, 팀 간 계약 충돌 감소처럼 운영 지표가 더 정확한 성과 지표입니다. React Router 7 + RSC 실무 운영을 제품 경쟁력으로 연결하려면, 기술 도입 지표보다 운영 안정성 지표를 우선해야 합니다.

## 트레이드오프

아래 표는 "기술 선호"가 아니라 "운영 책임" 기준으로 읽는 것이 핵심입니다.

| 항목 | Framework Mode | Data Mode | Library Mode |
|---|---|---|---|
| RSC 운영 적합성 | 가장 높음. 경계와 런타임 통합 | 높음. 데이터 경계부터 현실적으로 정리 | 제한적. 규약 없으면 파편화 |
| 초기 도입 비용 | 높음 | 중간 | 낮음 |
| 점진 전환 용이성 | 중간(사전 정비 필요) | 가장 높음 | 높음(하지만 표준화는 뒤로 미뤄짐) |
| 팀 간 일관성 | 매우 높음 | 규약 수준에 따라 높아짐 | 팀 역량 편차 큼 |
| 장애 대응 복구 속도 | 빠름(관측 지점 집중) | 중간~빠름 | 편차 큼 |
| 대규모 조직 적합성 | 높음 | 높음(중간 단계로 우수) | 낮음~중간(엄격한 제한 필요) |

실무적으로는 다음처럼 정리할 수 있습니다.

- 제품 핵심에 SSR/RSC를 두고 장기 운영할 계획이라면 Framework Mode가 유리합니다.
- 기존 서비스가 크고 전면 전환 리스크가 크다면 Data Mode가 최적의 출발점입니다.
- 속도가 최우선인 작은 범위에서는 Library Mode가 유효하지만, 조직 기본값으로 두면 장기 비용이 커집니다.

---

## 마무리하며

React Router 7의 RSC 수용 구조를 한 문장으로 요약하면 이렇습니다.

**RSC는 기능 토글이 아니라 운영 모델 선택 문제입니다.**

모드 선택을 잘하려면 "무엇이 더 최신인가"가 아니라 "우리 팀이 어떤 책임을 어디에 둘 것인가"를 먼저 정해야 합니다. 특히 MFE 전환 조직이라면 Data Mode로 데이터 경계를 먼저 통일하고, Framework Mode로 운영 표준을 흡수하는 경로가 가장 현실적입니다.

반대로 모드 합의 없이 기능을 먼저 붙이면, 초기에는 빨라 보여도 결국 경계 부채를 이자로 갚게 됩니다. RSC 시대의 라우터 설계는 렌더링 기법 선택이 아니라, 팀의 운영 체계를 설계하는 일입니다.

다음 단계에서 꼭 점검해 볼 질문은 하나입니다.

> 우리 팀은 Loader/Action과 RSC 데이터 흐름의 책임을 어디서 분리하고, 어떤 계약으로 검증할 것인가?

이 질문에 답이 생기면 모드 선택은 훨씬 단순해집니다.

## 한눈에 보기

React Router 7 + RSC 조합에서 성능은 “기능 하나를 켰더니 빨라졌다”로 설명되는 일이 드뭅니다. 전환은 항상 시간축 위에서 일어나며, 그 시간축에는 라우트 발견, 모듈 로딩, 데이터 수집, RSC 해석, 하이드레이션 이후 상호작용 가능 시점이 얽혀 있습니다. 그래서 Single Fetch, Route Module Splitting, Lazy Discovery를 각각의 최적화 카드로 분리해 보면 대개 한쪽을 개선할 때 다른 쪽 병목이 튀어나오는 현상이 반복됩니다. 이 글은 세 기능을 전환 파이프라인으로 묶어, 어떤 메커니즘으로 지연이 생기고, React Router 7 런타임에서 무엇을 근거로 판단해야 하며, 실제 운영 비용이 어떻게 이동하는지를 하나의 문맥으로 정리합니다.

핵심 메시지는 단순합니다. 요청 수를 줄였다는 사실, 번들 총량을 줄였다는 사실, 초기 진입이 빨라졌다는 사실은 각각 부분 최적화의 증거일 뿐, 사용자 체감 전환 품질의 증거가 아닙니다. React Router 7 데이터 라우터는 내비게이션 시점에 필요한 작업을 취소·병합·우선순위화하는 구조를 제공하고, 라우트 모듈 로딩과 lazy discovery를 통해 초기 비용과 전환 비용을 조정할 수 있게 합니다. 그러나 이 구조는 “비용을 없애는 마법”이 아니라 “비용을 언제 어디로 배치할지 결정하는 스케줄러”에 가깝습니다. 따라서 성능 설계의 초점은 평균 속도 경쟁이 아니라, 느린 순간이 발생하는 조건을 줄이고, 발생하더라도 원인을 즉시 분해할 수 있는 운영 체계를 갖추는 데 있어야 합니다.

운영 관점에서는 이 접근이 명확한 이득을 만듭니다. 첫째, 회귀 대응 속도가 빨라집니다. 전환을 discover/module/data/rsc/ui 단계로 계측하면 “무엇이 느려졌는지”를 배포 당일에 특정할 수 있습니다. 둘째, 최적화 우선순위가 바뀝니다. p50 개선보다 p95/p99 안정화가 사용자 불만 감소에 더 직접적으로 연결되기 때문에, 팀의 리소스가 불필요한 미세 튜닝보다 구조적 병목 제거에 배치됩니다. 셋째, 조직 비용이 줄어듭니다. “체감상 느린 것 같다”는 추상 논쟁이 줄고, 동일 지표를 기준으로 프런트엔드·백엔드·플랫폼이 같은 결론에 도달할 수 있습니다.

## 들어가며

React Router 7이 실무에서 크게 달라진 지점은 라우팅을 URL 변경 처리기로 보지 않고, 데이터와 렌더링 경계를 포함한 전환 오케스트레이터로 다룬다는 점입니다. 사용자가 링크를 클릭하면 단순히 컴포넌트가 바뀌는 것이 아니라, 어떤 라우트가 매칭되는지 확인하고, 해당 라우트 모듈이 아직 없다면 가져오고, loader/action 경로를 통해 필요한 데이터를 모으고, 중간에 더 새로운 전환이 들어오면 불필요한 요청을 취소하는 식으로 런타임이 움직입니다. 여기에 RSC를 결합하면 서버에서 미리 계산해 보낼 경계와 클라이언트에서 즉시 상호작용할 경계가 함께 설계 대상이 됩니다. 결국 성능 이슈는 네트워크, 자바스크립트 실행, 서버 계산, 하이드레이션, 사용자 입력 반응성이 서로 다른 리듬으로 충돌하면서 나타납니다.

문제가 어려운 이유는 오해가 매우 그럴듯하게 보이기 때문입니다. 요청 수를 줄이면 일반적으로 RTT 부담이 줄어드는 것은 맞습니다. 그러나 Single Fetch를 무계획으로 키우면 응답 페이로드가 커지고, 클라이언트에서 JSON 파싱과 객체 할당 비용이 늘어나며, 서버 측 직렬화 비용도 커집니다. 번들 크기를 줄이면 초기 다운로드가 유리해지는 것도 맞습니다. 하지만 Route Module Splitting을 지나치게 세분화하면 내비게이션 순간에 청크 요청이 동시 다발로 발생해 스케줄링 오버헤드와 parse/compile 분산 비용이 늘어납니다. Lazy Discovery로 초기에 라우트 메타를 덜 싣는 전략도 유효합니다. 다만 deep link나 드문 경로로 이동하는 순간 discovery 자체가 임계 경로에 올라오면, 사용자는 “처음엔 빨랐는데 쓰다 보면 갑자기 멈춘다”는 인상을 받게 됩니다.

React Router 7 문서가 강조하는 네트워크 동시성 관리와 자동 코드 분할, lazy route discovery의 의미를 운영 언어로 번역하면 이렇습니다. “라우터는 이미 좋은 기본 동작을 제공하지만, 앱별 트래픽 패턴과 사용자 동선이 다르므로 임계 경로를 앱 맥락에 맞게 다듬어야 한다”입니다. 즉, 프레임워크의 옵션을 켜는 순간 최적화가 끝나는 것이 아니라, 옵션을 켠 뒤에 생기는 비용 이동을 관측하고 통제해야 실제 품질 개선으로 이어집니다. 이 글은 바로 그 통제 방법을 설명합니다. 어떤 메커니즘에서 지연이 만들어지고, 런타임 근거를 어떻게 확보하며, 그 결과로 운영 비용이 어떤 형태로 줄거나 늘어나는지 순서대로 보겠습니다.

## 설계 방향과 의도

설계의 출발점은 “기능 중심”에서 “전환 시간축 중심”으로 사고를 바꾸는 것입니다. 사용자가 체감하는 것은 기능 체크리스트가 아니라, 클릭 이후 의미 있는 UI가 얼마나 일관되게 나타나는가이기 때문입니다. 전환을 시간축으로 보면 대체로 입력 이벤트 발생, 라우트 식별과 메타 확보, 모듈 로딩, 데이터 로딩, RSC 경계 해석, 화면 반영의 단계가 겹치며 진행됩니다. 이 단계들은 완전 직렬로 묶을 수도 있고 일부를 병렬화할 수도 있습니다. 병목은 대개 “직렬로 남겨둔 구간”과 “같은 시점에 과도하게 몰아넣은 구간”에서 생깁니다. 그러므로 설계 의도는 총 작업량을 0으로 만드는 것이 아니라, 사용자 대기 구간이 되는 임계 경로를 최대한 짧고 예측 가능하게 재구성하는 것입니다.

Single Fetch를 도입할 때도 같은 관점이 필요합니다. 메커니즘상 Single Fetch의 장점은 분산된 요청 왕복을 하나의 계약으로 묶어 네트워크 지연과 요청 오케스트레이션 복잡도를 줄인다는 데 있습니다. 그러나 계약이 불명확하면 모든 데이터를 한 번에 실어 보내는 “큰 응답 하나”가 되어 버립니다. React Router 7 loader 모델에서 중요한 것은 무엇이 첫 의미 있는 UI를 결정하는지 명확히 구분하는 일입니다. critical 데이터는 전환 임계 경로에 남기고, 부가 데이터는 deferred 또는 후속 요청 경로로 밀어야 합니다. 운영 비용 측면에서 이 설계는 단기적으로 데이터 스키마 관리 비용을 늘릴 수 있습니다. 대신 장기적으로는 전환 실패 범위를 줄이고, 특정 패널 실패가 전체 페이지 실패로 번지는 일을 막아 장애 대응 비용을 크게 줄입니다.

Route Module Splitting의 의도도 “파일을 많이 쪼개기”가 아닙니다. 메커니즘상 모듈 분할은 초기 번들 부담을 낮추는 대신, 전환 시점에 필요한 코드의 집합을 동적으로 선택하게 만듭니다. 이때 React Router 7 런타임은 매칭된 라우트 모듈을 가져오고 실행 준비를 하면서 내비게이션을 진행합니다. 따라서 분할 기준은 폴더 구조보다 사용자 동선이어야 합니다. 자주 왕복하는 경로가 서로 다른 거대한 청크를 매번 다시 열게 만들면, 총량이 작아도 체감은 무거워집니다. 반대로 거의 쓰지 않는 관리 경로를 강하게 분리하면 hot path는 가벼워집니다. 운영 비용 관점에서는 번들 그래프 관리가 복잡해지지만, 잘 설계하면 저사양 기기에서 parse/compile 지연이 줄어 고객 불만과 이탈이 완화됩니다.

Lazy Discovery는 더욱 주의가 필요한 선택입니다. 메커니즘은 단순합니다. 초기 로드에서 전체 라우트 정보를 다 준비하지 않고, 필요 시점에 발견합니다. 이 구조는 초기 LCP 개선에 도움이 되지만, discovery가 늦어지는 순간 module/data 시작 자체가 지연될 수 있습니다. React Router 7의 lazy route discovery 설명이 말하는 실무 함의는 “초기 비용 절감”과 “전환 꼬리 지연”의 균형입니다. 따라서 설계 의도는 이분법이 아니라 계층화입니다. 인접 경로는 보수적으로 선발견하고, hover·viewport·최근 이동 이력 같은 의도 신호가 나타날 때만 범위를 넓혀야 합니다. 운영 비용은 선발견 정책 튜닝이라는 형태로 증가하지만, deep link p95 악화 같은 치명적 회귀를 사전에 줄여 결과적으로 운영 안정성이 올라갑니다.

정리하면 세 기능은 모두 비용을 이동시키는 레버입니다. 요청 수, 코드량, 메타 준비 시점이라는 서로 다른 축에서 비용을 앞당기거나 미루는 선택을 하게 됩니다. 설계자는 “무엇이 빨라졌는가”보다 “어떤 비용이 어디로 이동했는가”를 먼저 물어야 하며, React Router 7 런타임에서 그 이동이 실제로 어떤 순서로 실행되는지 확인해야 합니다. 이 질문 습관이 자리 잡으면 성능 최적화는 개인의 감각이 아니라 팀의 재현 가능한 운영 능력이 됩니다.

## 실제 구현과 런타임 동작

실제 구현 단계에서 가장 먼저 해야 할 일은 계측입니다. 최적화를 먼저 하면 대개 개선 여부를 설명하지 못합니다. 전환 이벤트마다 discover, module load, data fetch, rsc resolve, first meaningful UI까지를 분리 기록해야 합니다. 메커니즘 관점에서 이 분해가 중요한 이유는, 사용자에게는 하나의 “느림”으로 보이는 현상이 내부적으로는 서로 다른 병목에서 발생하기 때문입니다. React Router 7은 내비게이션 취소와 재시도를 런타임에서 관리하므로, 단순 총시간만 보면 취소된 요청이나 중복 시작을 놓치기 쉽습니다. 운영 측면에서는 이 계측 하나로 디버깅 비용이 급격히 줄어듭니다. 장애 상황에서 “느리다”를 감정이 아니라 단계별 숫자로 바꿀 수 있기 때문입니다.

Single Fetch 구현은 loader 계약을 먼저 나누는 방식으로 접근하는 것이 안전합니다. 예를 들어 화면의 뼈대를 결정하는 요약값, 권한 검증 결과, 기본 목록처럼 즉시 필요한 데이터만 critical로 두고, 추천 카드·통계 패널·관련 항목처럼 지연 가능한 데이터는 deferred로 분리합니다. 메커니즘상 이렇게 나누면 전환 임계 경로에서 직렬 작업이 짧아집니다. React Router 7 데이터 로딩 모델에서는 critical이 준비되는 즉시 라우트 렌더링이 진행되고, deferred는 후속적으로 채워지는 흐름을 활용할 수 있습니다. 운영 비용은 API 계약을 세밀하게 나눠야 하므로 초기에 설계 공수가 늘어납니다. 그러나 장애 전파 범위를 줄여 “부가 패널 장애로 전체 페이지 다운” 같은 사건을 막는 효과가 큽니다.

Route Module Splitting은 번들 리포트 숫자보다 런타임 네트워크 패턴으로 검증해야 합니다. 메커니즘상 사용자가 특정 라우트로 이동할 때 실제로 동시에 어떤 청크들이 내려오고 어떤 순서로 파싱되는지가 체감을 만듭니다. React Router 7이 라우트 단위 코드 분할을 자연스럽게 지원해도, 앱의 shared dependency 구성에 따라 특정 전환에서 큰 공통 청크가 반복 로드되거나 재평가 비용이 커질 수 있습니다. 운영 지표로는 “라우트 진입별 동시 청크 수”, “청크별 parse/compile 시간”, “핫 경로의 총 실행 바이트”를 함께 봐야 합니다. 이 관측 체계를 갖추면 “번들 줄였는데 왜 느리냐” 같은 반복 갈등이 줄고, 정확히 어느 경계를 합치거나 나눌지 빠르게 결정할 수 있습니다.

Lazy Discovery 구현에서는 시점을 다루는 감각이 중요합니다. 메커니즘상 discovery가 늦으면 module/data 시작선이 뒤로 밀려 연쇄 지연이 생깁니다. 따라서 discovery를 독립 단계로 남겨두기보다, 사용자 의도 신호가 보일 때 앞당겨 실행해야 합니다. 예를 들어 사용자가 링크 근처에서 hover를 유지하면 해당 라우트 메타를 미리 준비하고, 리스트 하단이 viewport에 들어오면 다음 페이지 라우트를 선발견하는 방식이 실무에서 안정적입니다. React Router 7의 lazy discovery 철학과도 맞아떨어집니다. 운영 비용은 네트워크 상황별 정책 분기가 늘어난다는 점입니다. 저속 네트워크에서 과도한 선발견은 오히려 손해이므로, 연결 상태를 보고 공격도를 조절해야 합니다. 그 대신 deep link 전환 꼬리 지연을 낮춰 사용자 불만 피크를 줄일 수 있습니다.

RSC 경계는 전환 완결성에 직접 영향을 줍니다. 메커니즘상 서버 컴포넌트 경계가 깊어질수록 데이터 일관성과 보안 측면 장점이 커지지만, 사용자 상호작용까지 서버 왕복에 묶이면 즉시성이 떨어집니다. React Router 7 자체는 라우팅/데이터 오케스트레이션을 잘해주지만, RSC 경계 선택이 잘못되면 “데이터는 맞는데 손맛이 느린 UI”가 됩니다. 따라서 필터, 정렬, 탭 전환, 입력 보정처럼 고빈도 상호작용은 클라이언트 경계를 유지하고, 권한 검증·민감 조합 계산처럼 서버 우위 영역만 RSC로 강화하는 분리가 필요합니다. 운영 비용은 컴포넌트 경계 관리 복잡도가 증가한다는 점이지만, 효과는 분명합니다. 데이터 신뢰성과 상호작용 반응성을 동시에 확보할 수 있습니다.

마지막으로 도입 순서가 매우 중요합니다. 세 기능을 동시에 바꾸면 회귀 원인이 겹쳐 해석이 불가능해집니다. 메커니즘상 병목 축이 서로 다르기 때문입니다. React Router 7 런타임 근거를 유지하려면 기준선 계측을 확보한 뒤, 모듈 경계 정리, 데이터 계약 정리, discovery 정책 확장, RSC 경계 미세 조정 순으로 단계화하는 편이 안전합니다. 운영 비용은 배포 라운드가 늘어난다는 점입니다. 하지만 회귀 탐지와 롤백 판단이 빨라져 실제 총 비용은 오히려 낮아집니다. “빨리 한 번에 바꾸기”보다 “느리게 정확히 바꾸기”가 서비스에서는 더 빠른 길인 경우가 많습니다.

## 어떤 문제를 어떻게 해결하는가

현장에서 가장 흔한 문제는 “평균은 괜찮은데 가끔 너무 느리다”입니다. 이 문제의 메커니즘은 대개 전환 임계 경로의 직렬 구간이 길거나, discovery·module·data가 같은 순간에 몰려 스파이크를 만드는 데 있습니다. React Router 7 런타임에서는 내비게이션 취소와 재시작이 빈번할 때 이런 스파이크가 더 잘 드러납니다. 해결은 단일 트릭이 아니라 분해입니다. discovery를 의도 신호로 앞당기고, module 경계를 hot path 기준으로 재정렬하고, data를 critical/deferred로 나눠 차단 시간을 잘라야 합니다. 운영 효과는 p50 미세 개선보다 p95/p99 하락에서 크게 나타납니다. 사용자 불만이 줄어드는 이유도 평균보다 꼬리 완화에 있습니다.

두 번째 문제는 “코드는 줄였는데 체감이 그대로다”입니다. 메커니즘상 번들 총량 감소가 곧 전환 실행 비용 감소를 보장하지 않기 때문입니다. React Router 7이 자동 코드 분할을 제공해도, 실제 전환 시 동시에 열리는 청크 조합이 무겁다면 parse/compile과 실행 오버헤드는 남습니다. 이때 해결의 초점은 리포트 숫자가 아니라 진입 경로별 실행 그래프입니다. 어떤 라우트에서 어떤 shared chunk가 반복적으로 병목이 되는지 확인한 뒤, 경계를 재묶거나 공통 의존성 정책을 조정해야 합니다. 운영 비용은 번들 관리 규칙을 팀 규약으로 유지해야 한다는 점이지만, 효과는 명확합니다. “초기만 빠른 앱”에서 “전환도 가벼운 앱”으로 성격이 바뀝니다.

세 번째 문제는 “초기 진입 최적화 성공 후 deep link 품질 저하”입니다. 메커니즘은 비용 이연의 부작용입니다. Lazy Discovery가 초기 부담을 줄여준 대신, 덜 자주 쓰는 경로에서 discovery가 임계 경로로 올라와 지연을 키우는 것입니다. React Router 7의 lazy discovery 모델은 이를 허용하는 구조이므로, 정책 없이 방치하면 자연스럽게 발생합니다. 해결은 발견 범위의 계층화입니다. 기본은 보수적으로 유지하되, 사용자 의도 신호가 강해질수록 선발견 강도를 높이고, 네트워크 여건이 나쁘면 즉시 완화하는 동적 정책이 필요합니다. 운영 비용은 정책 튜닝과 관찰 지표 관리가 추가되는 점이지만, 효과는 전환 품질의 예측 가능성 상승입니다. 특히 드문 경로에서의 불쾌한 지연이 줄어 CS 노이즈가 감소합니다.

네 번째 문제는 “팀이 느려진 이유를 설명하지 못한다”입니다. 메커니즘상 측정 단위가 잘못됐기 때문입니다. 총 페이지 로드 시간이나 단일 synthetic 점수만 보면 원인 분해가 어렵습니다. React Router 7 런타임은 라우팅·데이터·모듈 로딩이 얽혀 움직이므로, 단계별 시간과 실패율을 라우트 단위로 분리해야 설명력이 생깁니다. 해결은 전환 이벤트 스키마의 표준화와 배포 전후 비교 프레임 고정입니다. 운영 비용은 초기 대시보드 구성과 로그 보존 비용이지만, 효과는 장애 대응 속도의 구조적 개선입니다. 더 이상 “누가 잘못했나”가 아니라 “어느 단계가 변했나”로 논의가 전환됩니다.

다섯 번째 문제는 “RSC 도입 후 데이터는 안정적인데 UI가 답답하다”입니다. 메커니즘상 서버 경계를 과도하게 확장해 상호작용 경로까지 서버 왕복에 종속시킨 결과입니다. React Router 7이 전환을 잘 관리해도, 고빈도 상호작용이 서버 완료를 기다리면 INP와 체감 반응성은 악화됩니다. 해결은 경계의 목적을 분리하는 것입니다. 데이터 무결성·보안·일관성이 핵심인 계산은 서버에 두고, 사용자 조작 피드백이 핵심인 경로는 클라이언트에서 즉시 처리하도록 배치해야 합니다. 운영 비용은 경계 설계 원칙을 코드리뷰 기준으로 내재화해야 한다는 점입니다. 하지만 효과는 큽니다. 품질 지표와 사용자 감각이 같은 방향으로 개선되기 시작합니다.

결국 이 섹션의 결론은 단순합니다. 문제는 “기능 미도입”보다 “비용 이동의 무의식적 방치”에서 생깁니다. 해결은 세 기능을 함께 켜는 행위가 아니라, 전환 시간축에서 각 기능이 만들 병목 변화를 예측하고 계측으로 검증하는 운영 루프를 갖추는 것입니다. React Router 7은 그 루프를 설계할 수 있는 좋은 기반을 제공합니다. 기반이 있다는 사실과 기반을 운영 역량으로 전환하는 일 사이에는 여전히 팀의 설계 discipline이 필요합니다.

## 마무리하며

Single Fetch, Route Module Splitting, Lazy Discovery는 React Router 7 + RSC 시대의 핵심 성능 레버가 맞습니다. 다만 이 레버들은 지연을 제거하기보다 지연의 위치와 시점을 바꾸는 도구라는 사실을 전제로 써야 합니다. 메커니즘을 이해하지 못한 채 개별 기능을 최적화하면, 초기 진입은 빨라졌는데 전환 꼬리가 길어지고, 번들 총량은 줄었는데 실행 지연이 남고, 데이터 계약은 단순해졌는데 실패 전파가 커지는 역설을 쉽게 만납니다. 반대로 전환 시간축 관점에서 세 레버를 함께 설계하면, 병목은 분산되고 회귀는 설명 가능해지며, 사용자 체감 품질은 평균보다 일관성에서 개선됩니다.

React Router 7 런타임 근거를 붙여 다시 정리하면 이렇습니다. 라우터는 내비게이션 단위로 데이터와 코드 로딩을 조정하고, 필요하면 취소하며, lazy discovery로 초기 비용을 다루는 구조를 제공합니다. 이 구조 위에서 팀이 해야 할 일은 critical/deferred 데이터 계약, 동선 기반 모듈 경계, 의도 신호 기반 discovery 정책, RSC 경계의 역할 분리를 명시하는 것입니다. 이 네 가지가 정리되면 “왜 느린가”에 대한 답이 빨라지고, “무엇을 고쳐야 하나”가 명확해집니다. 결국 프레임워크의 장점은 옵션 수가 아니라, 팀이 같은 사실을 보고 같은 결정을 내릴 수 있게 만드는 공통 언어에 있습니다.

운영 비용과 효과를 함께 보면 더 분명해집니다. 계측 체계와 경계 설계 원칙을 세우는 초기 비용은 분명 존재합니다. 그러나 장기적으로는 회귀 대응 시간 단축, 무의미한 논쟁 감소, 장애 전파 축소, 사용자 불만 피크 완화라는 형태로 비용을 회수합니다. 성능은 단발성 튜닝이 아니라 서비스 신뢰의 일부입니다. 따라서 목표는 “가장 빠른 데모”가 아니라 “대부분의 실제 전환이 꾸준히 빠른 운영 상태”여야 합니다. React Router 7 + RSC에서 이 목표를 달성하는 가장 현실적인 방법이 바로, Single Fetch · Route Module Splitting · Lazy Discovery를 하나의 파이프라인으로 설계하고 검증하는 접근입니다.

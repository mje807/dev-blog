## 한눈에 보기

React Router 7 + RSC 환경에서 성능은 보통 한 가지 기능으로 결정되지 않습니다. 실제 전환 속도는 데이터 요청 수, 라우트 단위 코드 로딩, 라우트 메타데이터 발견 시점이 동시에 맞물리며 결정됩니다. **Single Fetch · Route Module Splitting · Lazy Discovery**를 함께 설계해야 하는 이유가 여기에 있습니다.

핵심은 평균 속도보다 **전환 일관성**입니다. 사용자는 p50이 아니라 느린 순간의 체감으로 앱을 평가합니다. 따라서 실무에서는 “이 전환에서 어떤 요청이 발생했고, 어떤 모듈이 로드됐고, 사용자에게 첫 의미 있는 UI가 언제 보였는가”를 이벤트 로그로 설명할 수 있어야 합니다.

이 글은 **Single Fetch · Route Module Splitting · Lazy Discovery**를 옵션 목록이 아니라 하나의 전환 파이프라인으로 묶어 분석합니다. 설계 의도, 실제 런타임 동작, 해결되는 문제와 남는 한계를 분리해 정리하여 운영 가능한 성능 설계 기준을 제시합니다.

## 들어가며

React Router 7은 데이터 로딩과 라우팅을 프레임워크 레벨에서 결합해 전환 단위를 더 정교하게 다룰 수 있게 합니다. RSC(React Server Components)는 여기에 서버 렌더링 경계를 더해, 서버에서 계산할 것과 클라이언트 상호작용으로 남길 것을 명시적으로 분리합니다. 이 조합은 강력하지만, 성능 문제를 더 입체적으로 만듭니다.

실무에서 자주 발생하는 오해는 세 가지입니다. 첫째, 요청 수를 줄이면 전환이 항상 빨라진다고 보는 오해입니다. 둘째, 번들 크기만 줄이면 체감 성능이 자동 개선된다고 보는 오해입니다. 셋째, 초기 로딩만 빠르면 전체 성능이 좋아졌다고 판단하는 오해입니다. 실제로는 요청 수를 줄여도 응답이 비대해지면 파싱 비용이 증가할 수 있고, 번들을 잘게 쪼개도 전환 시점 동시 로딩이 몰리면 체감 지연이 커질 수 있으며, 초기 진입이 빨라도 자주 쓰는 전환이 불안정하면 서비스 평가는 낮아집니다.

React Router 7 + RSC에서 성능은 개별 기능의 고득점 합이 아니라, 전환 파이프라인의 병목 분산 품질입니다. 따라서 설계 단위를 기능에서 시나리오로 전환해야 합니다. 이 글의 목적은 다음 세 질문에 팩트 기반으로 답하는 것입니다.

1. 세 기능은 각각 어떤 비용을 어디로 이동시키는가
2. 런타임에서 실제로 어떤 순서로 작동하는가
3. 어떤 지표를 보면 개선과 회귀를 구분할 수 있는가

## 문제 정의: 기능을 켰는데 전환 품질이 흔들리는 이유

현장에서 가장 많이 보는 증상은 “개선했는데 느림이 남는” 상황입니다.

- Single Fetch 도입 후에도 특정 라우트에서 긴 대기(예: 로딩 UI 1초 이상)가 반복됩니다.
- Route Module Splitting 적용 후에도 초기 진입 JavaScript 바이트가 기대만큼 감소하지 않습니다.
- Lazy Route Discovery 적용 후 초기 페이지는 빨라졌지만 deep link 전환에서 지연 꼬리(p95/p99)가 늘어납니다.

이 현상은 기능 실패가 아니라 **병목 이동**입니다. 네트워크 왕복(RTT) 비용을 줄이는 대신 응답 직렬화/역직렬화 비용이 증가할 수 있고, 청크를 분할하는 대신 공통 의존성 중복으로 실제 전송 바이트가 유지될 수 있으며, 초기 발견 비용을 지연시킨 대신 전환 순간에 발견+모듈+데이터 로딩이 한 번에 집중될 수 있습니다.

RSC를 함께 쓰면 병목은 더 복합적입니다. 서버 컴포넌트 경계에서 계산량이 커지거나 캐시 무효화가 잦으면, 라우터 최적화가 사용자 반응성으로 이어지지 않습니다. 즉, React Router 7 성능 설계는 라우팅 계층만의 최적화가 아니라 서버 경계와 클라이언트 상호작용 경계를 포함한 시스템 설계입니다.

## 설계 방향과 의도

이 섹션은 “왜 이렇게 설계해야 하는가”를 다룹니다. 핵심 원칙은 기능 최적화가 아니라 **전환 시간축 설계**입니다.

### 1) 전환을 하나의 이벤트로 보고 단계별 비용을 분해합니다

전환은 보통 다음 단계로 진행됩니다.

1. 사용자 입력 발생(click, navigate)
2. 라우트 메타 확보(Lazy Discovery 필요 시)
3. 라우트 모듈 로딩(Route Module Splitting 영향)
4. 데이터 수집(Single Fetch 포함)
5. RSC 경계 해석 및 렌더 결합
6. 첫 의미 있는 UI 노출

이 단계는 전부 직렬일 필요가 없습니다. 발견과 일부 모듈 로딩, 데이터 준비는 조건에 따라 병렬화가 가능합니다. 설계 의도는 총 시간을 줄이는 것이 아니라, 사용자가 기다리는 **차단 구간(blocking segment)**을 최소화하는 것입니다.

### 2) Single Fetch는 요청 수 최적화가 아니라 데이터 계약입니다

HTTP 요청 수 감소 자체는 수단입니다. 목적은 전환에 필요한 데이터를 “필수(critical)”와 “지연 가능(non-critical)”로 나눠 첫 반응을 안정화하는 것입니다. 계약 없는 Single Fetch는 거대한 payload를 만들어 오히려 CPU 파싱 비용과 메모리 압박을 높일 수 있습니다.

실무 의도는 명확합니다.

- 첫 화면에 반드시 필요한 데이터만 동기 경로에 포함합니다.
- 상세 패널, 추천 영역, 부가 통계처럼 지연 가능한 데이터는 후속 경로로 분리합니다.
- 캐시 키와 재검증 정책을 요청 병합 설계와 함께 정의합니다.

### 3) Route Module Splitting은 파일 쪼개기가 아니라 책임 경계 설계입니다

라우트 모듈을 쪼개는 이유는 단순히 번들 그래프를 예쁘게 만들기 위해서가 아닙니다. 전환 시점에 필요한 코드만 로딩하도록 경계를 정의하기 위함입니다. 여기서 중요한 사실은 번들 크기 총합이 같아도, **동시에 열리는 청크 조합**이 다르면 체감 성능이 크게 달라진다는 점입니다.

따라서 분할 기준은 기술 폴더 구조보다 사용자 동선입니다.

- 함께 자주 이동되는 라우트는 캐시 재사용이 유리한 경계를 구성합니다.
- 거의 진입하지 않는 관리자/설정 라우트는 독립 청크로 분리합니다.
- 공통 의존성이 과도하면 분할 이득이 사라지므로 shared chunk 정책을 함께 설계합니다.

### 4) Lazy Route Discovery는 초기 최적화가 아니라 지연 분산 전략입니다

Lazy Discovery는 초기에 모든 라우트 메타를 가져오지 않아 초기 비용을 줄일 수 있습니다. 그러나 전략 없이 적용하면 “전환 직전의 surprise cost”를 만듭니다. 설계 의도는 초기 비용을 줄이되, 자주 발생하는 전환의 꼬리 지연을 억제하는 균형점 확보입니다.

실무에서는 보통 2계층 규칙이 효과적입니다.

- 보수적 선발견: 현재 라우트 인접 경로만 최소 선준비
- 의도 신호 기반 확장: hover, viewport 근접, 최근 전환 패턴 기반 추가 발견

이 방식은 과도한 선로딩을 피하면서 사용자 의도와 가까운 경로를 먼저 준비합니다.

### 5) 설계의 1차 목표는 “최고 속도”가 아니라 “예측 가능한 반응성”입니다

Core Web Vitals도 평균보다 tail latency와 상호작용 안정성을 강조합니다. 사용자는 200ms 빠른 한 번보다, 매번 비슷하게 반응하는 경험을 더 높게 평가합니다. React Router 7 + RSC에서 성능 설계의 의도는 따라서 다음과 같이 정리됩니다.

- 빠른 순간을 만드는 것보다 느린 순간을 줄입니다.
- 평균 개선보다 p95/p99 안정화를 우선합니다.
- 지표를 보고 “왜 느려졌는지”를 팀이 즉시 설명할 수 있게 합니다.

## 실제 구현과 런타임 동작

이 섹션은 설계가 코드와 런타임에서 어떻게 나타나는지를 다룹니다. 코드는 증거 용도로 최소화합니다.

### 1) 전환 계측 이벤트를 먼저 정의합니다

최적화 전에 관찰 가능성이 필요합니다. 전환별 이벤트 스키마를 정의하면 병목 축(요청/코드/발견)을 분해할 수 있습니다.

```ts
type NavigationMetric = {
routeId: string
discoverMs: number
moduleLoadMs: number
dataMs: number
rscResolveMs: number
firstMeaningfulUiMs: number
status: "ok" | "timeout" | "error" | "cancel"
}
```

이 스키마는 대시보드 꾸미기보다 원인 분석을 위해 사용합니다. 예를 들어 `dataMs`는 정상인데 `moduleLoadMs`만 급증하면 분할 경계 또는 공통 청크 회귀를 의심할 수 있습니다.

### 2) Single Fetch는 “핵심/부가” 분리로 구현합니다

아래 예시는 전환에 필요한 요약 데이터만 동기 경로에 두고, 부가 데이터는 지연 경로로 분리하는 패턴입니다.

```ts
export async function loader({ request }: LoaderArgs) {
const critical = await getCriticalSummary(request)
const deferred = getSecondaryPanels(request)
return { critical, deferred }
}
```

런타임에서 중요한 점은 두 가지입니다.

- `critical`은 첫 의미 있는 UI를 결정합니다.
- `deferred`는 렌더 후 보강되므로 전환 차단 시간을 늘리지 않습니다.

실패 경로도 분리해야 합니다. 부가 데이터 실패가 전체 화면 실패로 승격되면 전환 안정성을 잃습니다. 필수/부가 경계는 데이터 모델이 아니라 사용자 작업 흐름 기준으로 정합니다.

### 3) Route Module Splitting은 “라우트 진입 시 필요한 실행 코드” 기준으로 검증합니다

번들 분석에서 총량만 보면 착시가 생깁니다. 실제로는 다음을 봐야 합니다.

- 특정 라우트 진입 시 네트워크 패널에서 동시에 내려오는 청크 수
- 각 청크의 parse/compile 시간
- 공통 의존성이 여러 경로에서 중복 포함되는지

특히 저사양 모바일에서는 다운로드보다 parse/compile 시간이 체감 지연의 큰 비중을 차지할 수 있습니다. 즉, 청크를 작게 나누는 것만으로 끝나지 않고 “동시에 실행되는 코드량”을 줄여야 합니다.

### 4) Lazy Discovery는 발견 시점을 로딩 파이프라인에 삽입합니다

Lazy Discovery를 쓰면 라우트 메타 획득이 런타임 단계로 이동합니다. 이때 발견이 늦어지면 모듈 로딩과 데이터 요청 시작이 연쇄적으로 늦어집니다. 따라서 발견을 단독 단계로 두지 않고, 의도 신호 기반 pre-discovery를 사용해 선행시켜야 합니다.

- 링크 hover 시: 인접 라우트 메타 선발견
- viewport 진입 시: 다음 행동 가능성이 높은 경로 선발견
- 최근 전환 패턴 기반: 반복 이동 경로 우선 준비

이 전략의 검증 지표는 초기 LCP만이 아니라 `discoverMs` 분포입니다. 초기 성능이 좋아져도 deep-link `discoverMs` p95가 악화되면 운영 품질은 낮아집니다.

### 5) RSC 경계에서는 “데이터 완료”와 “상호작용 가능”을 분리해 봅니다

RSC 환경에서 서버 응답 완료 시점과 사용자가 버튼을 눌러 반응을 얻는 시점은 다를 수 있습니다. 따라서 `firstMeaningfulUiMs`와 상호작용 이벤트(INP 관련)를 함께 관찰해야 합니다. 서버 경계가 깊을수록 일관성은 좋아질 수 있지만, 클라이언트 상호작용 즉시성이 희생될 수 있습니다.

실무적으로는 상호작용 밀도가 높은 구간(필터, 탭, 정렬, 입력)은 Client Component 경계를 남기고, 데이터 무결성이 중요한 구간은 서버 경계를 강화하는 방식이 일반적입니다. 이 선택은 취향이 아니라 작업 특성 기반 분리입니다.

### 6) 배포 순서가 런타임 해석 가능성을 만듭니다

세 기능을 동시에 도입하면 회귀 원인을 분리하기 어렵습니다. 안정적인 도입 순서는 다음과 같습니다.

1. 기준선 계측(최소 1주)
2. Module Splitting 경계 정리
3. Single Fetch 계약 도입
4. Lazy Discovery 규칙 확장
5. RSC 경계 미세 조정

이 순서는 각 단계의 영향 축이 달라서 디버깅에 유리합니다. 런타임 문제를 재현했을 때 “이번 회귀는 어느 레이어에서 시작됐는가”를 더 빠르게 좁힐 수 있습니다.

## 어떤 문제를 어떻게 해결하는가

여기서는 세 기능 통합 설계가 실제로 해결하는 문제를 팩트 중심으로 정리합니다.

### 문제 1) 전환 대기시간이 길고 불규칙합니다

원인: 요청/모듈/발견이 직렬로 누적되거나 전환 직전 몰림이 발생합니다.

해결: 단계 병렬화와 필수/부가 데이터 분리로 차단 구간을 줄입니다.

- 발견을 의도 신호로 선행시켜 모듈·데이터 시작 시점을 앞당깁니다.
- 필수 데이터만 first paint 경로에 포함합니다.
- 부가 데이터 실패를 부분 실패로 격리합니다.

효과: 평균 개선보다 꼬리 지연 완화에 유리합니다. 운영에서 체감되는 품질 상승은 p95/p99 안정화에서 확인됩니다.

### 문제 2) 번들 최적화 후에도 실제 전환은 느립니다

원인: 번들 총량은 줄었지만 동시 로드 청크 조합과 parse/compile 비용이 유지됩니다.

해결: 사용자 동선 기반 분할 + 공통 의존성 정책을 함께 설계합니다.

- 라우트 진입별 동시 청크 패턴을 추적합니다.
- shared dependency를 명시적으로 관리합니다.
- 거의 사용하지 않는 경로를 강하게 분리해 hot path를 가볍게 유지합니다.

효과: “번들 크기 감소”가 아니라 “전환 시 실행 비용 감소”로 연결됩니다.

### 문제 3) 초기 진입은 빠른데 deep-link 전환이 불안정합니다

원인: Lazy Discovery로 초기 비용을 미뤘지만, 전환 순간 비용 집중이 발생합니다.

해결: 보수적 선발견 + 확장 발견의 2단계 규칙을 사용합니다.

- 초기에는 인접 라우트만 준비합니다.
- 행동 신호가 생기면 추가 라우트를 발견합니다.
- 네트워크 상태(예: 저속/절전)에서 공격적 선발견을 완화합니다.

효과: 초기 비용과 전환 꼬리 지연 사이 균형을 유지할 수 있습니다.

### 문제 4) 팀이 회귀를 설명하지 못합니다

원인: 지표가 총합 중심이라 병목 축 분해가 불가능합니다.

해결: 전환 이벤트 스키마를 표준화하고 배포 전후 비교 기준을 고정합니다.

- 전환별 discover/module/data/rsc/ui 시간을 분리 수집합니다.
- 배포 단위로 p50/p95/p99 및 실패율을 비교합니다.
- 이상치 발생 시 라우트 단위 로그를 즉시 조회할 수 있게 합니다.

효과: “느려졌다”를 감각이 아니라 재현 가능한 사실로 다룰 수 있습니다.

### 문제 5) RSC 도입 후 체감 반응성이 낮아집니다

원인: 서버 경계를 과도하게 확장해 상호작용 경로까지 지연됩니다.

해결: 상호작용 고밀도 구간은 클라이언트 경계를 유지하고, 데이터 일관성 우선 구간만 서버 경계를 강화합니다.

- 입력/필터/정렬/탭은 즉시 반응 경로로 설계합니다.
- 권한 검증, 조합 계산, 민감 데이터 결합은 서버 경계로 이동합니다.

효과: 데이터 무결성과 반응성을 동시에 확보할 수 있습니다.

### 실무 트레이드오프 스캔

| 선택 | 얻는 것 | 잃는 것 | 경고 신호 | 대응 |
|---|---|---|---|---|
| Single Fetch 강화 | RTT 감소, 요청 단순화 | payload 비대화 가능성 | dataMs p95 증가 | 핵심/부가 분리, 응답 슬림화 |
| Module Splitting 세분화 | 초기 JS 감소 | 로딩 오케스트레이션 복잡도 | moduleLoadMs 변동성 증가 | 동선 기반 재묶음 |
| Lazy Discovery 공격적 적용 | 초기 진입 개선 | deep-link 꼬리 지연 | discoverMs p95 급등 | 선발견 규칙 보강 |
| RSC 서버 경계 확대 | 일관성/보안 강화 | 상호작용 즉시성 저하 | INP 악화 | 상호작용 구간 client 유지 |

이 표의 목적은 정답 제시가 아닙니다. 각 선택이 비용을 어디로 이동시키는지 팀이 명시적으로 합의하도록 돕는 것입니다.

## 트레이드오프

Single Fetch · Route Module Splitting · Lazy Discovery를 함께 적용할 때 가장 자주 발생하는 판단 포인트는 “초기 비용”과 “전환 순간 비용”의 교환입니다. 초기 진입을 극단적으로 가볍게 만들면 deep-link 전환 꼬리가 길어질 수 있고, 반대로 모든 것을 선준비하면 초기 진입에서 저사양 기기 부담이 커질 수 있습니다.

운영에서 유효했던 기준은 다음과 같습니다.

- 초기 진입 최적화는 LCP 개선으로 검증하고, 전환 안정화는 p95 `firstMeaningfulUiMs`로 별도 검증합니다.
- 요청 병합(Single Fetch)을 강화할수록 응답 스키마를 줄이고 캐시 무효화 정책을 더 엄격히 관리합니다.
- 모듈 분할(Route Module Splitting)을 세분화할수록 공통 의존성 정책을 명시해 중복 로딩을 통제합니다.
- 발견 지연(Lazy Discovery)을 늘릴수록 의도 신호 기반 선발견 규칙을 강화해 surprise latency를 줄입니다.

즉, 이 세 기능의 트레이드오프는 우열 비교가 아니라 비용 이동 경로를 통제하는 문제입니다. 팀이 같은 지표를 보며 같은 용어로 설명할 수 있을 때, 성능 최적화는 개인의 감각이 아니라 재현 가능한 운영 역량이 됩니다.

---

## 마무리하며

Single Fetch, Route Module Splitting, Lazy Route Discovery는 React Router 7 + RSC에서 각각 강력한 도구입니다. 그러나 실무 성능은 도구의 개별 효과가 아니라 전환 시간축에서의 결합 품질로 결정됩니다. 요청 수 감소, 코드 분할, 발견 지연이라는 단일 최적화는 쉽게 병목 이동으로 끝나지만, 전환 이벤트 기준으로 설계하면 병목을 분산하고 예측 가능한 반응성을 만들 수 있습니다.

핵심 정리는 세 가지입니다. 첫째, 성능 최적화 단위를 기능이 아니라 사용자 전환 시나리오로 잡아야 합니다. 둘째, 평균 속도보다 꼬리 지연과 실패율을 관리해야 운영 신뢰가 유지됩니다. 셋째, 지표는 보고서가 아니라 원인 분해 도구여야 합니다.

결론적으로 React Router 7 + RSC 성능 설계의 목표는 “가장 빠른 순간”이 아니라 “대부분의 순간을 안정적으로 빠르게” 만드는 것입니다. 이 기준을 유지하면 개선은 일회성 튜닝이 아니라 운영 가능한 시스템 역량으로 축적됩니다.

# figma-to-react 아키텍처 의사결정 기록: 왜 4-Layer 구조를 선택했는가

자동 코드 생성 도구는 데모 단계에서 화려해 보이지만, 실무 단계에서는 거의 항상 같은 벽에 부딪힙니다. 입력 포맷 변화, 스타일 전략 다변화, 팀별 컨벤션 충돌, 그리고 "한 번만 수동 수정했는데 다음 생성에서 다 날아간다" 같은 신뢰성 문제입니다. figma-to-react도 처음에는 단순한 "Figma JSON → JSX" 파이프라인으로 시작할 수 있었지만, 그렇게 갔다면 기능을 추가할수록 품질이 떨어지는 구조가 될 가능성이 높았습니다.

그래서 이 프로젝트는 기능보다 구조를 먼저 고정했습니다. 그 결과가 Parser → IR → Adapter → Generator라는 4-Layer 모델입니다. 이 글에서는 그 선택의 배경, 대안, 트레이드오프, 그리고 지금까지의 결과를 ADR 관점으로 정리합니다.

---

## 문제 정의: 이 프로젝트가 풀어야 했던 진짜 문제

표면적 목표는 간단합니다.

- Figma 파일을 읽는다
- React 컴포넌트를 만든다

하지만 실무 요구를 붙이면 복잡도가 급상승합니다.

1. 스타일 타깃이 하나가 아니다 (Tailwind, CSS Modules, styled-components, emotion)
2. 디자인 토큰/Variant/레이아웃 규칙이 계속 늘어난다
3. 생성 결과에 사람이 손대는 순간이 반드시 생긴다
4. 팀이 커지면 생성 규칙 변경이 배포 리스크가 된다

즉 핵심 문제는 "생성 성공"이 아니라 **생성 규칙의 장기 유지보수**입니다.

---

## ADR-001: 4-Layer 분리 (Parser → IR → Adapter → Generator)

### 결정
변환 과정을 하나의 함수 체인이 아니라 네 개의 책임 계층으로 분리했습니다.

- Parser: Figma 구조 해석
- IR: 중립 의미 모델
- Adapter: 스타일 전략 번역
- Generator: 코드 조립/출력

### 왜 이렇게 했나
Figma 원본 구조를 Generator까지 끌고 가면 모든 레이어가 입력 세부사항에 결합됩니다. 반대로 IR를 경계로 두면 입력 변화는 Parser에서 흡수할 수 있습니다.

### 대안
- 대안 A: Parser+Generator 단일 레이어
- 대안 B: 스타일 전략별 별도 파이프라인 분기

두 대안 모두 단기 속도는 빠르지만, 규칙 추가 시 유지보수 비용이 기하급수적으로 증가합니다.

### 트레이드오프
- 단기 생산성 하락
- 타입/테스트 코드 증가
- 초기 설계 비용 증가

### 현재까지 결과
- Phase 확장 과정에서 구조 파손 없이 기능 추가 가능
- 레이어별 테스트/디버깅 경로 확보

---

## ADR-002: IR를 "진실의 원천"으로 고정

### 결정
하위 레이어(Adapter/Generator)는 Figma 원본 필드를 직접 보지 않고 IR만 사용하도록 제한했습니다.

### 이유
IR는 단순 DTO가 아니라 설계 의도를 담는 모델입니다.

- 어떤 노드가 컴포넌트 경계인지
- 어떤 레이아웃이 flex로 환원되는지
- 어떤 스타일이 토큰 후보인지

이 의미를 IR에 고정하면, 입력 API가 흔들려도 출력 품질이 흔들리지 않습니다.

### 운영 효과
- 테스트 fixture를 IR 중심으로 고정 가능
- 회귀 원인 파악이 빨라짐
- adapter 추가 시 parser 변경 최소화

---

## ADR-003: Plugin / Server / CLI 하이브리드 전략

### 결정
단일 런타임에 몰지 않고, 플러그인/서버/CLI를 병행했습니다.

- Plugin: 디자이너 접점
- Server: watch/API/SSE
- CLI: 로컬/CI 자동화

### 이유
현실 워크플로우는 디자이너·개발자·CI가 분리되어 있습니다. 한 런타임으로 모두 해결하려 하면 어느 쪽이든 UX가 나빠집니다.

### 트레이드오프
- 표면적 증가(문서, 테스트, 배포)
- 런타임 간 계약 관리 필요

### 얻은 것
- 사용 맥락별 최적화 가능
- 자동화와 수동 작업을 같은 규칙으로 연결

## ADR-004: strict TypeScript + exactOptionalPropertyTypes 유지

### 결정
`exactOptionalPropertyTypes: true`를 유지하고 회피하지 않았습니다.

### 왜 중요한가
생성 도구는 경계 타입이 느슨해지는 순간, 결과 코드 품질이 먼저 망가집니다. optional 필드 취급이 흐려지면 adapter/generator에서 방어코드가 폭증하고, 결국 버그가 런타임으로 누수됩니다.

### 적용 패턴
```ts
const out = {
  id,
  ...(layout && { layout }),
  ...(style && { style }),
};
```

### 트레이드오프
- 코드 장황화
- 신규 기여자 러닝커브 상승

### 장기 효과
- 타입 계약과 런타임 의미 정렬
- 생성 코드 일관성 개선

## ADR-005: 사용자 블록 보존 (Diff Marker)

### 결정
재생성 시 사용자 수동 코드를 보존하기 위해 marker 전략 채택.

- `@f2r-user-start [id]`
- `@f2r-user-end`

### 이유
실무에서 자동 생성기가 신뢰를 잃는 가장 빠른 경로는 수동 수정 유실입니다. 한번 유실 경험이 생기면 팀은 도구를 버립니다.

### 트레이드오프
- 병합 로직 복잡도 증가
- marker 규칙 준수 필요

### 결과
- 반복 생성 사이클에서 사용자 커스터마이징 유지 가능

---

## ADR-006: 테스트 전략을 기능이 아니라 경계 기준으로 설계

### 결정
테스트를 레이어 경계와 정렬했습니다.

- Unit: parser/adapter/generator 단위
- Fixture E2E: 입력-출력 스냅샷
- 실제 API 검증: 실전 회귀 감지

### 이유
"테스트는 통과하는데 실제 파일은 깨지는" 문제를 막기 위해서입니다.

### 현재 결과
- 263 tests passing 기준선 확보
- 레이어별 회귀 탐지 가능

---

## ADR-007: 경량 서버(HTTP + SSE) 선택

### 결정
서버는 대형 웹 프레임워크가 아니라 Node HTTP + SSE 중심으로 유지.

### 이유
이 프로젝트의 서버 역할은 플랫폼 API 제공보다 변환 상태 스트리밍/자동화 보조에 가깝습니다. 경량 아키텍처가 디버깅과 유지보수에 유리합니다.

---

## ADR-008: "실 API 검증"을 릴리즈 게이트로 승격

### 결정
테스트 통과만으로 완료 선언하지 않고, 실제 Figma 파일 변환 성공을 게이트로 둠.

### 이유
Figma API, 권한, 노드 예외 케이스는 fixture만으로 커버되지 않습니다.

---

## 메타 의사결정: 이 프로젝트의 설계 철학

figma-to-react의 모든 ADR을 관통하는 철학은 다음과 같습니다.

1. 복잡도를 없애지 못하면 위치를 제한한다
2. 입력 변화는 Parser에, 의미 변화는 IR에, 표현 변화는 Adapter에 격리한다
3. 생성 품질은 타입 계약으로 지킨다
4. 사용자 신뢰는 코드 보존 전략으로 지킨다

즉 "더 똑똑한 생성기"보다 "더 안전한 경계"가 먼저입니다.

## 결론

figma-to-react는 단순 변환기가 아니라 "규칙이 계속 늘어나는 시스템"입니다. 이런 시스템은 기능보다 경계 설계가 성패를 가릅니다. 4-Layer 구조, IR 중심 설계, strict 타입, 사용자 코드 보존 전략은 모두 같은 목표를 향합니다.

> 확장할수록 더 안정해지는 생성 파이프라인

이 목표를 유지할 수 있다면, figma-to-react는 단발성 툴이 아니라 팀의 지속 가능한 생산성 인프라가 될 수 있습니다.
